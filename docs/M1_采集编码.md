# M1 · 采集 + 编码 —— 详细拆解

> 目标：把画面变成 H.264 码流。**这一步不碰网络**，产物是本地一个能被 ffplay 播放的 `.h264` 文件。
> 原则：**先 Null 源再真摄像头**。Null 源保证没有设备也能开发、能压测、能复现问题。

## M1 完成后你会有什么

- `modules/capture/`：`ISource` 抽象 + `NullSource` + `V4l2Source`，两种源命令行可切
- `modules/encode/`：`Encoder`（libavcodec 封装，低延迟参数）
- 一条真正跑起来的**两线程管线**：采集线程 →`BoundedQueue`→ 编码线程 → dump 文件
- `out.h264` 能被 `ffplay` 直接播放，画面上的**帧号肉眼可辨**
- Ctrl-C 能干净退出（队列 `close()` + join，不死锁不丢尾帧）

## M1.1 · 帧类型与采集接口 `ISource`

### 做什么
定义贯穿整条流水线的数据单元 `RawFrame` 和采集源抽象 `ISource`。

### 接口设计

```cpp
// modules/capture/Frame.h
enum class PixelFormat { YUV420P };      // M1 只支持这一种, 编码器要的就是它

struct RawFrame {
    std::vector<uint8_t> data;           // YUV420P 紧凑排布, 大小 w*h*3/2
    int      width  = 0;
    int      height = 0;
    PixelFormat fmt = PixelFormat::YUV420P;
    uint64_t captureMs = 0;              // 采集时刻(steady_clock 毫秒), 端到端延迟的起点
    uint64_t frameId   = 0;              // 从 0 递增, 调试与画面标号用

    RawFrame() = default;
    RawFrame(const RawFrame&) = delete;              // 一帧 1080p ≈ 3MB, 禁止隐式拷贝
    RawFrame& operator=(const RawFrame&) = delete;
    RawFrame(RawFrame&&) = default;
    RawFrame& operator=(RawFrame&&) = default;
};
```

```cpp
// modules/capture/ISource.h
struct SourceConfig {
    int width = 640, height = 480, fps = 30;
    std::string device = "/dev/video0";   // 仅 V4L2 用
};

class ISource {
public:
    virtual ~ISource() = default;
    virtual Status open(const SourceConfig& cfg) = 0;
    virtual Status readFrame(RawFrame& out) = 0;   // 阻塞取一帧; 源结束返回 Code::Closed
    virtual void   close() = 0;
};

std::unique_ptr<ISource> createSource(const std::string& kind);  // "null" | "v4l2"
```

### 执行步骤
1. `RawFrame` 显式 delete 拷贝、default move —— 队列里传的是 `std::unique_ptr<RawFrame>`，
   这样"想拷贝一帧"会**编译报错**而不是悄悄慢下来
2. `readFrame` 返回 `Status` 而不是 `bool`：调用方要能区分"源正常结束(Closed)"和"设备炸了(IoError)"，
   前者正常退出，后者要报警
3. `captureMs` 用 `steady_clock`（单调，不受系统改时间影响）；日志时间戳才用 `system_clock`

### 验收标准
- [x] `RawFrame f2 = f1;` 编译失败，`RawFrame f2 = std::move(f1);` 通过
- [x] `BoundedQueue<std::unique_ptr<RawFrame>>` 能编译（M0 已验证 move-only 支持）
- [x] `createSource("bogus")` 返回 nullptr，调用方报错退出而不是崩（随 M1.2 落地）

## M1.2 · `NullSource`（先做这个）

### 做什么
不依赖任何硬件，生成**可辨识**的测试画面：移动色块 + 大号帧号。

### 为什么帧号必须画在画面上
后面 M2 验"逐字节一致"、M3 看延迟、M4 看丢帧花屏，全靠肉眼对帧号。
控制台打印的帧号证明不了**画面**对不对。

### 执行步骤
1. 画背景：随帧号缓慢变化的渐变或滚动色块（一眼能看出画面在动、卡没卡）
2. 画帧号：**自己写 5×7 点阵数字**，别为了画几个数字引入字体库（`static const uint8_t DIGITS[10][7]`）
3. 直接写 YUV420P：Y 平面写亮度，U/V 平面填 128（灰）即可；要彩色再单独填 U/V
4. **帧率节流**：绝对时间基准，不要 `sleep(1/fps)`

```cpp
// 错: 每帧误差累加, 跑一分钟就漂了
std::this_thread::sleep_for(std::chrono::milliseconds(1000 / fps));

// 对: 以 start_ 为基准算第 n 帧的应到时刻, 误差不累积
auto deadline = start_ + std::chrono::microseconds(frameId_ * 1000000 / fps_);
std::this_thread::sleep_until(deadline);
```

### 验收标准
- [x] `--source=null --dump-raw=out.yuv` 产出的文件大小 = `w*h*3/2*帧数`
      （10 帧 640x480 = 4608000 字节，精确相符）
- [x] `ffplay -f rawvideo -pixel_format yuv420p -video_size 640x480 out.yuv` 能播，
      **帧号连续递增、无跳变**
- [x] 跑 60 秒 30fps，实际帧数在 1800±5 之间（节流没漂）
      —— 1800 帧实测 59967ms，理论值 1799/30=59966.7ms，**偏差 <1ms**

## M1.3 · `Encoder`（libavcodec 封装）

### 做什么
YUV420P → H.264 Annex B 码流，**低延迟参数**。

### 接口设计

```cpp
struct EncoderConfig {
    int width = 640, height = 480, fps = 30;
    int bitrateKbps = 2000;
    int gop = 30;                 // 关键帧间隔(帧), 短 GOP = 起播快/抗丢强, 代价是码率
};

struct EncodedFrame {
    std::vector<uint8_t> data;    // Annex B, 含起始码
    uint64_t captureMs = 0;       // 从 RawFrame 透传, 别在这里重新取时间
    uint64_t frameId   = 0;
    bool     isKey     = false;   // IDR 标志, M4 的丢包策略靠它决定"保谁丢谁"
};

class Encoder {
public:
    Status open(const EncoderConfig& cfg);
    Status encode(const RawFrame& in, std::vector<EncodedFrame>& out);  // 可能吐 0 或多帧
    Status flush(std::vector<EncodedFrame>& out);                       // 收尾, 取出缓存
    void   close();
};
```

### 低延迟参数（这是能讲的部分）

```cpp
av_opt_set(ctx->priv_data, "preset", "ultrafast", 0);
av_opt_set(ctx->priv_data, "tune",   "zerolatency", 0);  // 关 lookahead / 关 B 帧 / 关帧级多线程
ctx->max_b_frames = 0;        // B 帧要等后续帧才能编, 天然增加延迟
ctx->gop_size     = cfg.gop;
ctx->time_base    = {1, cfg.fps};
ctx->flags       |= AV_CODEC_FLAG_GLOBAL_HEADER;  // 见下方取舍
av_opt_set(ctx->priv_data, "repeat-headers", "1", 0);  // 每个 IDR 前重复 SPS/PPS
```

> **SPS/PPS 取舍**：默认只在码流开头出现一次。M5 一推多拉时，中途加入的观众收不到 SPS/PPS 就**永远解不出画面**。
> 代价是每个 IDR 多几十字节。现在就打开 `repeat-headers`，别等 M5 再回来查这个"只有新观众黑屏"的诡异 bug。

### 执行步骤
1. RAII 包住 `AVCodecContext` / `AVFrame` / `AVPacket`（`avcodec_free_context` 等在析构里调）
2. 用 `avcodec_send_frame` / `avcodec_receive_packet` 的**新 API**，老的 `avcodec_encode_video2` 已废弃
3. `receive_packet` 要**循环取到 `EAGAIN`** —— 一次 send 可能吐出多个包，也可能一个都不吐
4. `pts` 必须自己设且**单调递增**（用 frameId），否则编码器会警告甚至丢帧
5. 拷贝 `RawFrame` 到 `AVFrame` 时按 **`linesize` 逐行拷**，不能整块 memcpy（见踩坑 3）
6. `close()` 之前先 `flush()`，把编码器缓存的帧吐干净，否则 dump 文件尾部缺几帧

### 验收标准
- [x] `--source=null --dump=out.h264` 产出的文件 `ffplay out.h264` 能播，帧号可辨
      （解出第 45 帧，画面上就是 "45"，编码前后帧序一一对应）
- [x] `ffprobe -show_frames out.h264 | grep key_frame=1 | wc -l` ≈ 总帧数 / gop
      （90 帧 gop=30 → 关键帧 3 个，精确）
- [x] 用 `xxd out.h264 | head` 确认开头是 `00 00 00 01 67`（SPS），不是裸 AVCC
- [x] 编码 1000 帧无内存增长（RAII 没漏）
      （峰值 RSS：100 帧 28468 KB / 1000 帧 28468 KB，一字节不差）

> ⚠️ 上面"低延迟参数"里的 `AV_CODEC_FLAG_GLOBAL_HEADER` + `repeat-headers=1` 是**错的**，实测：
> - libx264 的 AVOption 里**没有** `repeat-headers`，`av_opt_set` 静默失败
> - 设了 `GLOBAL_HEADER`：码流里 SPS 出现 **0 次**，开头是 `00 00 01 06`(SEI)
> - 不设：SPS 在**每个 IDR 前**各出现一次，开头 `00 00 00 01 67`
>
> 该 flag 的语义是"把 SPS/PPS 抽到 extradata、**不要**放进码流"，是给 MP4/FLV 容器用的。
> 正确做法是**什么都不设**——x264 默认就重复。实现按这个走。

## M1.4 · 两线程管线接起来

### 做什么
把 M0 的 `BoundedQueue` 真正用上：采集线程 → 队列 → 编码线程 → dump。
**这是 M0 那套基础设施第一次接受检验。**

```text
[采集线程] --BoundedQueue<unique_ptr<RawFrame>>--> [编码线程] --> out.h264
```

### 执行步骤
1. `app/sender/main.cpp` 只做**装配**：解析配置 → 建 source/encoder/queue → 起线程 → 等退出 → 收尾
   （业务逻辑不许写在 main 里，这是与旧 demo 的分界线）
2. 退出路径：`SIGINT` handler **只设一个 `std::atomic<bool>`**，别在信号处理函数里打日志或加锁
   （signal handler 里只有 async-signal-safe 的函数能调）
3. 收尾顺序：停采集 → `queue.close()` → join 编码线程 → `encoder.flush()` → 关文件
   **顺序反了就丢尾帧**
4. 队列容量 `--cap` 可配（默认 4）；退出时打印 `peak()`：
   peak 长期贴着 cap 说明编码跟不上采集，这条曲线 M6 还要用

### 验收标准
- [ ] Ctrl-C 后 1 秒内干净退出，无死锁、无 "terminate called"
- [ ] 退出日志打印总采集帧数 / 总编码帧数 / 队列 peak，**采集数 == 编码数**（没丢帧）
- [ ] 故意把 `--cap=1` 且编码器调慢，能观察到 peak 打满、采集端被阻塞（背压生效）

## M1.5 · `V4l2Source`

### 做什么
真摄像头采集。**M1.0 里确认过环境再做这一步。**

### 执行步骤
1. `open` → `VIDIOC_QUERYCAP`（确认支持 `V4L2_CAP_VIDEO_CAPTURE` + `V4L2_CAP_STREAMING`）
2. `VIDIOC_S_FMT` 设分辨率与像素格式；**驱动可能改你的参数**，S_FMT 返回后要**回读确认**实际值
3. `VIDIOC_REQBUFS` + `mmap` 申请缓冲（一般 4 个），RAII 包住 `munmap` 和 `close(fd)`
4. `VIDIOC_QBUF` 入队 → `VIDIOC_STREAMON` → 循环 `VIDIOC_DQBUF` 取帧 → 处理 → 再 `QBUF` 归还
5. 摄像头多半输出 **YUYV(YUV422)**，用 `sws_scale` 转 YUV420P（`SwsContext` 建一次复用，别每帧建）
6. `ioctl` 返回 `EINTR` 要重试，`EAGAIN` 要等（配 `select`/`poll` 加超时，别裸阻塞）

### 验收标准
- [ ] `--source=v4l2 --device=/dev/video0 --dump=cam.h264`，ffplay 能看到真实画面
- [ ] 实际分辨率与请求不一致时**打 WARN 并按实际值走**，不是崩或者静默出花屏
- [ ] 采集中拔掉设备：报 `IoError` 日志后干净退出，不崩
- [ ] `--source=null` / `--source=v4l2` 切换只改命令行，**不改一行代码**（ISource 抽象成立）

## ⚠️ 常见坑提醒（M1 预警）

1. **WSL2 没有 `/dev/video0`** —— M1.0 就要拍板，别写完 V4L2 才发现没法验证。
2. **FFmpeg 新旧 API 混用**：`avcodec_encode_video2` / `av_register_all` 在 4.0+ 已废弃或移除。
   网上教程一半是旧的，认准 `send_frame` / `receive_packet`。
3. **`AVFrame` 的 `linesize` 有对齐**：`linesize[0]` 通常大于 `width`（补齐到 32/64 字节）。
   按 `width` 整块 memcpy 会得到**斜着撕裂的画面**——这是 YUV 处理的经典翻车点，必须逐行拷。
4. **`send_frame` 之后不能立刻改 `AVFrame` 数据**：编码器可能仍持有引用。
   复用同一个 `AVFrame` 前调 `av_frame_make_writable`。
5. **`receive_packet` 要循环取到 `EAGAIN`**：一次 send 不保证一次 receive，写成 if 会漏包。
6. **忘了 `flush()`**：编码器内部缓存的帧不吐出来，dump 文件尾巴少几帧，
   而且这个错误在短测试里几乎看不出来。
7. **`pts` 不设或不递增**：编码器警告刷屏、码率控制失效、播放器时间轴错乱。
8. **SPS/PPS 只出现一次**：M5 中途加入的观众永远黑屏。M1 就打开 `repeat-headers`。
9. **B 帧没关干净**：`zerolatency` 之外还要显式 `max_b_frames = 0`。有 B 帧就必须等后续帧，
   延迟直接加一个 GOP 的零头——这跟项目立意冲突。
10. **fps 节流用相对 sleep**：误差累积，跑十分钟能漂出好几秒。用绝对 deadline。
11. **`RawFrame` 被隐式拷贝**：一帧几 MB，拷一次就是一次 memcpy。用 delete 拷贝构造让编译器帮你拦。
12. **信号处理函数里干活**：只设 `atomic<bool>`，打日志/加锁都是未定义行为。
13. **退出顺序**：停采集 → close 队列 → join → flush 编码器 → 关文件。反了就丢尾帧。
14. **`SwsContext` 每帧重建**：性能杀手，建一次存成员。

## 建议的执行顺序

```text
M1.0 环境扫雷 → M1.1 Frame/ISource → M1.2 NullSource(能 dump YUV 看到画面)
   → M1.3 Encoder(能 dump h264 播出来) → M1.4 两线程管线接起来
   → M1.5 V4L2Source → M1.6 单测 + tag
```

**M1.2 和 M1.3 各自能独立看到结果**（一个出 YUV、一个出 H.264），
中间不要跳步——先让画面出来，再谈接管线。每小步提交一次。
