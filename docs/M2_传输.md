## M2 完成后你有了什么

```text
[capture] --RawFrame--> [encode] --EncodedFrame--> [send] --UDP--> [recv] --> [assemble] --> 落盘
```

- 一套自研的应用层协议（`docs/PROTOCOL.md`），六种包类型，其中 DATA 在 M2 落地，
  FEC / NACK / PLI 的类型码**预留但未实现**
- 四块可独立测试的积木：`Packet`（编解码）、`UdpSocket`（RAII 封装）、
  `Packetizer`（切片）、`FrameAssembler`（组包 + 丢包统计）
- 发送端从两级线程变成三级，接收端从零变成一条完整管线
- 验收判据：两端 H.264 码流 **`cmp` 逐字节一致**

M2 的四块积木**都不碰编解码器**，`lltransport` 只依赖 `llcommon`。这是它能被单测
覆盖到每个分支的原因，也是 M5 的服务端可以直接复用它的原因。

## M2.0 · 协议规格与包头编解码（先做这个）

### 做什么

把 `PROTOCOL.md` 从"只有结构体定义"补成"照着能写出可互通的实现"，然后实现
`PacketHeader`(12B) / `DataHeader`(9B) 的四个编解码函数。

### 为什么第一步是它

它是**纯逻辑**：不碰 socket、不碰帧数据、没有时间和并发。单测能覆盖到每一个分支，
后面三块积木全建立在它之上。先做有 I/O 的部分，第一个 bug 就分不清是协议算错了
还是网络没通。

### 接口

```cpp
constexpr uint8_t  PROTOCOL_VERSION = 1;
constexpr size_t   PACKET_HEADER_SIZE = 12;   // 写死, 不用 sizeof
constexpr size_t   DATA_HEADER_SIZE   = 9;
constexpr size_t   MAX_PAYLOAD        = 1200;
constexpr size_t   MAX_DATA_PACKET_SIZE = 12 + 9 + 1200;   // 1221

enum class PacketType : uint8_t { Data=1, Fec=2, Nack=3, Pli=4, Signal=5, Stats=6 };

Status encodePacketHeader(const PacketHeader&, uint8_t* buf, size_t bufLen);
Status decodePacketHeader(const uint8_t* buf, size_t bufLen, PacketHeader& out);
Status encodeDataHeader  (const DataHeader&,   uint8_t* buf, size_t bufLen);
Status decodeDataHeader  (const uint8_t* buf, size_t bufLen, DataHeader& out);
bool   seqNewerThan(uint32_t a, uint32_t b);
```

### 定死的几条

**① 不许 `memcpy` 整个结构体上网。** `#pragma pack` 只让结构体*看起来*是 12 字节：
`sizeof` 不保证等于各字段线上长度之和（填充字节不属于协议），且多字节整数在内存里
是本机字节序 —— 小端机上 `0x12345678` 存成 `78 56 34 12`，直接拷就把顺序发反了。
必须逐字段按协议规定的偏移读写，`PACKET_HEADER_SIZE` 也得写死成 12 而不是
`sizeof(PacketHeader)`。

禁的是**一次拷整个结构体**；单个字段先转字节序、再 `memcpy` 到固定偏移是安全的。

**② `seq` 的比较一律用有符号差值。**

```cpp
bool seqNewerThan(uint32_t a, uint32_t b) { return int32_t(a - b) > 0; }
```

`seq` 是 32 位、每包 +1，**一定会回绕**。直接写 `a > b`，在 `0xFFFFFFFF → 0` 那一刻
会把最新的包判成最老的包 —— 表现为"跑了几十分钟后突然全是乱序"，只在长时间运行时
复现，极难查。前提是两个 seq 相距不超过 2^31（约 21 亿包），所有滑动窗口协议都有
这个前提。

**③ 解码先写局部变量，整体赋给出参。** 失败时出参不留半解析的垃圾字段。

**④ 两类失败用两个错误码，因为调用方的反应完全不同。**

| 情况 | 错误码 | 调用方该做什么 |
|---|---|---|
| 畸形包（版本不认识 / 类型未定义 / 分片自相矛盾） | `NetError` | 丢包 + 计数，继续收下一个 |
| 缓冲区太短、参数非法 | `InvalidArg` | 改代码 |

混成一个错误码，接收循环就分不清"该丢包继续"还是"该报警退出"。

**⑤ 编码时也查 `type`。** 这条是实现阶段补的（`befef41`）：`encodeDataHeader` 会挡住
自相矛盾的分片字段，`encodePacketHeader` 一开始却不查 `type`。本端把 type 写错只会
表现为"对端一直丢包"，排查方向指向网络，**bug 却在发送端**。把错误挡在离 bug 最近
的地方。类型合法性收进 `isKnownPacketType()`，编解码两边共用一处判定 —— 分两处写，
加新类型时迟早漏改一边。

### 整包为什么是 1221 字节

```text
1500 (以太网 MTU) − 40 (IPv6 头) − 8 (UDP 头) = 1452
1221 = 12 (通用头) + 9 (DATA 头) + 1200 (载荷)
余量 231 字节留给隧道 / VPN 的额外封装
```

**宁可小也不要触发 IP 分片**：IP 分片后任意一片丢失整个 IP 包都废掉，等于把丢包率
放大数倍，而且这一层的丢失**我们自己的 FEC/NACK 完全看不见**。

### 验收

`tests/test_packet.cpp` 19 条，分五组：线上布局（逐字节核对偏移与大端序、哨兵字节
确认不越界）、往返一致（含边界值与全部六种包类型）、缓冲区边界、畸形包、`seq` 回绕。

## M2.1 · `UdpSocket`

### 做什么

RAII 封装 socket 的六个动作：`open` / `bind` / `sendTo` / `recvFrom` /
`localEndpoint` / `close`。外加一个两端 main 共用的 `parseEndpoint("ip:port")`。

### 接口

```cpp
struct Endpoint { std::string ip; uint16_t port = 0; std::string toString() const; };
Status parseEndpoint(const std::string& text, Endpoint& out);

class UdpSocket {
public:
    UdpSocket() = default;
    ~UdpSocket();
    UdpSocket(const UdpSocket&) = delete;              // 可移动不可拷贝
    UdpSocket(UdpSocket&& other) noexcept;

    Status open();
    Status bind(const Endpoint& local);
    Status sendTo(const Endpoint& remote, const uint8_t* data, size_t len);
    Status recvFrom(uint8_t* buf, size_t bufLen, size_t& outLen,
                    Endpoint& outFrom, int timeoutMs);
    Endpoint localEndpoint() const;
    void close();                                       // 幂等
    bool isOpen() const;
};
```

### 定死的几条

**① 错误码分工**：未 `open` 是 `Closed`，参数错是 `InvalidArg`，syscall 失败一律
`NetError`，**收包超时是 `Timeout`** —— 超时是正常情况不是故障，收包线程正是靠它
周期性检查停止标志。

**② 数据报大于缓冲区必须报 `NetError`，不许悄悄截断。** 实现上靠 `recvfrom` 的
`MSG_TRUNC`：它让返回值是**真实长度**而不是拷进来的长度，否则"截断"这件事在
应用层根本观察不到。

**③ `bind(port=0)` 之后用 `localEndpoint()` 回读实际端口。** 和 M1 的
`ISource::actualConfig()` 是同一条原则：**请求值不等于生效值，生效值必须能读回来**。
测试全跑在回环上、端口由内核分配，因此不依赖外部网络也不会在 CI 上撞端口。

**④ 移动后源对象置 `-1`**，避免 double close；移动赋值先查自赋值。

### 实现阶段补的两条

- **`socket()` 直接带 `SOCK_NONBLOCK | SOCK_CLOEXEC` 建好，不走事后 `fcntl`。**
  分两步中间有窗口；而 `CLOEXEC` 漏设会让子进程继承 fd —— 端口在本进程 `close`
  之后**仍被占着**，表现为"明明退出了还是 Address already in use"。
- **`waitReadable` 的 `EINTR` 重试要扣除已等待时间**，不能重新计时。否则信号频繁
  时超时永远到不了，`--recv-timeout` 形同虚设。

### 验收

`tests/test_udp_socket.cpp` 17 条，全部回环。

## M2.2 · `Packetizer`

### 做什么

一帧 H.264 码流切成若干 DATA 包。

### 接口

```cpp
/** 只读视图, 故意不叫 EncodedFrame */
struct EncodedFrameView {
    const uint8_t* data = nullptr;
    size_t   len       = 0;
    uint64_t frameId   = 0;
    uint64_t captureMs = 0;
    bool     isKey     = false;
};

class Packetizer {
public:
    Packetizer(uint16_t streamId, uint32_t initialSeq);
    Status packetize(const EncodedFrameView& frame, std::vector<PacketBuffer>& out);
    uint32_t nextSeq() const;
};
```

### 为什么收 `EncodedFrameView` 而不是 `EncodedFrame`

接收端也要用 `lltransport`，但**它不该知道 libavcodec 的存在**。发送端多写一行构造
视图，换来接收端编译时不背编码器的头文件。这条决定后来在 M3 兑现了：`lldecode` 和
`lltransport` 是两个互不依赖的库。

### 定死的几条

**① 分片数向上取整，但不用加法形式。**

```cpp
// 用这个
const size_t count = len / MAX_PAYLOAD + (len % MAX_PAYLOAD != 0);
// 不用这个 —— len 接近 SIZE_MAX 时溢出
const size_t count = (len + MAX_PAYLOAD - 1) / MAX_PAYLOAD;
```

帧长恰好是 `MAX_PAYLOAD` 整数倍时不多切一片空的。

**② `seq` 跨帧连续自增，与 `frameId` 分工不同；回绕不跳过 0。**
这是本协议相对旧 demo 的主要改进 —— 旧 demo 用一个 `nalu_index` 兼两职，
重传包和 FEC 包一进来就把帧内序号搅乱，丢包检测和组包互相干扰。

**③ 同一帧所有分片共用一个 `captureMs`，不在打包时重新取时间。**
它是端到端延迟的**起点**，一帧一个值；打包时重取会把打包耗时从延迟里抹掉。

**④ 关键帧标志打在每一片上。** 单片就能判断这一包值不值得保，
**供 M4 按包做背压** —— 那时不需要先组齐帧才知道能不能丢。

**⑤ 校验全部前置：失败时 `out` 不变、`seq` 不推进。**
实现上靠结构保证而不是靠每条错误路径自觉：`seq` 先在局部变量上推进，
**整帧填完才写回 `nextSeq_`**。

**⑥ `out` 由调用方复用，内部只 `resize` 不 `shrink`。** 每帧一次堆分配是白给的开销。

**⑦ `encodePacketHeader` / `encodeDataHeader` 在这里失败一律包成 `Internal`。**
缓冲区是本函数按线上长度算好的，它们报错只可能是本文件算错了偏移 —— 那是 bug，
不是坏输入。

### 验收

`tests/test_packetizer.cpp` 15 条。

## M2.3 · `FrameAssembler`

### 做什么

分片进、完整帧出，顺带按 `seq` 统计丢包。这是 M2 里唯一有状态、也唯一出过真 bug 的一块。

### 接口

```cpp
struct AssemblerStats {
    uint64_t packetsReceived = 0;
    uint64_t packetsMalformed = 0;    // 与丢包分开计, 两者含义不同
    uint64_t packetsDuplicate = 0;
    uint64_t packetsTooLate = 0;
    uint64_t framesCompleted = 0;
    uint64_t framesDropped = 0;
    uint32_t baseSeq = 0, highestSeq = 0;
    bool     started = false;

    uint64_t expectedPackets() const;
    uint64_t packetsLost() const;     // expectedPackets() - packetsReceived, 下限 0
};

class FrameAssembler {
public:
    explicit FrameAssembler(size_t maxPendingFrames);
    Status offer(const uint8_t* packet, size_t len);
    bool   pop(AssembledFrame& out);
    const AssemblerStats& stats() const;
    size_t pendingFrames() const;     // 含墓碑, 用于验证内存有界
    void   reset();
};
```

### 四个定死的设计决定

**① 只组包，不排序。** 帧 5 先齐就先交出去，哪怕帧 4 还缺一片。按显示顺序排是
M3 `JitterBuffer` 的事 —— 混进来就没法单独测"组包对不对"。

**② 内存按帧数封顶。** 残帧永远等不齐是**常态**（那一片就是丢了）。不设上限的话
每丢一包就留下一个再也不会完成的条目，跑一晚上就是几个 GB。这种泄漏比队列积压更阴：
积压至少会在延迟上表现出来，它只会安静地涨。

上限用**帧数**而不是字节数，因为帧数直接对应"还能容忍多大的乱序"，是个能讲清楚的
取舍轴。

**③ 交付后留墓碑。** 挡住整帧重传导致的重复交付，同时释放分片内存。

**④ 丢包由 `seq 跨度 − 实收` 算出，不在发现缺口的当场累加。**

收到 `seq` 0,1,3 就记一笔丢包的话，2 号包晚一点到了，**那一笔再也减不回去**，
丢包率只会虚高 —— 然后 M7 的码率自适应照着虚高的数字降码率，越降越糟。
改成用跨度减实收：迟到的包一到，实收 +1，算出来的丢包自动就减回去了。
RFC 3550 里 RTP 的接收报告是同一个口径。

### 实现阶段改掉的一条（NOTES D19）

框架里写的是"容量满就淘汰最老的一条"。实现时发现这会被**更老的迟到帧**反过来利用：

```text
一个落后整个窗口的分片到达
  -> 挤掉最老的帧 5, 水位推到 5
  -> 它自己剩下的分片又被这个水位挡住
结果: 帧 5 白丢了, 挤进来的那帧也补不齐 —— 一个包坏两件事
```

改成**新来的帧必须比现有最老的更新才有资格挤掉它**。这条规则同时保证了水位单调，
`retiredFrameId_` 不会倒退。

值得记的不是这个 bug，而是**它为什么没被 22 条用例测出来**：写用例时脑子里的模型是
"帧号大致递增，偶尔乱一点"，压根没想过"新到的比表里所有帧都老"。而 M4 上了 NACK
重传之后这种包会**大量出现** —— 重传的分片天然比当前在收的帧老得多。

> 一般化：凡是**淘汰 / 驱逐**逻辑，都要单独问一句"被淘汰的一定该淘汰吗"。

### 回绕在这里也要处理

`frameId` 和 `seq` 都是 32 位循环计数器，淘汰"最老"的那条也必须用 `seqNewerThan` 比，
否则回绕点上会把刚到的新帧淘汰掉。

### 验收

`tests/test_frame_assembler.cpp` 23 条。

## M2.4 · 两端接起来

### 发送端加第三级线程

```text
[capture] --RawFrame--> [encode] --EncodedFrame--> [send]
```

**打包和发送独立成线，不搭在编码线程尾巴上。** 三个理由：

1. `sendTo` 会被内核发送缓冲顶住，挂在一起会让**网络一卡帧率也掉**；
2. M4 的 pacing 控速要按自己的节奏走；
3. M4 的重传缓存也是。

`target.ip` 为空时这一级**不存在**，行为与 M1 完全一致 —— 排查时这一档能一句话把
范围劈成两半：关掉发送还坏就是采集/编码的事。

`encodeLoop` 用 `sendQueueClosed` 标记区分"编码错了"和"发送侧先退了"，两种情况都要
唤醒采集线程并关掉两个队列，不能把生产者堵在满队列上。`sendLoop` 里 `packetize`
失败才算致命（那是本端 bug），单个 `sendTo` 失败只计数继续。

### 接收端：`ReceiverPipeline`

M2 版本是**单线程**跑完 `recvFrom → offer → pop → 落盘`。当时没有解码和渲染，
多切一个线程只多一个 `join` 要收尾。（M3 才拆成三线程。）

**`open()` 与 `run()` 分开**，让"端口已就绪"成为一个**可等待的时刻**，测试不必
`sleep` 猜 —— 慢机器上靠 sleep 必然偶发失败。

**空闲计时以"收到包"为准而不是"组齐帧"。** 只收到分片却一直组不齐时网络显然还活着，
按帧计时会把"一直丢包"误判成"对端已停止"然后自己退出。

### 验收（真机，两个可执行文件，回环 60 帧）

```text
sender:   encoded=60 bytes=21036 packets_sent=66 send_errors=0
receiver: frames=60  bytes=21036 packets=66 lost=0 malformed=0
cmp send.h264 recv.h264  ->  逐字节一致
```

**判据是 `cmp` 而不是 ffplay**：播放器对残缺码流很宽容，少了一个分片照样往下播，
花那么几帧屏靠肉眼根本发现不了。字节比对是唯一能把"看起来对"和"真的对"分开的东西。

## 留给 M4 的账

M2 定下的东西里，有六处明确写着"等 M4"。M4 开工前必须先看这一节。

### ① `packetsLost()` 的口径，M4 一开重传就失准 ⚠️

出处：`FrameAssembler.h:93`

> 会被重复包压低（实收里含重复），这是 RTP 同款口径下的已知偏差。真要精确区分，
> 得为每个 seq 记一个位图 —— 那是 M4 重传窗口的事。

M2 时重复包几乎不存在，所以这个偏差**只是理论上的**。M4 一上 NACK，重传包就是
重复包，它从零变成常态：算法是 `seq 跨度 − 实收`，重传让"实收"虚高，
**丢包率被系统性压低**。

要命的地方在于 M4 的验收判据就是「X% 丢包下不花屏」—— **测量工具自己会在 M4 失准，
而且是往"看起来更好"的方向偏。** 这是 [[D20]]「沉默的分母」的翻版，只不过这次坏的
是分子。

**已决定并进 M4 一起做，不单独提前修。**

### ② `minOffset_` 只减不增 + 时钟频差

出处：`JitterBuffer.h:253`（M3 写的，但归 M4 还）

> `minOffset_` 只减不增，网络永久变好之后水位不会自动收窄；时钟频差也会让映射慢慢漂。
> 两者都归 M4 的自适应水位处理。

M4 的「自适应 jitter buffer」这一项就是来还这笔账的。问题已经描述清楚，
M4 要决定的是**用什么信号驱动水位**。

### ③ 发送队列满时阻塞而不丢帧

出处：`SenderPipeline.h:61`

> 队满时编码线程**阻塞**等待，M2 就这样。M4 会改成丢非关键帧保 IDR —— 那时才有
> "丢什么"的判断依据（flags 里的关键帧位）。现在阻塞是诚实的：本机回环发不出去
> 只可能是自己写错了，悄悄丢包只会把 bug 藏起来。

判断依据 M2 时就备好了 —— `Packetizer` 的契约第 ④ 条「关键帧标志打在每一片上，
供 M4 按包做背压」。这条可以直接动手。

### ④ 接收端从来没有发过一个字节 ⚠️

`PROTOCOL.md` 的时序图画了 NACK 和 PLI 是**收→发**，`PacketType` 里
`Nack=3 / Pli=4` 也定义好了 —— 但 `ReceiverPipeline` 只 `bind` + `recvFrom`，
**一次 `sendTo` 都没有**。`ReceiverPipeline.cpp:203` 那个 `Endpoint from` 拿到了
对端地址，之后再没被读过。

对称地，`SenderPipeline` 也从来没 `recvFrom` 过（`SenderPipeline.cpp` 里只有
`open` / `sendTo` / `close`）。

**反向通道是 M4 唯一从零长出来的结构**，NACK 和 PLI 都压在它上面。M2 没做是对的
（当时没有任何东西需要往回发），但也因此**没有任何设计**：谁 bind、用不用同一个
socket、`from` 每包都可能不同时认哪一个、发送端在哪条线程收 —— 全是 M4 要新定的。

### ⑤ 没做 `sendmsg` / `iovec` 零拷贝（等 M6，不是 M4）

现在是把包头和载荷拼进一块连续缓冲再 `sendto`。`sendmsg` + `iovec` 可以让内核
直接从两段内存收集，省掉这次拷贝。

没做是因为**还没有证据说它值得**：1200 字节的 memcpy 在 30fps 下每秒才几十次，
真正的开销大概率在 syscall 本身。触发条件：M6 压测时 memcpy 出现在火焰图上。

### ⑥ 已经还清的两笔（不用再管）

- **`pop()` 一次可能放出多帧**（`FrameAssembler.h:162`，M4 的 FEC 恢复会一次放出
  好几帧）—— `ReceiverPipeline.cpp:221` 已经是 `while (assembler_.pop(frame))`，合规。
- **PLI 的落点**（`JitterBuffer.h:49`）—— `dropUntilKeyFrame()` M3 已经实现，
  PLI 收到之后有地方接。
