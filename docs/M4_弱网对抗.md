# M4 · 弱网对抗 —— 详细拆解与实测

> 目标：**在丢包和延迟抖动下把画面保住**。M3 打通了全链路并给出了延迟数字，
> 但那是在一条零丢包、零抖动的回环上。M4 要回答的是：**网络开始坏了之后，
> 还能不能看，以及每一层机制各自值多少。**
>
> 原则：**每一条结论都要有一个能推翻它的实验。** 这一版里有三条设计假设
> 被自己的实验推翻了，都留在文里。

## M4 完成后你会有什么

## M4.0 · 先有尺子，再有活

**不能拿真网络当测试环境。** 真丢包不可复现，改一行代码之后数字变了，
分不清是代码的功劳还是这一趟网络恰好好一点。

所以第一件事是丢包注入器，而它有两条硬要求：

**① 必须是纯函数，不能是有状态的 PRNG。**

```cpp
bool shouldDropPacket(const LossConfig&, uint32_t seq, PacketType type, bool isRetransmit);
```

有状态的 PRNG「每个包抽一次」，在 NACK 出现的那一刻就崩了：重传包会多消耗几次抽取，
**从此之后每一个包的命运都偏移了**。同一个种子在开 NACK 和不开 NACK 时丢的不是同一批包，
消融实验直接失去意义。做成 `hash(seed, type, seq)` 就没有这个问题。

**② 注入在接收端。** 丢包发生在传输途中，而接收端注入不需要改发送端一行代码，
也不会污染发送端的统计（`packetsSent` 仍然是真实上线的包数）。

> 代价见「已知限制」：接收端注入**不产生延迟**，所以回环上的重传是免费的。
> 这条一直到 M4.5 引入 `tc netem` 才被补上。

## M4.1 · NACK 与重传

### 判定「真丢了」用包数，不用时间

一个 seq 之后又收到了**至少一帧的包数**那么多个更新的包，才判它真丢了。

这个阈值恒等于**一个帧周期**，而且与码率无关：设帧率 f、每帧 k 个包，
则 k 个包 = k / (f·k) = 1/f 秒 —— **k 约掉了**。
写成固定常数反而会「码率翻倍 → 包率翻倍 → 同样 N 个包的时间减半 → 乱序容忍悄悄变差」。

一切以包数推进还有一个好处：**流停了自然就不再产生请求**，
不会对着一个已经退出的对端狂发 NACK。

### 一个只有一行、但会毁掉整份报告的守卫

```cpp
if (forwardDistance >= config_.windowPackets) { /* 按"换了一条流"处理 */ }
```

`seq` 是包头里**唯一没有任何校验的字段** —— 版本、类型、分片自洽性都查过了，
但 32 位里每一个取值都合法。而 `seqNewerThan` 只保证差值为正，上界是 2^31。

一个位翻转、一个上一轮残留的包、同端口上另一个进程，都能让 `forwardDistance` 变成十亿级，
于是 `lostForReal` 被永久污染 —— **而它正是「X% 丢包下不花屏」里那个 X 的来源**。

### 缓存存帧不存包

重传缓存里存 `EncodedFrame`，要重传时**按需重新分片**，而不是把打好的包存一份。
省的是内存，费的是我们自己的实现工夫 —— 这个项目以带宽和延迟为主，这笔交换划算。

配套的是把单片打包做成**自由函数**：

```cpp
Status packetizeOneFragment(uint16_t streamId, uint32_t seq, ..., PacketBuffer& out);
```

放在类外，它连 `nextSeq_` 都看不见 —— **重传结构上不可能推进发送序号**。
推进了的话后续原发包会跳号，接收端把跳号当丢包，一次重传引发一片重传。

## M4.2 · FEC

三个决定，理由见 [NOTES D24](NOTES.md)：

**① FEC 包用独立的编号空间。** 不占 `seq`。
理由是 `AssemblerStats::packetsLost()` 算的是「seq 跨度 − 组包器实收」，
而 `FrameAssembler::offer` 会在计数之前拒掉非 DATA 包 ——
**FEC 包每占一个 seq，丢包率就永久虚高 1/K**。测量工具自己会在最需要它的时候失准。

**② 按帧切组**，组内 K 个包异或出 1 个冗余包。

**③ 冗余包自描述**：头里带组内包数、这是第几组、以及 `payload_len_xor`。
XOR 只给字节不给长度，长度也必须异或进去（RFC 5109 的做法）。

### 实测过销是 30.8%，不是理论的 25%

K=4 的理论开销是 1/4。实测 `fec_bytes / encoded_bytes = 0.308`。

差的那 5.8 个百分点来自 **FEC 载荷取组内最长分片的长度** ——
一组里只要有一个满载分片，冗余包就得跟着满载。**报告里用实测值。**

## M4.3 · 自适应抖动缓冲

### 为什么不选峰值衰减

```cpp
target = max(d_本帧, target_上一帧 * 0.99);   // 被否掉的方案
```

不是因为复杂，是因为 **0.99 没有出处**。它的实际含义是「水位每 69 帧减半」，
而 69 帧是多少秒取决于帧率 —— **改一个 `--fps`，时间常数就跟着变，而代码里看不出这件事**。
滑动窗口的长度至少是「秒」。

### 一个恒等式，和它为什么最后没用上

从窗口里减一个常数再取分位数，等于直接取分位数。所以**无限速**时：

```
playAt = ts + p5(offset) + [p95(offset) − p5(offset)] = ts + p95(offset)
```

时钟基准整个消掉了 —— 顺带把 M2 留下的「`minOffset` 只减不增」和「时钟频差」两笔账
一起还了（窗口一滑，被钉低的样本自己就过期了）。

但选了**非对称跟随**（上调立刻、下调限速）之后这个化简就不成立了，必须把两半分开：

```
floor  = p5(窗口)          ← 时钟差，瞬时跟，绝不限速
target = p95(窗口) − floor ← 纯抖动，限速跟这个
```

**限速绝不能套在 `floor` 上**：它装的是两端时钟差，对端一重启就整体平移，
限成 10ms/s 的话一次 300ms 的跳变要 30 秒才对回来，期间每帧的 `playAt` 都是错的。

### 基准取 p5 而不是 min

`timestampMs` 和 `seq` 一样，32 位里每个取值都合法，49.7 天回绕一次。
一次回绕就能把 `min` 拉低 2^32 毫秒，于是 `playAt` 落在 49 天前，
每帧一到手就过期，**水位静默变成 0**。取 p5 要 5% 的样本一起坏才动得了。

### 上调有多快，是分位数和窗口决定的，不是限速

```
上调响应时间 ≈ (100 − 分位数)% × 窗口长度 = 5% × 10s = 500ms
```

p95 在 300 个样本里是第 15 大，攒够 15 个新样本就能把它整个换掉。
**想让上调更快只能缩窗口，而缩窗口直接减样本量** —— 两者对冲，没有两头都要的设法。

## M4.4 · PLI

两个触发源，都由**接收端**发起：

- **B**：队列 A 满 → `dropUntilKeyFrame()` → 画面已经冻结，主动要一个 IDR 把冻结时间从「半个 GOP」缩短
- **D**：NACK 在关键帧分片上放弃 → 那一帧拼不齐，后面依赖它的帧全会花

被否掉的 **C**（解码器报错时触发）理由是**收益和 B/D 重叠**，不是「跨线程贵」——
实现上只是一个 atomic 标志，代价是最多一个收包循环的延迟。

### 限流是必须的，而失效的表现不是崩溃

IDR 约 25~30 个分片。10% 丢包下一个 IDR 整帧到达的概率只有 `0.9^30 ≈ 4%`：

```
PLI → IDR → 96% 概率又丢 → PLI → …
```

**限流失效的表现是码率翻几倍而画面没有变好**，只看丢帧数完全看不出来 ——
所以 `pliSent` 和 `pliSuppressed` 必须分开计。只有一个数的话，
「只发了 2 个 PLI」分不清是只触发了 2 次，还是触发 200 次被挡掉 198 次。

## 实测

七组实验、89 格、每格 3 个种子、每次 1000 帧（33 秒 @30fps）。
命令与口径见 [`scripts/m45_bench.sh`](../scripts/m45_bench.sh)，
八轮实验里踩的坑见 [测试记录](测试记录.md)。

> **每个表都标了它是在哪个 build 上测的。** 消融表和 PLI 表是 M4.6 修复之前测的，
> 那次修复动了抖动缓冲而没动传输层，所以恢复量那几列不受影响、`rendered` 那列受影响。
>
> **原始数据在 [`docs/bench/`](bench/)** —— 但只有第三、四、五节那几张表的存了下来。
> 消融表和丢包扫描的源数据被误删了（见那里的说明），数字可信但不可追溯。

### 一、每一层各值多少（10% 丢包，M4.6 之前）

| 配置 | 渲染 /1000 | 真丢包率 | NACK 救回 | FEC 救回 | FEC 没救回 |
|---|---|---|---|---|---|
| 全关 | **47**（最低 **0**） | 10.51% | 0 | 0 | 0 |
| 只 FEC | 590 | 2.61% | 0 | 558 | 85 |
| 只 NACK | 998 | 0.02% | 817 | 0 | 0 |
| FEC + NACK | 995 | **0** | **261** | 558 | 85 |

**有一处独立的交叉验证**：「只 FEC」剩下 **261** 个包没救回来，
而「FEC+NACK」里 NACK 恰好救回 **261** 个。两个数出自不同的计数器，对得上说明口径没错。

**「全关」那格三个种子里有两个一帧都没渲染出来。**
IDR 约 25~30 个分片，`0.9^30 ≈ 4%` —— 起播门等不到一个完整的关键帧就一直关着。
不是画质下降，是**根本起不来**。

FEC 单独能救回约 68% 的丢包；NACK 在**零 RTT** 的回环上能救回 99.8%。
后面这个数字的水分见第四节。

### 二、丢包率扫描（全开，M4.6 之后）

| 丢包 | 渲染 /1000 | 水位 | p95 延迟 |
|---|---|---|---|
| 1% | 1000 | 34ms | 46ms |
| 3% | 991 | 34ms | 46ms |
| 5% | 987 | 34ms | 47ms |
| 10% | 999 | 36ms | 68ms |
| 20% | 989 | 59ms | 78ms |
| 30% | 988 | 67ms | 79ms |

**这条曲线不单调**，3% / 5% 反而比 10% 差。原因见第五节。

### 三、自适应水位 vs 固定水位（`tc netem`，M4.6 + p25 之后）

八格全部渲染 1000 帧，一帧不丢。每格三个种子分别列出：

| 链路抖动 | 固定 p50 | **自适应 p50** | 固定 p95 | 自适应 p95 |
|---|---|---|---|---|
| 无 | 53/53/53 | **8/8/8** | 53/53/53 | 46/46/45 |
| 10±5ms | 60/59/60 | **19/19/19** | 61/59/60 | 57/57/56 |
| 20±10ms | 67/66/68 | **34/34/34** | 67/71/71 | 64/64/64 |
| 30±15ms | 72/77/77 | **49/49/48** | 73/82/82 | 71/78/76 |

- **p50：省 25~45ms，种子间散布 ≤ 1ms。** 信号远大于噪声。
- **p95：省 3~7ms，而单格内种子间散布最大到 9ms**（`30±15` 的固定水位是 73/82/82）。
  **信号小于噪声 —— p95 上测不出差异。**

> 结论只能写成：**自适应把中位延迟砍到六分之一至一半，而尾延迟与固定水位没有可测的差异。**
>
> 中间有一版报告写过「30±15 时自适应的 p95 反超 1ms」并当成发现 ——
> 那 1ms 是噪声。**只看均值不看散布，就会把噪声读成结论。**

### 四、缓冲同时是个方差抑制器

| | p95 − p50 |
|---|---|
| 固定 50ms | 0~4ms |
| 自适应 5~15ms | 26~38ms |

水位大时每帧都要等，交付节奏被拉齐；水位小时帧一到期就放，节奏跟着到达抖动走
（差值恰好接近一个帧周期 33ms）。

**自适应买的是中位延迟，卖的是尾延迟的稳定性。**

### 五、分片本身就吃掉了大部分链路抖动

30±15ms 的链路上自适应水位只收敛到 **13~15ms** —— 远小于链路抖动。
不是估计器瞎了：**一帧要等它最慢的那一片**。8 个分片取最大值，分布窄得多：

```
p95 − p5 = 30 × (0.95^(1/8) − 0.05^(1/8)) ≈ 9.2ms
```

实测水位 13~15ms（多出来的是编码耗时的方差）。同一个量级。

**这解释了为什么自适应的优势不随链路抖动增长** —— 分片替它挡掉了大半。
详见 [NOTES D26](NOTES.md)。

## 三条被自己的实验推翻的设计假设

### ① 「RTT 超过 17ms 之后 NACK 会失效，FEC 接管」—— 错

设计时算的是：抖动 50ms − 检测延迟 33ms（一个帧周期）= 17ms 留给 RTT。

实测（`tc netem`，10% 丢包）：

| RTT | NACK 请求 | **NACK 救回** |
|---|---|---|
| 10ms | 217 | 262 |
| 30ms | 242 | 261 |
| 50ms | 439 | **264** |

**RTT 50ms 时 NACK 照样救回 264 个包，一个没少。** 请求数翻倍是重发，恢复量没掉。

真实机制比原预测更准确：

> **NACK 一直在工作。救回来的包是被 jitter buffer 当成迟到帧扔掉了。**

失效的不是重传，是下游把重传的成果丢了 —— 而那是下面这条。

### ② 「水位跟着 offset 的分位数走」—— 少问了一句：哪些帧有资格贡献 offset

`JitterBuffer::push()` 原本的顺序是：

```
1. extendFrameId
2. 起播门
3. framesTooLate 检查    ← 迟到的帧在这里被丢掉
4. 查重
5. computePlayAt         ← 估计器的样本在这里才取
```

**一帧迟到就在第 3 步被扔了，永远不会成为第 5 步的样本。**
于是估计器只看得到准时到达的帧 —— 那些按定义就是快的 —— p95 偏小、水位收窄、
更多帧迟到、采样更加只剩快的。**正反馈，而且是幸存者偏差长在控制器自己的输入上。**

系统因此**双稳**。RTT 50ms、10% 丢包下，三个种子：

| | 修复前 | 修复后 |
|---|---|---|
| 渲染 /1000 | 632 / 623 / 980 | **998 / 997 / 998** |
| jitter 丢帧 | 150 / 131 / 6 | 0.3 |
| 水位 | 10 / 10 / 87 | 86 |

同样的配置、同样的链路，结果差 1.6 倍 —— 全看早期样本有没有恰好把水位顶上去。

修法是把取样挪到两个 `return` 之前，并加一个哨兵计数器
`framesSampledButDropped`：它为 0 而 `framesTooLate` 不为 0，就说明取样点又跑回去了。

### ③ 「取中位数，乱序歪不了帧周期」—— 在乱序是少数时才成立

水位的**下限**由重传预算给出：`max(minDelayMs, 帧周期 + RTT)`。
帧周期由相邻 `timestampMs` 的差值量出来（RTT 则由 NACK 发出到重传回来实测）。

但②的修复让**每一帧**都进估计器，包括那些靠重传补齐、因而乱序到达的。
10% 丢包下一帧 8 个分片，`1 − 0.9^8 = 57%` 的帧要等重传 —— **乱序成了多数**，
中位数被向上污染：

| RTT | 帧周期实测 | 真值 |
|---|---|---|
| 10ms | 33.7 | 33 |
| 30ms | 33.7 | 33 |
| 50ms | **55.7** | 33 |

于是下限被抬高 23ms，每帧白付 23ms 延迟。

改成 **p25** 之后（乱序只会把相邻时间戳的差值**放大**，真值在分布低端）：
三档全部量成 33.0，下限 108.7 → 84.0，p95 162.7 → 134.7。

> **改一处会改变另一处的输入分布。** 帧周期估计器的输入本来是「按序到达的时间戳流」，
> 取样点前移把它变成了「大量乱序的流」，而估计器的假设没跟着变。

代价也记下来：下限收窄 24ms 之后每 1000 帧多丢约 5 帧。
**省 28ms 延迟换多丢 5 帧，是交换不是白捡。**

## 三件没兑现的

### 一、低丢包下的单帧丢失没治好

1% / 3% / 5% 三格在加下限前后**逐帧相同**（991.3 → 991.3，987.0 → 987.0）。

回环 RTT 只有 1ms，`floor = 33 + 1 = 34ms` —— **恰好等于一次典型重传，零余量**。
而被丢的那一帧，是需要**第二次**请求才回来的。

加宽到覆盖第二轮就是 `2 × (帧周期 + RTT)`，RTT 50ms 下是 170ms ——
**为每 300 帧里的 1 帧让所有帧多等 85ms，这笔账算不过来**（[NOTES D25](NOTES.md)）。

而那一帧贵在参考链：`gop=30` 时丢 1 帧会让约 **13** 帧解不出来
（实测 5% 丢包：组好 1000 帧、jitter 只丢 1 帧、解码器只吐 987）。
这个「约半个 GOP」的倍数在 gop=10 和 gop=30 两档吻合，gop=60 那档只发生过 1 次丢帧事件，
**样本量为 1，所以这条还不算测出来。**

### 二、PLI 端到端几乎没被触发

八轮实验里 `pli_sent` 只在 RTT 50ms 的两轮里各响过 **1 次**。
其余全部为 0，`nack_gaveup` 也基本为 0。

原因是**两个触发源都对不上实际观察到的故障**：

- B 要**队列 A 满**，而实测下游一直很闲；
- D 要 **NACK 在关键帧分片上放弃**，而 NACK 没放弃 —— 它成功了，只是回来晚了。

**缺的那个触发源是「帧被 jitter buffer 判为过期」** —— 那才是这个故障的现场。
记成 M4 留给 M5 的账。

### 三、丢包率的那个 X 还不能写进 README

回环 RTT ≈ 0 时重传有 4 次机会，30% 丢包下残留只有 `0.3^4 = 0.81%`。
所以「30% 丢包仍渲染 98.8%」量的是**「重传免费时能有多好」**，不是「弱网下能有多好」。

`tc netem` 那几组只跑了 10% 丢包 × RTT，**没有跑「高丢包 × 高 RTT」的组合** ——
而那才是真正的弱网。补上它才能给这个 X 定价。

```bash
./scripts/netem_check.sh          # 20 秒：这台机器能不能给回环 UDP 加延迟
./scripts/m45_bench.sh            # 全量 89 格，约 55 分钟
./scripts/m45_bench.sh g1 g3      # 也可以只跑指定的组
```

输出在 `bench/<时间戳>/`：`runs.csv`（每次运行一行）、`summary.csv`（按格聚合）、
`meta.txt`（commit / 内核 / 参数）、`logs/`（两端完整日志）。

**三条读数纪律**（违反了整张表就是废的）：

1. **丢包只认 `lost_exact + nack_pending`，不认 `lost`。**
   后者是「seq 跨度 − 组包器实收」，FEC 包占 seq 空间却被组包器拒收，每 K 个包永久多算 1 个；
   而流结束时最后几个缺口卡在 `pending` 里，只看 `lost_exact` 会漏报。
2. **FEC 带宽只能从发送端读。** 接收端注入的丢包不改变发送端发了多少。
3. **每格至少 3 个种子。** 注入器是纯哈希，同种子必然同结果 —— 这**不等于**
   「确定性所以不用重复」，一个种子只是一次抽样。

## 已知限制

**跨机器测不了延迟。** `steady_clock` 跨机器不可比，而端到端延迟就是 `nowMs − captureMs`。
跨机器只有丢包率、恢复率、带宽是可比的。**要延迟就必须单机**，
所以 `tc netem` 不是「退而求其次」，是唯一路径。

**WSL2 的 mirrored 网络模式下，netem 要挂在 `loopback0` 而不是 `lo`。**
挂在 `lo` 上时 `ping` 会变慢而进程间的 UDP 不会 —— ICMP 和 UDP 走的不是同一条路。
`netem_check.sh` 会自己探测并报告。

**p25 依赖「正常相邻对超过 25%」**，而这个占比随丢包率和 RTT 一起下降。
失效信号是 `frame_int` 明显大于 `1000/fps`。真跌破 25% 就得换掉这个代理 ——
检测延迟本来就该直接量（缺口出现 → NACK 发出），帧周期只是它一个会漏的替身。

**消融表和 PLI 表是 M4.6 修复之前测的**，`rendered` 那一列需要在最终 build 上重跑。
恢复量那几列是传输层的量，不受影响。

**RTT 50ms 时 `rtt10` 那一格的 p95 有一次 83 → 54 的跳变没查清**。
已排除机器状态（同位置不同代码给出不同结果，不同位置相同代码给出相同结果），
嫌疑在 p25，但能定论的日志被误删了。见 [测试记录](测试记录.md)。
