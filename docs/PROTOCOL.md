# 自研传输协议设计

> 跑在 UDP 之上的应用层协议。设计目标：**分片可组包、丢包可检测、可重传、可纠错、可请求关键帧**。
> 参考 RTP 的思想但简化自研（RTP 是同一问题的标准答案，见 [[RTP 说明]]）。

## 设计要点

- **`seq`（每发一个**该类型**的包 +1）** 用于**丢包/乱序检测**；
- **`frame_id` + `frag_index/frag_count`** 用于**组包还原**；
- 二者分离是关键：seq 管"网络层面丢没丢"，frame/frag 管"业务层面拼不拼得起来"。
  （旧 demo 只用 `nalu_index`+`frag_index`，检丢包不方便——这是本次改进点。）

> **`seq` 是「每种类型各数各的」，不是全局一个计数器。** M2 时只有 DATA 一种包，
> 所以写成了"每发一个 UDP 包 +1"；M4 加了 FEC 和 NACK 之后这条必须说清楚：
>
> | 类型 | 谁在数 |
> |---|---|
> | DATA | 发送端的 `Packetizer::nextSeq_` |
> | FEC | 发送端的 `FecEncoder` 自己的计数器 |
> | NACK / PLI | 接收端自己的计数器（反向通道，和发送方向无关） |
>
> **为什么 FEC 不能共用 DATA 的 seq**：接收端的丢包率算的是
> `packetsLost() = seq 跨度 − 组包器实收`，而组包器**只收 DATA 包**。
> FEC 一旦占号，跨度算进它、实收算不进它，丢包率被**永久虚高 1/K**
> （K=8 就是凭空多 12.5%）——而"X% 丢包下不花屏"里那个 X 正是它。

## 通用包头（所有包共有，12 字节，网络字节序）

```cpp
#pragma pack(push, 1)
struct PacketHeader {
    uint8_t  version;    // 协议版本，当前 1
    uint8_t  type;       // 包类型，见下
    uint16_t stream_id;  // 流标识（房间内第几路）
    uint32_t seq;        // 全局包序号，每发一包 +1（丢包/乱序检测）
    uint32_t timestamp;  // 采集时刻（毫秒，用于端到端延迟测量）
};
#pragma pack(pop)
```

线上布局（网络字节序）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | `version` |
| 1 | 1 | `type` |
| 2 | 2 | `stream_id` |
| 4 | 4 | `seq` |
| 8 | 4 | `timestamp` |

> `#pragma pack` 只是让结构体**看起来**是 12 字节，**不代表可以 `memcpy` 上网**：
> 本机字节序不一定是网络序。序列化必须逐字段按上表偏移读写，这也是编解码函数
> 存在的理由。

### 包类型

| type | 名称 | 方向 | 用途 |
|---|---|---|---|
| 1 | `DATA` | 发→收 | 媒体分片 |
| 2 | `FEC` | 发→收 | 冗余校验包 |
| 3 | `NACK` | 收→发 | 请求重传 |
| 4 | `PLI` | 收→发 | 请求关键帧 |
| 5 | `SIGNAL` | 双向 | 信令（加入房间/开始/停止/心跳） |
| 6 | `STATS` | 收→发/服务端 | 上报指标 |

### seq 的比较必须处理回绕

`seq` 是 32 位、每包 +1，**一定会回绕**。判断先后一律用有符号差值：

```cpp
bool seqNewerThan(uint32_t a, uint32_t b) { return int32_t(a - b) > 0; }
```

无符号相减本身就是模 2^32 运算，回绕后差值仍然正确，转成有符号即得到带方向的距离。
直接写 `a > b`，在 `0xFFFFFFFF → 0` 的那一刻会把最新的包判成最老的包 ——
表现为"跑了几十分钟后突然全是乱序"，且只在长时间运行时复现，极难查。

前提是两个 seq 相距不超过 2^31（约 21 亿包）。所有滑动窗口协议都有这个前提，
`jitter buffer` 和重传窗口的大小远小于它，不构成实际限制。

## DATA 包

```cpp
struct DataHeader {          // 紧跟 PacketHeader，线上 9 字节
    uint32_t frame_id;       // 第几帧（组包用）
    uint16_t frag_index;     // 该帧第几片，从 0 开始
    uint16_t frag_count;     // 该帧共几片，恒 ≥ 1
    uint8_t  flags;          // bit0: 关键帧(IDR)  bit1: 重传包(M4)  bit2-7: 保留，必须为 0
};
// 之后是载荷（≤ MAX_PAYLOAD）
```

线上布局（偏移相对 DataHeader 起点，均为网络字节序）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | `frame_id` |
| 4 | 2 | `frag_index` |
| 6 | 2 | `frag_count` |
| 8 | 1 | `flags` |

- `MAX_PAYLOAD = 1200`（保守值，留足 IP/UDP + 自定义头空间，避免 IP 分片）
- 整包上限 `12 + 9 + 1200 = 1221` 字节，安全落在以太网 MTU 之下
  （1500 − 40 IPv6 − 8 UDP = 1452，余量用于容忍隧道/VPN 的额外封装）
- **宁可小也不要触发 IP 分片**：IP 分片后任意一片丢失，整个 IP 包都废掉，
  等于把丢包率放大数倍，而且这一层的丢失我们自己的 FEC/NACK 完全看不见
- 载荷**包含起始码**，接收端还原出的即为合法 Annex B（可直接喂解码器/ffplay 验证）

### `flags` 位定义

| bit | 名称 | 谁置位 | 干什么用 |
|---|---|---|---|
| 0 | `FLAG_KEYFRAME` | 发送端打包时 | 该分片属于 IDR 帧。**打在每一片上**，单片就能判断值不值得保，供发送侧背压按包丢 |
| 1 | `FLAG_RETRANSMIT` | 发送端响应 NACK 时 | 这一片是重传的，不是原发的 |
| 2–7 | 保留 | — | 必须为 0 |

`FLAG_RETRANSMIT` 存在的理由有两条，都不是"顺便记一下"：

1. **丢包注入器只丢原发包。** 注入器把"丢不丢"实现成 `hash(seed, seq)` 的纯函数
   （这样丢包序列与到达顺序、与是否有重传都无关，换个种子才变），
   但同一个 `seq` 因此永远得到同一个答案 —— 重传包会被反复丢掉，
   **NACK 的恢复路径永远跑不出成功的一次**。接收端自己看不出这是第几次传输，
   所以必须由发送端在包里说。
2. **"重传救回来几个"要单独统计**，不能混进 `packetsReceived` 的口径 ——
   `packetsLost()` 算的是 `seq 跨度 − 实收`，重传包一进"实收"就会把丢包率压低
   （见 `docs/M2_传输.md` 的「留给 M4 的账」第 ① 条）。

> 接收端**不能**因为 bit2–7 非 0 就丢包 —— 那是给以后的版本留的扩展位，
> 老接收端遇到新发送端时应当忽略不认识的位，而不是把整个包判成畸形。

## FEC 包（XOR 方案）

**分组：按帧切，每组固定 `K` 个 DATA 包**，一帧内的最后一组可能不足 K。
每组生成 1 个 FEC 包 = 组内各分片**载荷**（不含包头）按字节异或，短的补零。

```cpp
struct FecHeader {              // 紧跟 PacketHeader，线上 12 字节
    uint32_t group_base_seq;    // 覆盖 [base, base + group_size)
    uint16_t group_size;        // 组内 DATA 包数，恒 ≥ 2
    uint16_t payload_len_xor;   // 组内各分片载荷长度的异或
    uint8_t  group_index;       // 本帧第几组 —— 仅供诊断
    uint8_t  group_count;       // 本帧共几组 —— 仅供诊断
    uint16_t reserved;          // 必须为 0；接收端忽略而不是判成畸形
};
// 之后是异或载荷，长度 = 组内最长的那片
```

线上布局（偏移相对 `FecHeader` 起点）：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | `group_base_seq` |
| 4 | 2 | `group_size` |
| 6 | 2 | `payload_len_xor` |
| 8 | 1 | `group_index` |
| 9 | 1 | `group_count` |
| 10 | 2 | `reserved` |

- **恢复条件**：组内**恰好丢 1 个** DATA 包 → 用其余包 + FEC 包异或还原。
- 丢 ≥2 个 → FEC 无能为力，退回 NACK 或 PLI。
- 整包上限 `12 + 12 + 1200 = 1224` 字节，**比 DATA 包大 3 字节**——
  所有收包缓冲一律按 `MAX_PACKET_SIZE` 开，按 `MAX_DATA_PACKET_SIZE` 开的话
  满载的 FEC 包会被 `MSG_TRUNC` 判成"数据报大于缓冲区"，现象是
  "FEC 全部收不到而 DATA 一切正常"。

### 恢复只认 `group_base_seq` + `group_size`

`group_index` / `group_count` 只回答"这帧的 FEC 收全了吗"，**不参与恢复**。

> **XOR 恢复没有任何校验。** 异或错了一组包，出来的是一串看着完全合法的字节，
> 长度也对，组包器会把它当真分片收下喂给解码器——**没有报错，只有偶发花屏**。

DATA 包有 `frag_index`/`frag_count` 可以验证拼得对不对，XOR 没有对应的东西。
所以头里必须**直接写明覆盖哪些 seq**，而不是让接收端按切分规则推算第 j 组是哪几片——
两端的规则一旦有一点不一致（改了策略、版本不同），不会报错，只会静默异或错组。

`payload_len_xor` 同理是必须的：**XOR 出来的是字节，不是长度**。一帧的最后一片是短的，
恢复时长度猜错就是静默损坏。RFC 5109 同款做法。

### 为什么按帧切组，而不是固定 K 跨帧

**FEC 包必须等组满才发得出去。** 组跨帧的话，第 1 帧最后几个包所在的组要等第 2 帧的包
补满——FEC 包比它保护的数据**晚一整帧**。而 FEC 相对 NACK 的全部优势就是"不用等一个
往返"，晚一帧等于把这个优势还回去了。

按帧切组还白送一条好处：接收端的 NACK 触发阈值是"一帧的包数"，而 FEC 包在**本帧之内**
就到了，**FEC 天然抢在 NACK 前面**——不需要额外协调，也不会出现"FEC 救回来了但 NACK
还是白发了一遍"。

### `K` 的取舍（可以算，不用猜）

一个 DATA 包丢了能被救回来的条件是**组内其它 K 个包一个都没丢**，即 `(1-p)^K`；
带宽开销 `1/K`：

| K | 冗余带宽 | p=5% | p=10% | p=30% |
|---|---|---|---|---|
| 4 | 25% | 81% | 66% | 24% |
| 8 | 12.5% | 66% | 43% | 5.7% |
| 16 | 6.25% | 44% | 18.5% | 0.3% |

**XOR FEC 在高丢包率下基本没用**——p=30%、K=8 时花 12.5% 带宽换回 5.7%。
这是"只能纠 1 个"的天花板，不是实现问题；要纠多个得上 Reed-Solomon（见「待定 / 可演进」）。

`group_size < 2` 的组**不发 FEC**：1 个包的"FEC"就是原包的完整副本，那不叫纠错叫重复发送。

## NACK 包（重传请求）

载荷是若干条**位图条目**，形状取自 RFC 4585 的 Generic NACK（只把 PID 从 16 位改成
32 位，因为本协议的 `seq` 是 32 位）：

```cpp
struct NackHeader {          // 紧跟 PacketHeader，线上 2 字节
    uint16_t entry_count;    // 位图条目数，≥ 1
};
// 之后是 entry_count 条，每条 6 字节：
struct NackEntry {
    uint32_t pid;            // 基准 seq，它本身一定是缺的
    uint16_t blp;            // bitmask of following lost packets
                             // bit i (0..15) 置 1 表示 pid + 1 + i 也缺
};
```

线上布局：

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 2 | `entry_count` |
| 2 + 6k | 4 | 第 k 条的 `pid` |
| 6 + 6k | 2 | 第 k 条的 `blp` |

### 容量：一个包永远装得下整个窗口

```text
一条 6 字节，覆盖 17 个连续 seq 位
一包能装  (1221 − 12 包头 − 2 entry_count) / 6 = 201 条  →  最多 3417 个 seq

而缺口数被接收端的跟踪窗口卡死（NackTrackerConfig::windowPackets，默认 1024）：
1024 个 seq 位最多需要 ceil(1024 / 17) = 61 条 = 366 字节 —— 不管缺口怎么分布
```

所以默认配置下**截断路径走不到**。编码函数仍然要在装不下时报错，但那是
`Internal` 级别的错误（缓冲区是本端按线上长度算好的，装不下只可能是自己算错了），
不是正常路径。调用方超了就截断，剩下的留到下一轮 —— `collectNackTargets` 本身有限流，
下一轮很快。

### 为什么用位图而不是 seq 列表

真实网络的丢包是**扎堆**的（同一次拥塞、同一次链路抖动），位图对连续缺口是
6 字节管 17 个，列表是 4 字节管 1 个。

> **但要说清楚边界**：丢包**均匀分散**时位图反而更费（每个孤立缺口都要一条 6 字节，
> 而列表只要 4 字节）。M4 的丢包注入器是均匀随机的，实测连续段分布
> `1x16060 2x1675 3x161`，基本不扎堆 —— 也就是说**在当前能测到的场景里，
> 位图比列表费 50%**。选它是因为真实网络的丢包形态，不是因为当前测得出来的数据。
> 验收报告里别把"省空间"写成已验证的结论。

### 其余规则

- 接收端发现 `seq` 缺口且**超过等待窗口仍未到**（排除乱序）→ 发 NACK。
  等待窗口取「一帧的包数」，由每个包自带的 `frag_count` 自适应（详见
  `modules/transport/NackTracker.h`）。
- 发送端维护**重传缓存**（最近 N 个包，环形缓冲），收到 NACK 后重发，
  重发的包必须置 `DataHeader.flags` 的 `bit1`（`FLAG_RETRANSMIT`）。
- **限流**：同一 seq 最多重传 M 次；超过重传窗口的请求直接忽略（太老的包重传没意义 ——
  帧早过了 `playAt`，接收端会以 `framesTooLate` 计数然后扔掉）。
- NACK 包**不参与 DATA 的 seq 空间**：它走的是反向通道，`PacketHeader.seq` 由发送方
  （即接收端）自己的计数器给，两个方向各数各的。

## PLI 包（关键帧请求）

无负载，仅靠 `PacketHeader.type=PLI`。

- 触发：关键帧分片无法恢复 / 缺口过大 / 新观众加入需要立即起画。
- 发送端收到后：**立即编码一个 IDR**（呼应"花屏撑到下一个 IDR"，主动缩短这个等待）。

## SIGNAL 包（信令）

用简单文本（JSON）承载，便于调试：

```json
{"cmd":"join","room":"1001","role":"publisher|player"}
{"cmd":"leave","room":"1001"}
{"cmd":"heartbeat","room":"1001"}
{"cmd":"ack","result":"ok","stream_id":1}
```

## 字节序

**所有多字节字段一律 `htonl/htons` 转网络字节序**（不图省事，跨机器必须）。

## 畸形包的处理

UDP 上收到的每一个字节都是**不可信输入**：可能被网络损坏、可能来自旧版本的对端、
也可能是别人往这个端口上乱发的。解析层必须在入口挡住，不能让下游拿着垃圾字段去索引数组。

一律**丢弃该包并计数**，不中断接收循环：

| 情况 | 判据 | 为什么不能放过 |
|---|---|---|
| 版本号不认识 | `version != 1` | 字段一旦挪位，硬解出来的是随机数，表现为莫名其妙的巨大 seq 和永远组不起来的帧 |
| 包类型未定义 | `type` 不在 1–6 | 会被分派到错误的处理分支 |
| 长度不足 | 不够一个包头 | 越界读 |
| 分片字段自相矛盾 | `frag_count == 0` 或 `frag_index >= frag_count` | 组包器直接拿它索引数组，**越界写** |

实现上用**错误码区分两类失败**，因为调用方的反应完全不同：

- **畸形包 → `NetError`**：对端或网络的问题，反应是"丢包 + 计数"，继续收下一个；
- **缓冲区太短、参数非法 → `InvalidArg`**：本端调用错误，反应是"改代码"。

混成一个错误码，接收循环就分不清"该丢包继续"还是"该报警退出"。

丢弃计数要单独统计（不要混进丢包率），M6 的指标里它是一条独立曲线：
**丢包**说明网络差，**畸形包**说明有人在乱发或版本不匹配，两者的处置方式不同。

## 交互时序（简化）

```text
推流端                     服务端                    接收端
  │──SIGNAL(join,publisher)─▶│                          │
  │                          │◀─SIGNAL(join,player)─────│
  │──DATA(seq,frame,frag)───▶│──转发 DATA──────────────▶│
  │──FEC───────────────────▶│──转发 FEC───────────────▶│
  │◀─────NACK(seq列表)───────│◀──NACK（缺口）────────────│
  │──重传 DATA──────────────▶│─────────────────────────▶│
  │◀─────PLI─────────────────│◀──PLI（无法恢复）─────────│
  │──立即 IDR───────────────▶│─────────────────────────▶│
```

## 待定 / 可演进

- 拥塞控制：接收端定期上报丢包率/RTT，发送端据此调码率（M7）
- 升级到标准 RTP + FU-A（M7 可选）
- FEC 从 XOR 升级到 Reed-Solomon（可纠多个丢包）
