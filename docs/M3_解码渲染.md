# M3 · 接收端解码渲染 —— 详细拆解

> 目标：**第一次看到实时画面**。M2 把码流原样送到了对端并落盘，M3 要让它变成窗口里动起来的图像，
> 并且给出**端到端延迟的数字**——这是整个项目立意的第一次兑现。
> 原则：**先能出画面，再谈延迟好看**。中间每一步都要能单独看到结果。

## M3 完成后你会有什么

- `modules/decode/`：`Decoder`（libavcodec 封装，低延迟解码参数）
- `modules/render/`：`IRenderer` 抽象 + `SdlRenderer`（真窗口）+ `NullRenderer`（只计数，供 CI）
- `modules/transport/JitterBuffer`：按 `frameId` 排序、按时间放行、从关键帧起播
- `common/Metrics.h`：`LatencyRecorder`，退出时给出 p50/p95/p99
- 接收端从**单线程**变成**三线程管线**：收包 →`BoundedQueue`→ 解码 →`BoundedQueue`→ 渲染
- `./lowlat_receiver` 跑起来是一个**能看到 NullSource 帧号在跳**的窗口，终端每秒打印一次当前延迟
- 关窗口、Ctrl-C、发送端先退出——三种收场都能干净退出，不死锁不刷屏

## M3.0 · 环境与依赖（先扫雷）

### 做什么
把 SDL2 装好、确认**这台机器能开出窗口**，并确认解码器可用。

### 执行步骤

```bash
sudo apt install libsdl2-dev
pkg-config --modversion sdl2
ffmpeg -hide_banner -decoders | grep ' h264 '     # 确认软解 h264 在
```

`modules/render/CMakeLists.txt`：

```cmake
find_package(PkgConfig REQUIRED)
pkg_check_modules(SDL2 REQUIRED IMPORTED_TARGET sdl2)
target_link_libraries(llrender PUBLIC llcapture PRIVATE PkgConfig::SDL2)
```

SDL2 走 `PRIVATE`，理由同 `llencode` 对 FFmpeg：`SdlRenderer.h` 里只前向声明
`struct SDL_Window;` 这类指针成员，**不 include `<SDL2/SDL.h>`**。
一旦 include，`SDL.h` 里的 `#define main SDL_main` 会跟着传染到每个使用者，
在 `main.cpp` 里表现为莫名其妙的链接错误——这是 SDL 特有的老坑。

### ⚠️ 先回答这个问题：窗口从哪来

| 环境 | 能否开窗 | 备注 |
|---|---|---|
| WSL2 + WSLg | **能**（已实测：`DISPLAY=:0`、`WAYLAND_DISPLAY=wayland-0`） | 本项目的开发环境走这条 |
| 纯 SSH 无 X11 转发 | 不能 | 只能用 `--render=null` |
| CI / `ctest` | **假设不能** | 所以 `NullRenderer` 不是可选项，是必需品 |

**`ctest` 里绝对不能开窗**：CI 上没有 display，`SDL_Init(SDL_INIT_VIDEO)` 会直接失败，
测试红一片却跟代码没关系。`NullRenderer` 的存在理由和 `NullSource` 一模一样——
让"没有硬件/没有显示器"不成为开发和验证的阻碍。

### 验收标准
- [ ] `pkg-config --modversion sdl2` 有输出，CMake 配置阶段不报错
- [ ] 写个 20 行的最小 SDL 程序，能弹出一个纯色窗口并在 2 秒后自己关掉
      （**先验证环境，再写业务**；否则第一次看不到画面时你分不清是环境还是代码）
- [ ] 明确记录本机的 `SDL_VIDEODRIVER`（wayland / x11），出问题时这是第一个要换的变量

## M3.1 · `JitterBuffer`（先做这个，它不依赖任何库）

### 做什么
`FrameAssembler` 只回答"这一帧齐了没有"，**明确不排序**（见 `FrameAssembler.h` 的职责边界）。
JitterBuffer 补上剩下两件事：**按 `frameId` 排序**、**按时间放行**。

### 为什么必须有它，哪怕本机回环从不乱序
1. H.264 是**帧间预测**的，喂进去的顺序错了，解码器不会报错，只会吐出**看起来像画面的垃圾**——
   这类 bug 没有报错信息，只能靠肉眼，是最难查的一种。
2. 本机回环不乱序，M4 一开丢包注入立刻就乱。等到那时再插一层，改的是三线程之间的接口。
3. **起播必须从关键帧开始**：解码器拿到的第一个包不是 IDR，就会持续吐 `no frame!` / `non-existing PPS`，
   画面要么全绿要么全花，直到下一个 IDR 才恢复。这条策略放在这里，M4 的 PLI 才有地方接。

### 接口设计

```cpp
// modules/transport/JitterBuffer.h
struct JitterBufferConfig {
    /** @brief 目标缓冲水位(毫秒); 0 表示水位为零, **同时也就放弃了乱序容忍** */
    int targetDelayMs = 50;

    /** @brief 软上限: 攒到这么多就把最老的立刻放出去(不丢) */
    size_t maxFrames = 16;

    /** @brief 硬上限: 超过就真丢最老的; 0 表示取 maxFrames * 2 */
    size_t hardLimitFrames = 0;

    /** @brief 第一帧必须是关键帧, 之前收到的一律丢弃 */
    bool startOnKeyFrame = true;
};

struct JitterBufferStats {
    uint64_t framesIn = 0;
    uint64_t framesOut = 0;
    uint64_t framesTooLate = 0;      ///< 比已交付的帧还老, 直接丢
    uint64_t framesDuplicate = 0;    ///< 同一个 frameId 重复到达
    uint64_t framesForcedEarly = 0;  ///< 超软上限被提前放行(**没丢**)
    uint64_t framesDropped = 0;      ///< 超硬上限被真正丢弃
    uint64_t framesBeforeKey = 0;    ///< 起播前丢掉的非关键帧
};

class JitterBuffer {
public:
    explicit JitterBuffer(JitterBufferConfig cfg = {});

    /** @brief 放入一帧组好的帧; 移动进来 */
    void push(AssembledFrame frame, uint64_t nowMs);

    /**
     * @brief 取出一帧到点该播的帧
     * @return true 取到; false 现在没有该播的帧
     */
    bool pop(AssembledFrame& out, uint64_t nowMs);

    /**
     * @brief 距离下一帧该播还有多久(毫秒)
     * @return 没有待播帧时返回 -1
     * @note 收包线程的 poll 超时要拿它来夹一下, 见 M3.5
     */
    int msUntilNextDue(uint64_t nowMs) const;

    const JitterBufferStats& stats() const;
    void reset();
};
```

### 放行时刻怎么算（这是能讲的部分）

**错的做法**：`playAt = 到达时刻 + targetDelayMs`。
这只是给每一帧统一加了个延迟，**抖动一点没被吸收**——早到的帧照样早播，晚到的帧照样晚播。

**对的做法**：在**发送端时间轴**和**本地时间轴**之间维护一个偏移量，所有帧按它排期：

```cpp
const int64_t offset = int64_t(nowMs) - int64_t(frame.timestampMs);  // 本帧观测到的偏移
minOffsetMs_ = std::min(minOffsetMs_, offset);                       // 历史最小 = 走得最快的那一趟
const uint64_t playAtMs = frame.timestampMs + minOffsetMs_ + cfg_.targetDelayMs;
```

这样早到的帧算出来的 `playAt` 更靠后、于是**多等一会儿**，晚到的帧**少等或不等**，
抖动被吸收在缓冲水位里——这才是 "jitter buffer" 这个名字的意思。

取**最小**偏移而不是第一帧的偏移：只锚定第一帧的话，万一它恰好赶上一次慢传输，
整条时间轴就被钉在偏晚的基准上，之后每帧都"已经到期"，水位白设。
最小偏移对应"网络最顺的那一趟"，是这条链路真实下限的估计。

全程走 `int64_t`：跨机器时两台机器 `steady_clock` 的起点毫不相干，`offset` 可能是很大的负数，
用无符号算会直接绕成天文数字。反过来说，**偏移量只参与差值运算，所以跨机器排期照样是对的**，
只是算出来的绝对延迟数字没意义（见 `Clock.h`）。

> **已知缺陷（M3 不修，写进 README 已知限制）**：`minOffset` 只减不增，网络永久变好之后
> 水位不会自动收窄；两端时钟频差也会让映射慢慢漂，跑久了缓冲要么越攒越深（延迟变大）、
> 要么越来越空（卡顿）。正确解法是定期重估 + 自适应水位，那是 M4 的内容。
> M3 先把固定水位做对，**并且明确知道它为什么不够**。
>
> 另外 `timestampMs` 是 32 位毫秒，约 **49.7 天**回绕一次。单次演示和压测都碰不到，
> 但它是个真实的上界，一并记在已知限制里。

### 执行步骤
1. **入口处先把 32 位 `frameId` 扩展成 64 位单调序号**，之后一律拿扩展号排序和比较：

   ```cpp
   const int32_t delta = static_cast<int32_t>(frameId - refFrameId_);
   refExtended_ = uint64_t(int64_t(refExtended_) + delta);
   refFrameId_  = frameId;      // 锚点每帧都跟着走
   ```

   **不能拿 `seqNewerThan` 当 `std::map` 的比较器**：它不是全序（回绕点上 `a<b`、`b<c`
   推不出 `a<c`），而有序容器要求严格弱序，违反了就是未定义行为——表现为偶发的
   元素找不到、迭代顺序错乱。同一个有符号差值技巧只在**入口用一次**，
   这就是 RTP 的 extended sequence number
2. `std::map<uint64_t, Entry>` 按扩展号排序；条目最多十几个，红黑树的常数完全无所谓，
   换来的是"取最小"（就是 `begin()`）和查重都现成
3. 记住 `lastOutExtended_`：**不比它新**的帧到了就丢并计 `framesTooLate`，绝不回头输出——
   解码器收到倒退的帧比收不到更糟。判据是 `<=` 不是 `<`：整帧重传会把已交付的帧原样送回来
4. `startOnKeyFrame`：在收到第一个 `isKey` 的帧之前，所有帧丢弃并计数
5. 容量分两级：
   - 超 `maxFrames`（软）：把最老的一帧 `playAt` 改成 0 —— **立刻放行而不是丢掉**。
     它已经在手里了，丢必然花屏，播早了至少画面是对的
   - 超 `hardLimitFrames`（硬）：真丢最老的。软上限只改"什么时候该放"，**并不减少条目数**，
     消费端彻底卡住时光靠它内存会一直涨。到了这一步那些帧早过了该显示的时刻，
     留着只是给延迟做加法
   - 被丢的帧**不推 `lastOutExtended_`**：那个水位的含义是"已经交付到哪儿"，丢掉的从没交付过

### 验收标准
- [ ] 乱序喂入 `frameId = 3,1,4,2`，输出顺序是 `1,2,3,4`
- [ ] 早到的帧多等、晚到的帧立刻放行（这两条分开测，才能证明吸收的是**抖动**而不是统一加延迟）
- [ ] 第一帧走得慢时，后续更快的一趟能把 `minOffset` 收窄（排期跟着往前挪）
- [ ] 输出 5 之后再喂 4 → 丢弃且 `framesTooLate == 1`，不影响后续的 6；重复喂 5 也算太晚
- [ ] `startOnKeyFrame=true` 时，起播前的非关键帧全被丢弃并计数，关键帧一到正常起播
- [ ] `frameId` 在 `0xFFFFFFFE → 0x00000001` 回绕区间内乱序送入，输出顺序仍正确
- [ ] 超软上限：最老帧被改成立刻到期，`framesForcedEarly` 每超一帧只加一次，**没有**帧被丢
- [ ] 超硬上限：`size()` 有界，`framesDropped` 对得上，且被丢的帧不会把后续帧误判成太晚
- [ ] `msUntilNextDue()`：空缓冲 -1；有帧时随 `nowMs` 递减到 0；过期返回 0 **不返回负数**
- [ ] 计数器总账：`framesOut + tooLate + duplicate + dropped + beforeKey + size() == framesIn`

## M3.2 · `Decoder`（libavcodec 封装）

### 做什么
H.264 Annex B → YUV420P，**低延迟解码参数**。结构和 `Encoder` 对称，看一眼那份就知道该怎么写。

### 接口设计

```cpp
// modules/decode/Decoder.h
struct DecoderConfig {
    /**
     * @brief 解码线程数; 1 表示单线程
     * @note 见下方"低延迟解码"——这个参数不是性能旋钮, 是延迟旋钮。
     */
    int threads = 1;
};

class Decoder {
public:
    Status open(const DecoderConfig& cfg);

    /**
     * @param data 一整帧 Annex B 码流(含起始码)
     * @param captureMs 该帧的采集时刻, 原样透传到输出, **不在这里重新取时间**
     * @param out 出参, 追加解出的帧; 可能 0 个或多个
     */
    Status decode(const uint8_t* data, size_t len, uint64_t captureMs,
                  std::vector<RawFrame>& out);

    Status flush(std::vector<RawFrame>& out);
    void   close();
};
```

**输出复用 `RawFrame`**（`modules/capture/Frame.h`），不另起一个 `DecodedFrame`：
它俩字段完全一样，分成两个类型的唯一后果是渲染器得写两遍、或者中间加一次无谓的转换。
代价是 `lldecode` 要链 `llcapture`，CMake 里看着有点怪——真觉得别扭了，
把 `Frame.h` 挪进 `common/` 是个十分钟的机械改动（它只依赖 `Status.h`），
但**现在不动**，为了改名字去动一堆 include 不值当。

`RawFrame::captureMs` 从 `AssembledFrame::timestampMs` 透传，`frameId` 也一样。
延迟测量全靠这一路透传不断链，谁在中间重新取一次时间，测出来的就是个假数字。

### 低延迟解码（这是能讲的部分，也是最容易被忽略的一条）

```cpp
ctx->thread_count = cfg.threads;          // 1
ctx->thread_type  = FF_THREAD_SLICE;      // 关键: 不要 FF_THREAD_FRAME
ctx->flags       |= AV_CODEC_FLAG_LOW_DELAY;
ctx->flags2      |= AV_CODEC_FLAG2_FAST;
```

**`FF_THREAD_FRAME`（帧级多线程）是低延迟的隐形杀手**：它靠"同时解 N 帧"提高吞吐，
代价是解码器要**先攒够 N 帧才吐第一帧**。默认开着，且 FFmpeg 不会告诉你。
现象是"明明编码端 zerolatency 了，端到端还是稳定多出 3~4 帧的延迟"，
换算到 30fps 就是 100ms 以上——比整条网络链路的延迟还大。
`FF_THREAD_SLICE`（片级）只在一帧内部并行，不引入跨帧排队。

这条和 M1 里编码端关 B 帧是**同一件事的两端**：任何"要等后面的数据才能出结果"的优化，
在实时场景里都是负收益。面试时这两个点连起来讲，比单说 `zerolatency` 有说服力得多。

### 执行步骤
1. RAII 包住 `AVCodecContext` / `AVFrame` / `AVPacket`，与 `Encoder` 保持一致
2. `avcodec_send_packet` / `avcodec_receive_frame`，**循环取到 `EAGAIN`**（同 M1 踩坑 5 的镜像）
3. **`AVPacket` 的数据尾部必须留 `AV_INPUT_BUFFER_PADDING_SIZE`（64）字节的填充**：
   H.264 的比特流读取器会越界预读，不留就是实打实的堆溢出，
   valgrind 下必报、平时可能"看着没事"。用 `av_new_packet()` 分配再 `memcpy` 进去，
   或者自己维护一块尾部多 64 字节且**清零**的缓冲复用
4. `receive_frame` 拿到的 `AVFrame` 是**解码器内部复用的**，下一次调用就失效——
   必须当场按 `linesize` 逐行拷进 `RawFrame`，不能存指针
5. 拷贝时按 `linesize` 逐行（同 M1 踩坑 3，方向相反）：解码器输出的 `linesize[0]` 通常大于 `width`
6. 检查 `ctx->pix_fmt`：本项目的编码端固定产出 `AV_PIX_FMT_YUV420P`，直接拷即可；
   但别假设——不是 420P 时用 `sws_scale` 转一次（`SwsContext` 建一次复用，M1 踩坑 14）。
   这段代码平时不执行，它的价值是让"别人的流"进来时是花屏还是正常有区别
7. **把 FFmpeg 的日志接进自己的 Logger**：`av_log_set_callback()`。
   丢包时解码器会疯狂往 stderr 刷 `error while decoding MB`，
   不接管的话 M4 一开丢包注入，终端就没法看了

### 验收标准
- [ ] 拿 M2 产出的 `recv.h264` 整个喂进去，解出的帧数 == 编码端的帧数
- [ ] 解出的第一帧尺寸与编码配置一致，`data.size() == w*h*3/2`
- [ ] 把解出的 YUV 写盘，`ffplay -f rawvideo` 能播且**帧号肉眼可辨**
      （这一步单独就能看到结果，先做到这里再碰 SDL）
- [ ] 故意从中间截断码流（跳过第一个 IDR）喂进去：日志里是自己的 WARN，不是 stderr 刷屏，且不崩
- [ ] 解 1000 帧无内存增长（RAII 没漏，同 M1.3）
- [ ] `threads=1 + FF_THREAD_SLICE` 与默认配置对比，记录下"送第 1 帧到吐第 1 帧"差几帧
      —— 这个数字直接进 README

## M3.3 · `IRenderer` + `SdlRenderer` + `NullRenderer`

### 做什么
把 YUV420P 显示出来。抽象成接口的**第一**理由是**让整条管线在没有显示器的机器上也能跑完**，
不是"将来可能换个渲染后端"。

---

### 线程模型：渲染循环独占一条线程

SDL 的规则要分成两条，它们的强度**不一样**（`/usr/include/SDL2/SDL_events.h:679,885`）：

| | 头文件原话 | 性质 |
|---|---|---|
| `SDL_Init` / `CreateWindow` / 渲染 / `PollEvent` 在**同一条**线程 | "you **can only** call this function in the thread that initialized the video subsystem" | **硬规则**，所有平台 |
| 那条线程**是主线程** | "for extra safety, you **should consider** ... on the main thread in any case" | **建议**，不是要求 |

"必须主线程"那条之所以存在，是因为 **macOS** —— Cocoa 的 `NSApplication` 事件循环是
操作系统级强制在主线程。Linux/X11、Wayland 上没有这个约束。

**本项目取舍：渲染跑在一条专门的 `std::thread` 上**（M3.5 定，理由见那一节）。
代价是**显式放弃 macOS** —— 记在这里，是一次有记录的取舍，不是忘了考虑。

不管跑在哪条线程，下面这个"一条线程等两个事件源"的问题都一样存在。

```cpp
// 主线程
for (;;) {
    if (renderer->pumpEvents()) { stopRequested = true; }   // 先泵事件
    if (stopRequested.load()) break;

    RawFrame f;
    if (queueB.popFor(f, 5ms)) {          // 帧一到立刻返回, 零额外延迟
        renderer->renderFrame(f);
    }
}
```

难点在于：**主线程只有一个，却要同时等两个互不相干的事件源** ——
队列 B 来的帧（自己进程 `notify` 的）和窗口系统来的事件（socket 上来的）。
堵在 `pop()` 上就没人泵事件，窗口点不掉。

三个方案对账：

| | 帧延迟 | 事件响应 | 空转 | 要加的 API |
|---|---|---|---|---|
| 1. 轮询 `tryPop` + 睡 2ms | +0~2ms | 0~2ms | 500 次/秒 | `tryPop` |
| **2. `popFor(5ms)`** ✅ | **+0** | 0~5ms | 200 次/秒 | `popFor` |
| 3. `SDL_PushEvent` 唤醒 | +0 | +0 | 0 | `tryPop` |

**关键：带超时的等待不增加帧延迟。** `wait_for` 在 `notify_one()` 时立刻返回，
超时是"最多等多久"的上限，不是"必须等多久"的下限。那 5ms 只影响事件响应
（关窗口最多晚 5ms 被处理），人眼无感。

方案 3 看着最优雅，但要多付：自定义事件类型、`SDL_PushEvent` 队列满
（SDL2 上限 65535）返回负数的处理、以及**所有权穿过 `void*`** 的泄漏风险
（`SDL_Event` 是固定大小的 union，装不下一帧，只能塞指针）。

**判据：这多出来的复杂度，换到了什么能被人感知的东西？**
答案是"事件响应快 5ms"和"省 200 次/秒空转"——人和 CPU 都感觉不到。这笔交易亏。
完整推演见 `NOTES.md` **D16**。

### 渲染由谁驱动：队列，不是时钟

**选队列驱动。** 一个很容易掉进去的坑是选时钟驱动（每 33ms 醒一次取最新的画），
理由是"队列驱动两帧之间时间差不固定"——**这个前提是错的**。
`JitterBuffer::pop()` 不是"有货就给"，是按 `playAt` 时刻给：

```text
playAt = ts + minOffset + delay
ts 是采集时刻, 30fps 下每帧相差 33ms; minOffset 和 delay 对每帧都一样
→ playAt 之间也正好相差 33ms
```

**`JitterBuffer` 已经是节拍器了。帧到渲染器手上时，节奏已经是齐的。**

再加一个 33ms 定时器就有了两个时钟：一个跟发送端时间轴走，一个跟本地时钟走。
两台机器晶振有频差（10~100ppm），它们永远不会一致，于是：

| 谁快 | 后果 | 现象 |
|---|---|---|
| 定时器快 | 队列 B 反复取空 | 周期性卡顿 |
| 定时器慢 | 队列 B 持续堆积 | 延迟越滚越大，最后丢帧 |

表现是每隔几十秒画面顿挫一下，而且查网络、查解码都查不到——病根是两个时钟在对抗。

时钟驱动还白送一笔延迟：帧刚取完的下一瞬间来了新帧，也得等一整个周期，
**平均 16.7ms、最坏 33ms**，对一个卖点是低延迟的项目是纯亏。

> **原则：一条流水线上只该有一个节拍器。**
> 这里已经有了（源 → JitterBuffer），渲染器的活是"到了就画"，不是"自己数拍子"。

完整推演见 `NOTES.md` **D15**。

### 接口设计

```cpp
// modules/render/IRenderer.h
struct RendererConfig {
    std::string title  = "lowlat_stream";
    int         width  = 640;    // 只是窗口初始大小, 画面尺寸以每帧自带的为准
    int         height = 480;
    bool        vsync  = false;  // 默认关: 开了平均多 8ms、最坏 16ms
};

struct RendererStats {
    uint64_t framesRendered  = 0;
    uint64_t framesRejected  = 0;   // 不变量没过, 单测应当 EXPECT_EQ(_, 0)
    uint64_t texturesRebuilt = 0;   // 稳态下恒为 1; 持续增长 = 每帧重建纹理
};

class IRenderer {
public:
    virtual ~IRenderer() = default;                    // 必须虚, 否则派生类资源全泄漏
    IRenderer(const IRenderer&) = delete;              // 持有窗口句柄, 拷贝无语义
    IRenderer& operator=(const IRenderer&) = delete;

    virtual Status open(const RendererConfig& cfg)  = 0;
    virtual Status renderFrame(const RawFrame& f)   = 0;
    virtual bool   pumpEvents()                     = 0;
    virtual const RendererStats& stats() const      = 0;
    virtual void   close()                          = 0;

protected:
    IRenderer() = default;
};

std::unique_ptr<IRenderer> createRenderer(const std::string& kind);   // "sdl" | "null"
```

**方法集是怎么定下来的** —— 判据只有一条：

> **拿 `NullRenderer` 去套每一个方法。它实现不了、或者只能写成空函数的，出局。**

按这条筛掉的：

| 想加的 | 为什么出局 |
|---|---|
| `runLoop()` 主循环 | `NullRenderer` 没有窗口没有事件源，只能写成假循环。而且循环体里同时出现队列 B 和 SDL——队列 B 是渲染器**不该知道**的东西（它不关心帧从哪来）。循环归 `main.cpp`，同 `ISource::readFrame()` 不跑循环 |
| 自建消息队列 + 取/加消息 | `SDL_QUIT` 只有 `SDL_PollEvent` 看得见，自建一套之后是**两套并行**的事件机制而不是替换 |
| `validateConfig()` | 校验是 `open()` 自己的第一件事。独立出来调用方就可能忘了调，于是 `open()` 还得再校一遍。**能被忘记的检查等于没有检查** |
| 「已打开」+「未关闭」两个 bool | 同一个状态的两面。两个 bool 有 4 种组合而其中有自相矛盾的，说明它们不独立。`SdlRenderer` 里连一个都不要：`window_ != nullptr` 本身就是答案 |

`pumpEvents()` 反而**留下来了**——`NullRenderer` 恒返回 `false` 不是空实现，
它**真的**没有事件源。而它必须在接口上，是因为「用户点了 ×」这件事只有渲染器一侧看得见，
而让 `main.cpp` 直接调 `SDL_PollEvent` 就得 include `SDL.h`，那个头文件里的
`#define main SDL_main` 会传染给每个使用者。

**三个返回值分别为什么长这样：**

判据是**调用方拿到不同的返回值，能做出不同的动作吗**。能，才值得区分；不能，返回值就是摆设。

| | 里面在干什么 | 失败了调用方能干嘛 | 定 |
|---|---|---|---|
| `open()` | `SDL_Init` / `CreateWindow` / `CreateRenderer` | `InvalidArg`=命令行写错了，报错退出；`IoError`=这台机器没 `DISPLAY`（SSH 上去跑就是这个），可以退回 `NullRenderer` 继续跑。**两种动作不同** | `Status` |
| `renderFrame()` | 建/重建纹理、`UpdateYUVTexture`、`RenderCopy`、`RenderPresent` | `InvalidArg`=这帧坏了但**下一帧可能是好的**，记一笔继续；`Internal`=渲染器自己坏了，继续没意义。**两种动作不同** | `Status` |
| `close()` | `SDL_DestroyTexture/Renderer/Window`、`SDL_Quit` | **这四个 SDL 函数全都返回 `void`**——就算声明成 `Status` 也没有任何信息可以填进去 | `void` |

`close()` 这条比 `ISource::close()` 的理由还硬一层：那边是"知道了也没用"，这边是"压根不知道"。

**帧怎么传：** `const RawFrame&`，而且这不是风格选择——
`RawFrame` 的拷贝构造在 `Frame.h` 里被 `= delete` 了，隐式拷贝一帧是 `w*h*3/2` 字节的整块搬运，
已经从类型层面堵死。**渲染器只读不留，零次拷贝。**

**工厂是自由函数不是成员函数**：成员函数得先有对象才能调，而工厂的全部意义就是"我还没有对象"。
返回 `unique_ptr` 而不是按值——`IRenderer` 是抽象类，不能实例化，也就不能按值存在。

### `NullRenderer` 做什么

它**不是**"什么都不做"。参照 `NullSource`：那个也不是"什么都不产出"，
它画了一张内容只取决于 `frameId` 的合成画面，好让下游出问题时看得出来。这边对应的是：
**每一帧都过一遍不变量检查，坏帧计数，让测试有东西可断言。**

**能查的是"结构"，不是"内容"**——它没有参考图，而且 H.264 是有损压缩，
解出来的像素值本来就跟原图不完全相等。所以只查各字段之间自不自洽。

单帧内部：

```text
width > 0 && height > 0
width % 2 == 0 && height % 2 == 0            YUV420P 色度平面是 1/2 下采样, 奇数除不尽
fmt == PixelFormat::YUV420P
data.size() == width * height * 3 / 2        Y(w·h) + U(w·h/4) + V(w·h/4)
```

最后一条才是真正的检查。**"data 非空"是它的一个特例，而且太弱**——
一个 640×480 的帧带着 100 字节数据同样是坏帧，"非空"会放它过去。

跨帧：

```text
captureMs 严格递增, 但 captureMs == 0 时跳过比较
frameId   严格递增, 允许跳号(丢帧就跳了)不要求 +1, 同样在 0 时跳过
```

三个坑：

- **0 是哨兵不是数据，而且 `captureMs` 和 `frameId` 是同一个哨兵。**
  `Decoder::drainFrames()` 查不到 `pending_` 元信息时，这两个字段会**一起**留在默认值 0 出去——
  那正是 `DecoderStats::framesMissingMeta` 存在的原因（`NOTES.md` D14）。
  **两条都得跳过，只跳一条等于没跳**：`frameId` 那条不豁免的话 `0 <= 任何已见过的 id` 恒真，
  元信息一丢失就被记成坏帧，而且错误信息指向渲染器，把人往反方向带。
- **不查"宽高跨帧一致"。** 那不是不变量：H.264 码流自带 SPS，对端重开编码器时分辨率会变，
  而那恰恰是渲染器该正确处理的场景（重建纹理），不是错误。
- **`frameId` 不查回绕。** `RawFrame::frameId` 是 **uint64**，30fps 跑满 2^64 要约 195 亿年。
  会回绕的是 `PacketHeader` 里那个 **uint32**，而它已经在 `JitterBuffer::extendFrameId()`
  里用扩展序列号解决掉了。**回绕是传输层的问题，在传输层就该终结，不该一路渗到渲染器。**

**检查没过怎么办：计数 + 返回 `InvalidArg` + 继续跑。**
30fps 下丢一帧是 33ms，人眼察觉不到；偶发 1 帧是噪声，每秒 30 帧全坏才是上游炸了——
**只有计数能区分这两件事。**

但闭环有三层，缺一层这套就白做：

| 层 | 干什么 |
|---|---|
| `renderFrame()` 内部 | 查不变量，坏了 → `++stats_.framesRejected`，返回 `InvalidArg` |
| 主循环 | `InvalidArg` → 记一笔，**继续**；`Internal`/`IoError` → 退出 |
| 单测 | 跑完读 `stats()`，`EXPECT_EQ(framesRejected, 0)` |

**为什么不能只靠 `assert()`**：项目的 `CMakeLists.txt:8-9` 默认 `CMAKE_BUILD_TYPE=Release`
→ 定义 `NDEBUG` → **所有 `assert` 被预处理器整个删掉**。CI 上跑的是没有任何 assert 的二进制。

**为什么计数器自己也不是防线**：它不会让测试变红。计数器是**机制**，
`EXPECT_EQ` 才是**策略**，两者在不同的地方（同 `DecoderStats::framesMissingMeta`）。

### 干净退出：三种收场

三个触发源，两个入口，**一条收尾路径**。

| 收场 | 谁先发现 | 现状 |
|---|---|---|
| 点窗口的 × | 主线程 `pumpEvents()` | M3.3 新增 |
| Ctrl-C | signal handler | ✅ M2 已有，`app/receiver/main.cpp:19-23` |
| 发送端先退出 | 收包线程静默超时 | ✅ M2 已有，`ReceiverPipelineConfig::idleTimeoutMs` |

后两个 M2 就做完了，M3.3 只补第一个。

**核心：退出 = 置标志 + 唤醒。缺一不可。**
标志告诉线程"该走了"，唤醒让它有机会**看到**这句话。而阻塞在系统调用上的线程看不到标志：

| 线程 | 阻塞在 | 标志能救它吗 | 靠什么醒 |
|---|---|---|---|
| 收包 | `recvFrom()` | ❌ | **超时** —— `recvTimeoutMs = 200`（`ReceiverPipeline.h:52` 的注释就是这条） |
| 解码 | `queueA.pop()` | ❌ | **`queueA.close()`** |
| 主循环 | `popFor(5ms)` | ✅ | 自己会醒 |

收尾顺序：

```text
① stopRequested = true
② queueA.close()          上游先关
③ queueB.close()          再关下游
④ join(收包线程)          按上游 → 下游
⑤ join(解码线程)
⑥ renderer 出作用域 → ~SdlRenderer() → close()
```

**② ③ 必须在 ④ ⑤ 之前**，这是本节唯一会死锁的地方：

```text
主线程:   置标志 → close(A) → join(解码线程)         ← 卡在这
解码线程: 从 A 取完残留 → 解码 → queueB.push()       ← B 满了, 阻塞在这
主线程在 join, 不再从 B pop → B 永远腾不出位置 → 死锁
```

`BoundedQueue::close()` 会 `notFull_.notify_all()`，阻塞的 `push()` 立刻返回 `false`，
解码线程走完循环正常退出。

> **规则：`join` 一个线程之前，它可能阻塞的每一个地方，都必须已经被打开了。**

关闭顺序是 A 再 B（顺流），因为**每个线程都阻塞在自己的输入队列上**，顺流关正好逐个唤醒。
反过来先关 B 的后果不是"数据卡住"，而是解码线程**继续从 A 取、继续解码、然后 push 失败**——
全程白干，而且它不知道自己该退出了。

三条注意：

- **signal handler 里只能置标志。** 它只能调 async-signal-safe 的函数，
  而 `close()` 要加 mutex，**在 handler 里调会死锁**。
  `app/receiver/main.cpp:23` 的注释已经写了这条。
- **`join` 期间没人泵事件。** 收包线程最坏要 200ms 才醒（`recvTimeoutMs`），
  这段时间窗口会显示"无响应"。200ms 可以忍——这是**有意接受**的取舍。
- **不排空队列。** 用户点 × 是要**立刻**退出，还剩 15 帧慢慢渲染完是 0.5 秒的白等。
  队列里的数据直接丢掉。

### SDL 的六条事实（客观约束）

1. **线程规矩**：`SDL_Init` / `CreateWindow` / `CreateRenderer` / `RenderPresent` / `PollEvent`
   **必须是同一条线程**（这条是硬规则，头文件原话 "you can only call this function in the
   thread that initialized the video subsystem"）。**"而且是主线程"只是建议** ——
   原话是 "for extra safety, you should consider"，它存在的理由是 macOS 的 Cocoa。
   本项目跑在专门的渲染线程上，代价是放弃 macOS。
2. **关窗口只能从事件泵拿到**：`SDL_QUIT` / `SDL_WINDOWEVENT_CLOSE` 只有 `SDL_PollEvent` 看得见。
   不泵事件的后果不只是点不掉窗口——合成器过一会儿会判定程序卡死，打上灰色遮罩。
3. **SDL 原生吃 YUV420P**：`SDL_PIXELFORMAT_IYUV` + `SDL_UpdateYUVTexture`，
   **省掉一次 swscale 全画面转换**。注意别和 `YV12` 搞反（U/V 顺序相反，
   现象是颜色诡异但形状正常，很容易误判成解码错了）。
4. **vsync 是自己选的**：带 `SDL_RENDERER_PRESENTVSYNC` 时 `RenderPresent` 会阻塞到下一次垂直同步。
   **默认关**，留 `--vsync=1` 给"我就是要看画面不撕裂"的场合。
5. **`SDL.h` 里有 `#define main SDL_main`**：所以 `SdlRenderer.h` 里只前向声明
   `struct SDL_Window;` 这类指针成员，**绝对不 include `SDL.h`**。CMake 里 SDL2 走 `PRIVATE`。
6. **分辨率可能中途变化**：H.264 码流自带 SPS，对端重开编码器时会变。
   输出的 `RawFrame` 尺寸以每帧自己带的为准，渲染器要据此重建纹理。

另外两条不在"SDL 事实"里但同样是硬约束：

- **销毁有顺序**：Texture → Renderer → Window → `SDL_Quit()`。
  Texture 从 Renderer 创建，Renderer 绑在 Window 上，反过来就是拿已释放的对象干活。
- **`SDL_Init` / `SDL_Quit` 是进程级全局的**，不是对象级的。
  一个进程里同时活着两个 `SdlRenderer`，第一个 `close()` 就把另一个的 SDL 也关了。
  现在只有一个渲染器所以不是问题，但单测里反复 `open`/`close`/`open` 会踩到。

### 每帧一共拷贝几次

```text
AVFrame ──memcpy──> RawFrame        1 次   Decoder::copyToRawFrame, 逐行拷是因为 linesize 有对齐
RawFrame ──move──> 队列 B            0 次   unique_ptr 移动
队列 B ──const&──> renderFrame       0 次   拷贝构造已 = delete
RawFrame ──memcpy──> 显存            1 次   SDL_UpdateYUVTexture, 必要的一次
```

**总共 2 次**，两次都不可省。

### 执行步骤
1. `SDL_Init(SDL_INIT_VIDEO)`（**不要** `SDL_INIT_EVERYTHING`——白初始化音频和手柄子系统，
   而 `SDL_Init` 是**任一子系统失败就整体返回失败**，在没有声卡的容器里可能因此起不来）
2. 纹理：`SDL_PIXELFORMAT_IYUV` + `SDL_TEXTUREACCESS_STREAMING`
3. 上传：`SDL_UpdateYUVTexture(tex, nullptr, y, yStride, u, uvStride, v, uvStride)`
   —— **stride 传的是行跨距不是 `width`**。`RawFrame` 是紧凑排布，
   所以这里恰好就是 `w`、`w/2`、`w/2`；等哪天换成直接吃解码器输出，这里要改成 `linesize`
4. `SDL_RenderClear` → `SDL_RenderCopy` → `SDL_RenderPresent`
5. `ensureTexture()` 里**只在尺寸变了时重建**——每帧重建就是每帧一次显存分配
6. `pumpEvents()` 把事件队列**抽干**，`SDL_QUIT` 或 `SDLK_ESCAPE` → 返回 `true`
7. `NullRenderer` 先写，它是单测的主力，也是 `SdlRenderer` 的行为参照

## M3.4 · 延迟测量

### 做什么
把 `captureMs` 一路透传的成果兑现成数字 —— 并且兑现成一个**别人有资格判断可不可信**的数字。

---

### 一个样本是什么

| | |
|---|---|
| **起点** | `RawFrame::captureMs` —— 采集那一刻盖的章，一路透传 |
| **终点** | 渲染提交返回那一刻（`SDL_RenderPresent()` 返回） |

起点特意不在编码或打包时重取（`Encoder.h:50` 和 `Packetizer.h:38` 的注释都写着「不在这里重新取时间」）——
重取就少算了编码耗时，而**编码耗时正是要测的东西之一**。

完整推演见 `NOTES.md` **D10**。

---

### 采样点在渲染器**外面**

```cpp
// 主循环
const Status st = renderer->renderFrame(f);
if (st.isOk() && f.captureMs != 0) {
    const uint32_t now32 = static_cast<uint32_t>(steadyNowMs());
    recorder.add(now32 - static_cast<uint32_t>(f.captureMs));
}
```

不放进 `IRenderer` 的两条理由：

1. **渲染器根本不读 `captureMs`。** `renderFrame()` 只碰 `width / height / fmt / data`。
   塞进去等于给它一个它本来完全不看的字段。
2. **`IRenderer` 是接口，逻辑放上去就要写两遍**（或者塞进基类 —— 那接口就不是纯虚接口了）。

白送的一条：D10 定的终点是「`RenderPresent()` 返回那一刻」，从外面看**恰好就是**
「`renderFrame()` 返回之后」。端点定义和调用点天然对齐。

（注意这里 `NullRenderer` 筛子**筛不动** —— `NullRenderer` 测延迟其实是有意义的，
那正是"不含显示开销的下限基准"。判据得换成上面这两条。）

---

### 这个减法必须在 `uint32` 里做

`captureMs` 的位宽在管线中间变过：

```text
发送端  RawFrame::captureMs          uint64   <- steadyNowMs()
   |
Packetizer.cpp:47
   packetHeader.timestampMs = static_cast<uint32_t>(frame.captureMs);   <- 截断
   |  网络
接收端  AssembledFrame::timestampMs  uint32
   |
       CodedFrameView::captureMs     uint64   <- 从 32 位提升上来, 高 32 位全是 0
   |
       RawFrame::captureMs           uint64   <- 类型 64 位, 里面装的是个 32 位数
```

协议那个字段是 32 位（`Packet.h:71`），因为**每个包都要带它**，省 4 字节划算。

于是最朴素的写法 `steadyNowMs() - f.captureMs`（全程 uint64）会在开机 49.7 天后翻车：

```text
真实时刻            4,320,000,000 ms   (uptime 50 天)
2^32              = 4,294,967,296

发送端 captureMs    4,320,000,000       完整
包里 timestampMs       25,032,704       <- 高位被切掉
接收端 captureMs       25,032,704       uint64 变量, 装的是个 32 位数

20ms 后:
  steadyNowMs()     4,320,000,020       完整, 没被切过
  latency = 4,320,000,020 - 25,032,704 = 4,294,967,316 ms ~= 49.7 天
```

**不报错、不崩、不警告** —— 就安静地给你这个数，从此每一帧都是。

> **变量的类型宽度 != 里面那个数的宽度。**
> 拿一个被切过的数去减一个没被切过的数，位宽对不上，结果必然是垃圾。

两边都切到 32 位再减，无符号 32 位减法自带模 2^32 回绕，**跨越回绕点也正确** ——
和 `JitterBuffer::extendFrameId()` 处理帧号回绕是同一招。

验一下回绕点：`captureMs32 = 4,294,967,291`，20ms 后真实时刻切成 32 位是 `15`，
`15 - 4,294,967,291 (mod 2^32) = 20` ✓。

（顺带：**不要**先转成 `int64_t` 再减，那样跨回绕点会得到一个巨大的负数。）

### 哪些帧不该进 recorder

**① `renderFrame()` 没返回 `Ok` 的。**
端点定义是「画面提交完成那一刻」。没提交成功，这一帧就**没有终点**，
「它的延迟」这个说法根本不成立。

用白名单（`st.isOk()`）而不是枚举失败码：枚举法每加一种失败就得回来补一次，
漏一次就多一个假样本。

**② `captureMs == 0` 的。**
那是 `Decoder` 元信息丢失的哨兵（`DecoderStats::framesMissingMeta`），不是时间。
算进去就是 `now32 - 0` = **开机至今的毫秒数** —— 机器开了 3 天，这一帧就报 3 天延迟，
`max` 当场废掉，`mean` 跟着废。

**③ 被丢掉的帧压根到不了这里 —— 这条不是"要跳过"，是"要在报告里补偿"。**

队列 B 满了走 `forcePush` 丢最老的（D11），被丢的帧**从来没进过 recorder**。
它们不是"延迟很大"，是"不存在"。后果很别扭：

```text
轻载:  30 fps 全部显示,  p99 = 25ms
重载:  15 fps 一半被丢,  p99 = 25ms   <- 数字一模一样, 画面已经卡成幻灯片
```

> **延迟统计会自我美化 —— 越是扛不住，越是只有"跑得快的帧"活下来被统计。**

所以这个数字**不能单独报**，必须带上丢帧数，否则 `p99 = 25ms` 这一句可以同时描述
"完美"和"崩了"。

### 接口设计

```cpp
// common/Metrics.h
class LatencyRecorder {
public:
    void     add(uint32_t sampleMs);   // O(1), 只 push_back
    size_t   count() const;
    uint32_t percentile(int p);        // p 是 0~100 的整数; 非 const
    uint32_t max() const;              // 在 add() 里增量维护
    void     reset();

private:
    std::vector<uint32_t> samples_;
    uint32_t max_ = 0;
};
```

**只攒不算** —— 排序推迟到真正取数那一刻。每加一个样本重排一次纯属浪费，
而且中途没人看那个结果。

三个 API 决策：

**① 参数是整数 `99` 不是浮点 `0.99`。**

```text
0.5  * 100 = 50.0                  floor=50   OK
0.95 * 100 = 95.0                  floor=95   OK
0.99 * 100 = 99.0                  floor=99   OK
0.29 * 100 = 28.999999999999996    floor=28   错, 应该是 29
```

`0.29` 这个 double 存下来是 `0.28999999999999998...`，乘 100 落在 29 下面一点点。
**最坏的地方是它只在某些值上错** —— `0.5 / 0.95 / 0.99` 恰好都对，
也就是你会写的那几个测试用例恰好都过，这个 bug 能一直躺到有人问 p29 那天。

整数版 `p * count / 100` 全程整数，没有这个问题。中间量用 `size_t` ——
写成 `uint32_t` 的话 `100 * count` 在 count 超过约 **4295 万**（30fps 跑 16.6 天）时溢出。

代价：问不了 p99.9。尾延迟有时候要看它，到那天把刻度换成 `/1000`。

**② 空样本：加 `count()`，由调用方先查。**

不能"没样本就返回 0" 然后当没事 —— **0 是一个合法的延迟值**，而且失败方式是**报喜**：

```text
程序刚起来还没收到帧就被 Ctrl-C
  -> p50=0ms  p95=0ms  p99=0ms  max=0ms
  -> "哇, 零延迟"
```

跟上面那条"自我美化"是同一种病：数字把"什么都没发生"报成了"完美"。

`percentile()` 在空时返回 0（不越界、不除零），但**判断写在打印那一侧**。
`count()` 本来就要有 —— 报告里"实际统计了多少帧"就是它。

**③ `percentile()` 不是 `const`。** 取数要排序，排序就是改动容器。
代价是这个对象不能被当 `const` 传 —— 对一个存在意义就是"累积可变状态"的类不算损失。

（不用 `nth_element`：它平均 O(n) 更快，但会重排容器且只保证第 k 位对，
而退出时要连取 p50/p95/p99 —— `sort` 一次全都能用。18000 个样本排一次是微秒级的事。）

**百分位的定义**取「最近排名」(nearest-rank)：

```text
第 p 百分位 = 排序后第 ceil(p / 100 * N) 个元素(1-based)
```

N=100 时 p50 -> 第 50 个，p99 -> 第 99 个，p100 -> 第 100 个(=max)，p0 -> 夹到第 1 个。
整数除法能直接算出这个 ceil，不要引入浮点。

### 报告里必须带的字段

`latency p50=? p95=? p99=? max=?` **单独一行是没有信息量的** ——
别人没法判断它是不是在骗人。至少还要这些：

| 字段 | 不带它会怎样 |
|---|---|
| **本机回环** | 跨机器的 `steady_clock` 起点毫不相干，那个"延迟"是两台机的开机时间差（D10） |
| **运行时长 / 总帧数** | 跑 3 秒的数字和跑 10 分钟的数字说服力差一个量级；样本太少时 p99 基本等于 max |
| **`count()`（实际统计帧数）** | 它**不等于**采集帧数 —— 丢的、坏的、元信息缺失的都不在里面 |
| **丢帧数** | 见上面第 ③ 条：不带它，同一个 p99 可以既表示"完美"又表示"崩了" |
| **队列峰值有没有顶到头** | 队列 A 顶到头 = D11 那根**保险丝烧了** = `dropUntilKeyFrame()` 被调过 = 画面真的冻结过（最长一个 GOP）。而这件事在 p99 里**一点痕迹都没有** —— 冻结期间根本没有帧被渲染，也就没有样本 |
| **`--jitter-ms` 水位** | 这个数字**包含** jitter buffer 的等待时间，水位调大延迟就直接变大 |
| **分辨率 / 帧率** | `p99=25ms` 在 320x240 和 1920x1080 上是两个完全不同的成就 |
| **Release 还是 Debug** | Debug 构建能差好几倍。项目默认 Release（`CMakeLists.txt:8-9`） |
| **`--vsync` 开没开** | 见下 |
| **"不含最后一次 vsync（<=16.7ms @60Hz）"** | 这是唯一一条**结构上就测不到、只能声明**的。不写它就是在暗示"这就是用户看到画面的延迟"；别人发现你少说了一段，会连带怀疑你没少说的那些 |

`--vsync` 那条有个反直觉的地方：

| | `RenderPresent()` | 测出来的数字 | 测不到的那段 |
|---|---|---|---|
| vsync **关** | 立刻返回 | 小 | 最多 16.7ms |
| vsync **开** | **阻塞到下一次垂直同步** | 大（含等待） | 约 0 |

**开着 vsync 的数字更大，但更完整。** 关掉 vsync 测出来的漂亮数字，
有一整个刷新周期藏在外面。两种都合理，但必须说是哪一种。

> **一个说清楚了边界的数字是可信的；一个没说清边界的数字比没有数字更糟。**

---

### 两个数字，两种用途

| | 回答的问题 | 什么时候打 |
|---|---|---|
| **整场汇总** | 「这次跑下来到底多少延迟」 | 退出时一行总账 |
| **最近一段** | 「**现在**是不是正在变坏」 | 每 `--stats-interval` 一行 |

整场数字**跑得越久对新变化越迟钝** —— 后面的坏样本被前面积累的海量好样本稀释。
M4 要注入丢包，那就是有意制造"前后两段不一样"，整场数字恰好会在最需要它的时候变糊。

所以是两个 `LatencyRecorder`，"最近一段"那个每打完一行就 `reset()`。
`reset()` 用 `clear()` 保留容量，免得每秒去堆上要一次内存。

### 执行步骤
1. `LatencyRecorder` 是纯逻辑，放 `common/Metrics.h`，先写它 + 单测，跑通再接管线
2. 采样在主循环（= 渲染线程）做，离最终呈现最近；不线程安全也不需要，没有第二个线程碰它
3. 每 `--stats-interval`（默认 1000ms）打一行 INFO 汇总：`fps / 延迟 p50 p95 / 队列深度`。
   **每帧一条日志是绝对禁止的**（CONVENTIONS：热路径禁 INFO）——
   30fps 跑一分钟就是 1800 行，而且格式化本身就会影响你要测的东西（NOTES D1）
   。即使一秒一行符合频率要求，它仍会拖慢**下一帧**在队列里的等待；报告需声明
   "统计日志的开销包含在后续帧的端到端延迟中"，不能把该数字包装成无侵入测量。
4. 退出时打一行总账，字段按上面那张表来
5. 丢帧数/队列峰值这些不归 `LatencyRecorder` 管，它们分散在 `AssemblerStats` /
   `JitterBufferStats` / `RendererStats` / 队列自己那里 —— 汇总是 M3.5 装配时的活

## M3.5 · 三线程管线接起来

### 做什么
把 `ReceiverPipeline` 从"单线程收包落盘"改成三线程。**M2 那个单线程实现是有意为之**
（见 `ReceiverPipeline.h` 的注释），现在到了它说好要拆的时候，拆分点就在 `pop()` 之后。

```text
[recvLoop]                                [decodeLoop]            [renderLoop]
 recvFrom                                  pop 队列 A            pumpEvents()
   |                                         |                       |
 FrameAssembler::offer/pop                 Decoder::decode        popFor(队列 B, 5ms)
   |                                         |                       |
 JitterBuffer::push/pop  --队列 A-->      RawFrame  --队列 B-->   IRenderer::renderFrame
   |                                                                 |
 (可选)dump 落盘                                                    延迟采样

三条循环形状一致, 各自独占一条线程。渲染线程自己 Init、自己建窗、自己泵事件 ——
SDL 的硬规则是"同一条线程", 不是"主线程", 见 M3.3。三条都要 join。
```

---

### `run()` 是什么形状：三条硬约束打架

**① 渲染必须和 `SDL_Init` / `CreateWindow` / `PollEvent` 在同一条线程**（M3.3）

**② `run()` 是个阻塞函数** —— `Status run(const std::atomic<bool>&)`，调它，它跑完才返回

**③ `main.cpp` 只做装配，业务逻辑一行不许进**（M1.4 定的规矩）

四条候选：

| | `run()` 形状 | `main.cpp` | 代价 |
|---|---|---|---|
| A | 内部起 2 线程 + **自己跑渲染循环** | 纯装配 | `run()` 必须在主线程调 —— 一条**写不进类型系统**的契约 |
| B | 只管到队列 B | **出现一个真循环** | 破 ③ |
| C | 拆成 `start()` / `pumpOnce()` / `stop()` | 纯装配但要按顺序调 | 多三个 API + 一个会被忘的约定 |
| **D** ✅ | 内部起 **3** 条线程，形状不变 | 纯装配 | 显式放弃 macOS |

**选 D。** 三条循环形状一致，没有隐藏契约，这比"省一条线程"值钱。

A 那条契约有个很具体的问题：**它今天就已经被违反了。**

```cpp
// tests/test_receiver_pipeline.cpp —— 15 个用例都是这么写的
auto done = std::async(std::launch::async, [&] { return pipeline.run(stop); });
```

现有的接收端管线测试**全都从 `std::async` 起的线程里调 `run()`**。现在没炸，
是因为测试用的是 `NullRenderer`（压根不碰 SDL）。**靠人记的约定是记不住的** ——
它已经被违反了 15 次，一点征兆都没有。

D 不需要这条约定，现有测试一行都不用改。

**代价要写清楚**：显式放弃 macOS。SDL 的硬规则只要求"碰 SDL 的每一行在同一条线程"，
"而且是主线程"那条原文是 "for extra safety, you should consider" —— 但它在 macOS 上是
操作系统级强制。这是一次**有记录的取舍**，不是忘了考虑。

---

### 渲染器的生命周期怎么切

选了 D 之后有个陷阱直接掉在这儿。摆开看错误的切法：

```text
主线程:    SDL_Init  CreateWindow  CreateRenderer          <- renderer_->open()
渲染线程:  CreateTexture  UpdateYUVTexture  RenderPresent
           SDL_PollEvent                                    <- renderLoop
主线程:    DestroyWindow  SDL_Quit                          <- renderer_->close()
```

视频子系统是**主线程**初始化的，而 `SDL_PollEvent` 在渲染线程调 —— 违反硬规则。
失败方式还特别恶心：Linux/X11 上**可能照常跑**，也可能随机崩、可能卡死，
**而且不会有任何错误信息指向线程模型**。

正确的切法：

| 动作 | 线程 | 时机 | 为什么 |
|---|---|---|---|
| `createRenderer(kind)` | **主线程** | `ReceiverPipeline::open()` 里 | 只是 `make_unique`，**不碰 SDL**；放这儿才能早失败（`--render=xyz` 打错立刻报，不用等线程起来） |
| `renderer_->open(cfg)` | **渲染线程** | `renderLoop()` 的**第一件事** | 这里才开始碰 SDL |
| `renderer_->close()` | **渲染线程** | `renderLoop()` 退出前的**最后一件事** | `Destroy*` / `SDL_Quit` 也在硬规则覆盖范围内 |

> **规则不是"渲染在哪条线程"，是"碰 SDL 的每一行都在同一条线程"。**
> `open` 和 `close` 是这条链的两端，最容易被漏掉 —— 因为它们看起来像"初始化/清理"，不像"渲染"。

**一个白送的回报**：`renderer_` 是 `unique_ptr` 成员，析构仍然跑在主线程上。
但渲染线程退出前已经 `close()` 过了，所以那次析构里三个指针都是 `nullptr`、
`SDL_WasInit(0)` 是 0 —— **一行 SDL 都不会调，是个彻底的空操作**。

这就是 M3.3 那两条设计（`close()` 幂等 + `SDL_WasInit(0)` 守卫）真正的回报：
当时的理由是"防止忘了调"和"别关一个还没开的东西"，现在它们顺手把**跨线程析构**也解决了。

**渲染线程里 `open()` 失败怎么办**（比如没有 `DISPLAY`）：那时
`ReceiverPipeline::open()` 早就返回 `Ok` 了，另外两条线程还在跑。
渲染线程要写 `renderStatus_` **再调 `requestStop()`**，不能只是自己退出。

### 停止信号：一个函数，四个触发源

四个触发源（Ctrl-C / 窗口关闭 / `maxFrames` 收满 / `idleTimeout` 空闲），**一条收尾路径**：

```cpp
void ReceiverPipeline::requestStop() {   // 任何线程都能调, 调几次都行
    stopping_.store(true);   // 让还在循环里的线程下一轮就退出
    queueA_.close();         // 唤醒堵在 pop(A) 的解码 / 堵在 push(A) 的收包
    queueB_.close();         // 唤醒堵在 push(B) 的解码
}
```

**三件事必须一起做。** 因为标志位只在循环顶部被查，而线程可能根本回不到循环顶部：

| 线程 | 阻塞在 | 标志能救它吗 | 靠什么醒 |
|---|---|---|---|
| 收包 | `recvFrom(..., 200ms)` / `queueA.push()` | 部分 | 超时，或 `close(A)` |
| 解码 | `queueA.pop()` / `queueB.push()` | **不能** | **只能靠 close** |
| 渲染 | `popFor(队列B, 5ms)` | 能 | 超时，自己会醒 |

解码线程两头都可能无限期阻塞，而 `pop()` 是**没有超时**的条件变量等待 ——
标志位对它一点用都没有。

> **退出 = 置标志 + 唤醒，缺一不可。**
> 标志说"该走了"，`close()` 让它**有机会听见**。

**为什么不能由 `run()` 统一协调**：`run()` 那条线程已经堵在 `join()` 上了，
收尾**只能由三条工作线程自己发起**。

**`stopRequested` 是 `const` 引用，管线写不了它。** 这在 M2 是对的（那时所有停止信号
都从外面来），但窗口关闭是**管线内部产生**的第四个触发源，借不到这个变量往外传。
所以内部另有一个 `std::atomic<bool> stopping_`，三条循环判两者的并集。

**并发发起是安全的**：`atomic` 的写天然安全，`BoundedQueue::close()` 内部加锁且幂等。

顺带澄清两个容易混的机制：

```text
Ctrl-C  ->  SIGINT  ->  main.cpp 的 onSignal()  ->  gStopRequested = true
                        (内核送信号, 跟 SDL 一点关系都没有)

点  x   ->  窗口系统  ->  SDL 事件队列  ->  渲染线程 SDL_PollEvent()
```

Ctrl-C **不经过 SDL 事件泵**。之后哪条线程先"发现"取决于谁先回到循环顶部
（渲染 5ms 一轮、收包 200ms 一轮），但这不重要 —— **谁先发现谁调 `requestStop()`**。

完整推演见 `NOTES.md` **D17**。

---

### 错误怎么走到 `run()` 的返回值里

三个 `Status` 成员，`join()` 之后按**上游优先**（收包 > 解码 > 渲染）挑一个返回。

**不需要加锁也不用 atomic** —— `join()` 本身提供 happens-before：被 join 的线程
结束前写的任何东西，join 返回之后都能安全读到。

优先级取上游的判据：**下游的错误常常是上游错误的后果，上游的错误更可能是根因。**
网卡挂了 → 队列 A 一直空 → 解码线程空转 → 渲染无帧可画；三条线程都不正常，
但只有第一条说出了原因。

**但有个坑，它跟上面这条规则互相咬 ——**

走一遍点 × 的路径：渲染线程 `requestStop()` 之后，解码线程正堵在 `queueB_.push()` 上，
被唤醒后 `push()` 返回 `false`；收包线程同理。**那两个 `false` 是正常收尾的一部分，不是故障。**

写成错误有两层后果：

- **表层**：每次正常退出（点 ×、Ctrl-C）`run()` 都返回非 `Ok`，退出码变 1。
  顺带一提 `test_receiver_pipeline.cpp` 里 15 个 `ASSERT_TRUE(done.get().isOk());` 会全红。
- **深层（这个才要命）**：

```text
真实故障:  渲染线程 open 失败(没有 DISPLAY)  ->  renderStatus_ = IoError("SDL_Init failed")
                     |  requestStop()
假错误:    收包线程 push 返回 false           ->  recvStatus_  = NetError("队列已关闭")
                     |  上游优先
run() 返回: NetError("队列已关闭")             <- 真正的原因被埋掉了
```

**噪声按优先级排在了信号前面。**

`BoundedQueue::push()` 的 `false` **只有一个含义**（看实现：它不会因为"队列满"返回 false，
那时它阻塞等待，只会因为**关闭**）。所以 `push()` 返回 false 时写 `Status::ok()` 是无条件正确的。

> **收尾路径上的每一个"失败"返回值，都要先问一句：这是故障，还是正常结束？**

完整推演见 `NOTES.md` **D19**。

### 每秒那行统计：跨线程读计数器

```text
[INFO] fps=30 latency p50=8 p95=14 | 队列A=0 队列B=1 | 丢帧=0 组包丢包=0
```

这行由渲染线程打（延迟样本在它手上），但数字散落在别处：`AssemblerStats` /
`JitterBufferStats` 由**收包线程**每收一个包就 `++`，`DecoderStats` 由**解码线程**改。

渲染线程直接读它们是**数据竞争** —— C++ 标准判它未定义行为，不是"值可能不准"。
（实践上在这个形状里最可能看到的只是字段之间错位，因为 `offer()` 是跨编译单元的
非内联函数；但开了 LTO 或者哪天 `offer()` 变成 `inline`，编译器就有机会把计数器
提到寄存器里 —— 那时渲染线程会读到一个**几秒钟不动**的数字。
**"当前编译器碰巧没这么优化"不是一个可以依赖的性质。**）

**先问需求再选机制**：这一行日志需要"每个字段各自正确"，还是"所有字段属于同一瞬间"？
对一行给人看的统计，前者就够 —— 而且实际偏差比直觉小得多：渲染线程读那五六个字段是
连续几条 load（纳秒级），包是每约 1.3ms 来一个，最坏差 1 个包。

两条路的对账（**结论跟直觉相反**）：

| | 改动面 | 热路径 | 得到的保证 |
|---|---|---|---|
| 计数器改 `std::atomic` | 三个 stats 结构体共约 20 个字段全改；结构体变**不可拷贝**，`stats_.assembler = assembler_.stats();` 直接编译不过 | 每包约 6 次 `lock xadd` | **弱**（字段仍会错位） |
| **快照 + 一把锁** ✅ | 三个模块**一行不改**，只在 `ReceiverPipeline` 加 1 个 mutex + 1 个 `shared_` + 3 处调用 | 频率自己定，可降到 10 次/秒 | **强**（一致快照，白送） |

> **"无锁"不等于"更轻"。** 这里它改动面大 20 倍、保证更弱、热路径反而更重。

各个 stats 结构体仍然**被各自的线程独占**，本来就没有竞争 —— 需要同步的只有那次快照拷贝。
无竞争的 `std::mutex` 加解锁约 20ns，750 次/秒 = **15 微秒/秒**。

`BoundedQueue::size()` / `peak()` **本来就加了锁**（`BoundedQueue.h:193`），队列深度不用操心。

完整推演见 `NOTES.md` **D18**。

### 为什么 JitterBuffer 挂在收包线程，而不是解码线程
项目定死了"**`BoundedQueue` 是线程间唯一的数据通道**"。JitterBuffer 有内部状态且不是线程安全的，
挂在收包线程上它就被单线程独占，一把锁都不用加。
挂在解码线程则要么再加一个队列（那 jitter 的时序就被前一级的排队污染了），要么给它上锁——
两条路都比现在差。

### ⚠️ 必踩的坑：poll 超时会吃掉 jitter 的精度

收包线程的循环是 `recvFrom(..., recvTimeoutMs)`，M2 里这个值是 200ms。
现在同一个线程还要负责"到点了把帧放出去"，如果还是傻等 200ms，
一帧最坏要多压 200ms 才被放行——`--jitter-ms=50` 设了等于没设，
而且现象是**延迟数字比设定值大得离谱且忽大忽小**，很容易怀疑到解码器头上去。

所以每次进 `recvFrom` 之前，超时值要被**下一帧的到期时间夹一下**：

```cpp
int timeoutMs = config_.recvTimeoutMs;
const int untilDue = jitter_.msUntilNextDue(steadyNowMs());
if (untilDue >= 0) timeoutMs = std::min(timeoutMs, untilDue);
if (timeoutMs < 0) timeoutMs = 0;          // 已经过期了, 别传负数进 poll
```

`JitterBuffer::msUntilNextDue()` 这个方法就是为这件事存在的。

### 执行步骤

1. **`ReceiverPipelineConfig` 新增**：`renderKind`、`jitter`（整个 `JitterBufferConfig`）、
   `decoder`、`renderer`、`decodeQueueCapacity`、`renderQueueCapacity`、`statsIntervalMs`。
   嵌整个子配置而不是逐字段抄，改一个默认值只用改一处
2. **队列元素用 `std::unique_ptr<AssembledFrame>` / `std::unique_ptr<RawFrame>`** ——
   两者都是 move-only，`BoundedQueue` 早就支持（M0 验过）
3. **队列容量给小**（2~3）。**队列容量就是延迟预算**（D4）：30fps 下 cap=3 就是 100ms。
   这跟发送端恰好相反 —— 发送端积压只占内存，接收端积压是实打实加到用户看到的延迟上
4. **`recvLoop()` 基本就是 M2 那个 `run()` 的循环体搬过来**，唯一的结构改动是
   原来 `pop()` 出来直接 `writeFrame()`，现在还要 `push` 进队列 A；外加超时夹一下（见上）
5. **构造函数要动**：`BoundedQueue` 只有 `explicit BoundedQueue(size_t)`，没有默认构造，
   `queueA_` / `queueB_` 必须进初始化列表。注意**初始化顺序按声明顺序走**，不是书写顺序
6. **CMake**：`llreceiver` 现在要 `PUBLIC lltransport lldecode llrender`。
   SDL 和 FFmpeg 本身仍是 `PRIVATE` 的（在各自的 CMakeLists 里挡着），
   这里链进来的只是接口，不会把 `#define main SDL_main` 传染出去
7. **`--dump` 保留**：解码前的码流照旧可以落盘。出问题时第一件事就是把 dump 出来的文件
   丢给 ffplay，一秒钟就能分清是"传输错了"还是"解码/渲染错了"
8. `main.cpp` 只做装配，业务逻辑一行都不许进去（M1.4 定的规矩）

## ⚠️ 常见坑提醒（M3 预警）

1. **帧级多线程解码（`FF_THREAD_FRAME`）默认开着**：解码器攒够 N 帧才吐第一帧，
   凭空多出 3~4 帧延迟，而且没有任何报错。低延迟项目必须显式设 `FF_THREAD_SLICE`。
2. **`AVPacket` 尾部不留 `AV_INPUT_BUFFER_PADDING_SIZE`**：比特流读取器越界预读，
   平时"看着没事"，valgrind 下必报，压力大时随机崩。
3. **存 `receive_frame` 返回的 `AVFrame` 指针**：它是解码器复用的，下一次调用就变了内容。必须当场拷走。
4. **解码输出也有 `linesize` 对齐**：`linesize[0] > width` 是常态，整块 memcpy 得到斜着撕裂的画面
   —— M1 踩坑 3 的镜像版，编码端踩过一次，解码端还会再踩一次。
5. **不从关键帧起播**：解码器狂吐 `no frame!`，画面全绿或全花，直到下一个 IDR。
   JitterBuffer 的 `startOnKeyFrame` 就是为它存在的。
6. **FFmpeg 日志不接管**：M4 一开丢包注入，`error while decoding MB` 会把终端刷到没法看，
   自己的日志全被淹没。`av_log_set_callback()` 现在就接上。
7. **喂进解码器的帧顺序错了**：不报错，只是画面"看着不太对"。这类 bug 没有任何错误信息可查，
   所以 JitterBuffer 必须先做、必须单测。
8. **SDL 跨线程用窗口**：创建、渲染、泵事件、销毁必须同一个线程。违反的表现是随机崩或直接卡死。
9. **不泵事件**：窗口不响应关闭，合成器判定程序无响应给你打灰色遮罩。哪怕不处理也要抽干队列。
10. **IYUV 和 YV12 搞反**：U/V 平面顺序反了，画面颜色诡异（人脸发蓝发紫）但形状正常，
    很容易误判成"解码错了"。本项目用 `SDL_PIXELFORMAT_IYUV`。
11. **`SDL_UpdateYUVTexture` 传 `width` 当 stride**：画面斜着撕裂，和第 4 条现象一样、成因不同。
12. **默认开 vsync**：白送最坏 16ms 延迟，还会让你测出来的延迟数字莫名其妙地锯齿状波动。
13. **`recvFrom` 超时没被 jitter 到期时间夹住**：帧最坏被压满一个 `recvTimeoutMs` 才放行，
    延迟远大于设定的水位，且忽大忽小——查半天会怀疑到解码器头上。
14. **接收端队列容量给大**：队列深度直接变成用户看到的延迟。接收端和发送端在这件事上**恰好相反**，
    发送端积压只占内存，接收端积压是实打实的延迟。
15. **只 close 下游队列**：上游线程永远堵在 `push()` 上，join 回不来。M2 的 `sendLoop` 踩过，
    三线程下有两倍的机会再踩。
16. **窗口关闭这个停止信号是自下而上的**：另外三个（Ctrl-C / 收满 / 空闲超时）都是自上而下，
    唯独它方向相反，最容易漏掉对上游队列的唤醒。
17. **测试里开 SDL 窗口**：CI 上没有 display，`ctest` 直接红。`NullRenderer` 不是锦上添花。
18. **`SDL_INIT_EVERYTHING`**：白初始化音频/手柄，而任一子系统失败就整体失败，
    在没声卡的容器里可能因为音频起不来而整个视频也没了。只要 `SDL_INIT_VIDEO`。
