## M0 · 工程骨架

### 1. 头文件里在类外定义函数，必须加 `inline`

**现象**
只有一个 `.cpp` 包含时一切正常；第二个 `.cpp` 也包含之后，**编译全过、链接失败**：

```
multiple definition of `parseLogLevel(std::string const&)'
first defined here
```

**原因**
不是"重复编译"，是**重复定义**。`#pragma once` 只防同一个翻译单元（TU）内重复展开，
挡不住两个 TU 各自展开一份。每个 TU 编出一份同名强符号，链接器合并时撞车 —— 违反 ODR。

**做法**
头文件里**在类外（命名空间作用域）定义**的函数一律加 `inline`；`inline` 在这里的语义不是
"建议内联展开"，而是"允许多个 TU 各有一份定义，链接器挑一个"。

以下几种是**隐式 inline，不用加**，别乱加噪音：

| 写法 | 是否需要 `inline` |
|---|---|
| 类**体内**直接写实现的成员函数（如 `Status::isOk()`） | 否，隐式 inline |
| 模板函数 / 模板类的成员函数 | 否 |
| `constexpr` 函数 | 否 |
| 类**体外**定义的成员函数（`inline bool Status::isOk() const {...}`） | **是** |
| 头文件里的普通自由函数 | **是** |
| 头文件里的非 const 全局变量 | **是**（C++17 `inline` 变量） |

> 另一条出路：只在头文件里**声明**，实现挪进 `.cpp`。热路径上的短函数（访问器）才值得放头文件，
> 见 `common/Status.h` 里 `isOk()/code()/message()` 三个访问器的处理。

### 2. 宏定义末尾不要写分号

**现象**

```cpp
#define LOG_INFO(mod, ...) Logger::instance().log(...);   // ← 结尾多了个分号

if (ok)
    LOG_INFO("sender", "done");
else                       // error: 'else' without a previous 'if'
    ...
```

**原因**
调用处本来就要写分号，宏里再带一个，展开后变成**两条语句**（第二条是空语句），
把 `if` 的单语句体撑爆，`else` 就找不到对应的 `if` 了。同理会让
`while (x) MACRO(...);` 的循环体提前结束。

**做法**
- 宏定义**永远不以分号结尾**，让调用点自己写分号——这样宏用起来才像函数。
- 单表达式宏：直接写表达式（本项目 `LOG_*` 就是这样，展开成一次函数调用）。
- 多语句宏：包 `do { ... } while (0)`（**注意 `while(0)` 后面也不加分号**），
  这是唯一能同时满足"能带 `;` 调用"和"能安全放进 `if` 单语句体"的写法。
- 宏参数每个都用括号裹住：`#define MAX(a,b) ((a) > (b) ? (a) : (b))`，防运算符优先级被拆。

### 3. 模板类不能拆成 `.h` + `.cpp`

**现象**
`BoundedQueue.h` 放声明、`BoundedQueue.cpp` 放实现，编译两个文件都过，**链接报错**：

```
undefined reference to `BoundedQueue<int>::push(int)'
```

**原因**
模板不是代码，是**代码生成器**。编译器只有在看到 `BoundedQueue<int>` 这个具体用法时
才会实例化出真代码，而实例化**必须能看到模板的完整定义**。
`main.cpp` 只 include 了 `.h`（光有声明），编不出实体；
`BoundedQueue.cpp` 里有定义，但它自己没用过 `BoundedQueue<int>`，不会主动实例化。
两边都没生成 → 符号不存在。

**做法**
模板**全部实现写在头文件里**（本项目 `common/BoundedQueue.h` 就是这么做的）。
如果嫌头文件太长，可以把实现放 `.tpp/.ipp`，在头文件**末尾** `#include` 进来——
本质仍是同一个头文件，只是物理分开。
第三条路是显式实例化（`template class BoundedQueue<int>;` 写在 `.cpp` 里），
但那要求**类型集合是封闭的**；本项目后面要塞 `unique_ptr<Frame>`、`unique_ptr<Packet>`
等一堆类型，用它等于每加一种类型改一次库，不划算。

### 4. `condition_variable::wait` 必须带谓词

**现象**
`BoundedQueue` 压测偶发：队列明明是空的，`pop()` 却往下走了；或者 `close()` 之后
个别线程死活不退出。

**原因**
两件事叠在一起：**虚假唤醒**（wait 可能无缘无故返回），以及 `close()` 用的是
`notify_all()`——多个线程被同时唤醒，但只有第一个抢到数据，其余的醒来时条件已经不成立。

**做法**
一律用带谓词的重载，等价于"`while (!pred()) wait();`"：

```cpp
notEmpty_.wait(lk, [this]{ return !q_.empty() || closed_; });
```

谓词里**必须把 `closed_` 一起判**，否则 `close()` 唤不醒等待者，退出时直接挂死。

### 5. `close()` 的语义在 push 和 pop 上是**不对称**的

**现象**
第一版 `pop()` 写成 `if (closed_) return false;`，结果 `close()` 一调，队列里
残留的数据全丢了——表现为"退出时最后几帧莫名其妙没了"。

**原因**
关闭的语义是"不再接收新数据"，不是"立刻丢掉已有数据"。

**做法**

| | close 后的行为 |
|---|---|
| `push` / `tryPush` | 立即返回 false，拒收新数据 |
| `pop` | **先把残留取完**，取空之后才返回 false |

所以 `pop()` 的判断是 `if (q_.empty()) return false;` 而不是判 `closed_`
（见 `common/BoundedQueue.h`）。这样消费者线程能自然跑完 `while (q.pop(x))` 循环退出，
不需要额外的退出标志位。

### 6. 按值传参的 `push` 失败时，实参已经被掏空

**现象**
`if (!q.push(std::move(frame))) { /* 想把 frame 重新入队 */ }` —— 拿到手的是个空壳。

**原因**
`bool push(T item)` 按值接收，`std::move` 在**进函数那一刻**就完成了转移，
后面无论成功失败，调用方的 `frame` 都已经是 moved-from 状态。

**做法**
接受这个语义并在文档里写死：push 返回 false 意味着整条流水线正在退出，丢弃可接受。
真需要"失败可回滚"的地方，改用 `tryPush` **先探测再转移**，或者传指针自己管所有权。

### 7. 先解锁再 notify

**现象**
不算 bug，是性能问题：持锁状态下 `notify_one()`，被唤醒的线程立刻又堵在同一把
mutex 上，白白多一次上下文切换（惊群的小号版本）。

**做法**
```cpp
lk.unlock();
notEmpty_.notify_one();
```
反过来 `close()` 里是先在小作用域里改完 `closed_` 再出作用域解锁、然后 `notify_all()`，
同一个道理。

### 8. `std::mutex` 不可重入，私有辅助函数不要再锁一次

**现象**
把 `push`/`tryPush` 的公共部分抽成 `enqueue()`，里面又 `lock_guard` 一次 —— 自己把自己锁死。

**做法**
抽出来的函数**不加锁**，用 `Locked` 后缀 + 签名上收一个用不到的
`const std::unique_lock<std::mutex>&` 参数，把"必须在锁内调用"这件事钉在接口上
（编译器查不了这个约定，锁外误调是**不崩不报错的数据竞争**，只能靠命名和签名防）。
参数配 `[[maybe_unused]]`，否则 `-Wextra` 会报未使用参数。

### 9. `size()` 返回即过期

多线程下 `size()` 的返回值在 return 的下一纳秒就可能变了。
只能用于**观测**（打点、日志、`peak()` 水位分析），
绝不能写 `if (q.size() < cap) q.push(...)` 这种 check-then-act —— 中间有窗口。
真要非阻塞入队，用 `tryPush`（判断和入队在同一个临界区内）。

### 10. 阻塞类单测必须有超时保护

**现象**
测试一旦写错（比如 `close()` 没唤醒等待者），`ctest` 不是失败，是**永远卡住**，
CI 挂到超时才被杀。更阴的是 `std::future` 的**析构函数也会阻塞**到任务结束。

**做法** 两层保险：
1. 用例内部 `std::async` + `future.wait_for(timeout)` 判断是否按预期阻塞/返回；
2. CMake 侧兜底：`gtest_discover_tests(${name} PROPERTIES TIMEOUT 30)`，
   让挂死表现为"这条用例失败"而不是"整条流水线卡住"。

### 11. 测试目标别逐个列 `../common/*.cpp`

**现象**
最初 `tests/CMakeLists.txt` 里把 common 的源文件一个个列进 `add_executable`。
`common/` 每加一个 `.cpp` 就得同步改测试这边，漏一个就是 undefined reference；
同一份源码还被编译两遍。

**做法**
统一 `target_link_libraries(... PRIVATE llcommon)`。
`llcommon` 用 `PUBLIC` 声明的 include 路径和 `pthread` 会自动传递过来，测试侧一行不用重复写。
顺带：根 `CMakeLists.txt` 里 `add_subdirectory(common)` **必须排在 `app/*` 之前**，否则找不到 target。

### 12. clangd 报一堆"找不到头文件"的假错

**现象**
代码能正常编译，编辑器里却满屏红波浪线。

**原因**
根目录放了一份手工拷贝的 `compile_commands.json`。新增源文件、新增 FetchContent 依赖之后，
这份副本就过期了，clangd 拿着旧的 include 路径找不到东西。

**做法**
`.clangd` 里直接指向 build 目录，让它读 `CMAKE_EXPORT_COMPILE_COMMANDS` 生成的**活的**数据库：

```yaml
CompileFlags:
  CompilationDatabase: build
```

## M1 · 采集 + 编码

### 14. 只 `= delete` 拷贝，会把移动一起弄没

**现象**
`RawFrame` 想做成"禁止拷贝、允许移动"，于是先写了两行：

```cpp
RawFrame(const RawFrame&) = delete;
RawFrame& operator=(const RawFrame&) = delete;
```

结果 `RawFrame b = std::move(a);` 编译失败，而且报的是**拷贝**构造函数：

```
error: use of deleted function 'RawFrame::RawFrame(const RawFrame&)'
note: declared here
    RawFrame(const RawFrame&) = delete;
```

明明写的是 `std::move`，报错却指向拷贝——第一眼完全看不懂。

**原因**
两步：

1. **只要声明了拷贝构造/拷贝赋值（哪怕是 `= delete`），编译器就不再隐式生成移动构造/移动赋值。**
   于是 `RawFrame` 压根没有移动构造函数。
2. `std::move(a)` 产生一个右值，重载决议里唯一能接住它的是 `const RawFrame&`
   （const 左值引用可以绑右值），而它恰好是 deleted → 报错，且报的是拷贝版本。

反过来也成立：声明了移动构造，拷贝构造会被自动 delete。这就是**五法则**——
拷贝构造、拷贝赋值、移动构造、移动赋值、析构，一旦手写其中任何一个，
其余几个的默认生成规则就会变，最稳妥的做法是**要么一个都别写（零法则），要么写全**。

**做法**
四行成套写，缺一不可：

```cpp
RawFrame(const RawFrame&)            = delete;   // 3MB 一帧, 隐式拷贝是无声的性能陷阱
RawFrame& operator=(const RawFrame&) = delete;
RawFrame(RawFrame&&)            = default;       // 队列靠 move 交接所有权
RawFrame& operator=(RawFrame&&) = default;
```

并在单测里用 `static_assert` 钉住这四条性质（见 `tests/test_frame.cpp`），
哪天有人手滑删掉 move 那两行，编译期立刻指出问题，而不是等到调用点报一句
看不懂的 "use of deleted function"。

这就是 **move-only 类型**的标准写法，`unique_ptr` / `thread` / `fstream` / `mutex`
全是这个路子：资源天然独占，拷贝没有合理语义，但所有权可以转交。

**附带一个坑**：`= default` 生成的是**逐成员移动**。`data`（vector）被偷走指针变空，
但 `width` / `height` / `frameId` 这些标量是**照抄**过去的——被 move 走的帧会
"自称 64×32 却一个字节数据都没有"。所以 move 之后不要再读那个对象，要用先 `reset()`。
流水线里全程传 `unique_ptr<RawFrame>`，正是为了根本不出现这种半空对象。

### 15. 周期性任务不要用相对睡眠

**现象**
`NullSource` 的帧率节流，第一反应是每帧睡一个固定时长：

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(1000 / fps));
```

实测 150 帧 @30fps（应该 5000ms）：

```
sleep_for   : 5245 ms   实际 28.60 fps
sleep_until : 4968 ms   实际 30.19 fps
```

5 秒漂 277ms，**折算到 60 秒是 3.3 秒**。而且是稳定偏慢，不是抖动。

**原因**
`sleep_for(T)` 的标准语义是"**至少**睡 T"（at least），保证不会少睡，从不保证不会多睡。
于是每帧的实际周期是：

```
一帧 = 干活时间 + sleep 时间 = 1.5ms + (33ms + 调度误差)
```

误差**恒为正**，且没有任何机制把它拿回来——只能一帧帧累加。写成递推式一眼看穿：

```
sleep_for   :  t(n+1) = t(n) + T + ε(n)      ← 误差进入下一轮的输入, 滚雪球
sleep_until :  t(n)   = start + n·T + ε(n)   ← 误差不进状态, 每帧独立
```

**做法**
以 `open()` 时取的 `start_` 为**绝对基准**，算第 n 帧的应到时刻：

```cpp
const auto offset = std::chrono::microseconds(frameId_ * 1000000ULL / fps);
std::this_thread::sleep_until(start_ + offset);
```

绝对基准**自带纠错**：某帧被系统卡住迟到 100ms，下一帧的目标时刻没变，它会睡得更短甚至
立即返回，把欠的追回来。实测 1800 帧 @30fps 用时 59967ms，理论值 59966.7ms，**偏差 <1ms**。

两个细节：

- **先乘后除**：`frameId_ * 1000000 / fps` 而不是 `frameId_ * (1000000 / fps)`。
  后者 `1000000/30 = 33333`（真值 33333.33），每帧丢 0.33µs——又一个只增不减的累加项。
  先乘后除，整个运行期的截断误差合计不超过 1µs。
- **治不了"真的算不过来"**：如果画一帧要 40ms 而目标 33ms，`sleep_until` 每次都发现已超时、
  立即返回，帧率自然掉下来。这是正确行为，节流器的职责是"别跑太快"，不是变出算力，
  更不该靠补帧去追（那会产生一串时间戳挤在一起的帧，下游更难受）。

**为什么这事对"低延迟"是硬伤**
漂移本身是"帧率不准"，它变成延迟要经过一条链：**速率失配 → 队列积压 → 积压就是延迟**。
下游全都按 30fps 的节奏工作，采集实际 30.3fps 的话每秒多产 0.3 帧，10 秒后队列里躺着
3 帧 = 100ms 额外延迟，且只增不减，直到队列满开始丢帧（第 5 条那个有界队列就是兜这个的）。
反方向偏慢则是接收端 jitter buffer 饿死、卡顿重复帧。

还有更阴的一条：`captureMs` 是端到端延迟的**起点**，采集节奏漂了这个时间戳就偏，
M3 算出的 p50/p95 本身就不准——**测量工具自己先漂了**。

> 通用结论：任何周期性的东西（定时器、心跳、pacing 发包、码率控制）都不要拿
> "上一次的时间"当基准，要拿一个固定原点。

### 16. 编码结束前必须发送空帧排空编码器

**现象**
所有输入帧都已经通过 `avcodec_send_frame()` 送入编码器，但直接关闭编码器后，输出视频的
最后几帧消失，时长比预期短；使用 B 帧或带 lookahead 的编码器时更容易出现。

**原因**
编码器不保证“输入一帧，立刻输出一个包”。为了 B 帧重排、帧间预测和码率分析，编码器可能
在内部暂存若干输入帧。送完最后一张正常帧只表示“目前没有继续送”，不表示“以后不会再送”，
所以编码器不能主动把依赖后续输入的状态收尾。此时直接 `avcodec_free_context()`，内部尚未输出的
编码包会被直接丢弃。

`avcodec_send_frame(ctx, nullptr)` 里的 `nullptr` **不是一张黑帧**，而是 EOF/排空信号：
告诉编码器不会再有输入，让它进入 draining 状态并输出所有剩余包。

**做法**
正常结束时先发送一次 `nullptr`，然后持续接收，直到 `avcodec_receive_packet()` 返回
`AVERROR_EOF`：

```cpp
int rc = avcodec_send_frame(ctx_, nullptr);
if (rc < 0 && rc != AVERROR_EOF) {
    return Status::error(Code::Internal,
                         "avcodec_send_frame(nullptr) failed: " + avErr(rc));
}

// flush 之后必须一直 drain 到 AVERROR_EOF，不能只收到 EAGAIN 就当作完成。
return drainPackets(out);
```

注意三个边界：

- 发送 `nullptr` 后已经进入 draining 状态，不能再发送普通帧；想重新开始要重置或重建上下文。
- `drainPackets()` 在普通编码阶段可以遇到 `AVERROR(EAGAIN)` 就返回；进入 draining 状态后则应
  一直接收到 `AVERROR_EOF`，此时正常流程不应再返回 `EAGAIN`。
- 不要用 `avcodec_flush_buffers()` 替代。前者的目标是**取完剩余输出**，后者是**重置内部状态**，
  可能直接丢掉尚未输出的数据。

### 17. 摄像头挂不进开发环境，最后改用 v4l2loopback 造虚拟设备

**现象**
V4L2 采集代码写完、契约测试全绿，但真机验证跑不起来 —— 开发环境里根本没有 `/dev/video0`。
为了给它变出一个摄像头，连试三条路，全废：

| 尝试 | 结果 | 原因 |
|---|---|---|
| WSL2 直通笔记本摄像头 | `/dev/video*` 不存在 | WSL2 默认内核没编 `CONFIG_VIDEO_DEV`，**没有 V4L2 子系统**。就算用 `usbipd-win` 把 USB 设备转进去，也没有驱动去认领它 |
| VMware 虚拟机 + USB 直通 | `lsusb` 里始终看不到设备 | 笔记本内置摄像头虽然走 USB 协议，但被主机固件/系统握得很紧，VMware 抢不过来 |
| `apt install v4l2loopback-dkms` | dkms 编译失败 | 发行版打包的是 0.12.7，比内核老 |

第三条的报错值得单独记，因为它和前两条不是一类问题：

```
v4l2loopback.c:2089:9: error: too few arguments to function 'v4l2_fh_add'
  2089 |   v4l2_fh_add(&opener->fh);
/usr/src/linux-headers-.../include/media/v4l2-fh.h:97:6: note: declared here
    97 | void v4l2_fh_add(struct v4l2_fh *fh, struct file *filp);
```

**原因**
内核给 `v4l2_fh_add` / `v4l2_fh_del` 加了 `struct file *filp` 参数，而发行版仓库里的
v4l2loopback 版本早于这次改动。**内核模块没有稳定 ABI，也不承诺 API 兼容** —— 树外模块
（out-of-tree module）必须跟着内核版本走，发行版打包滞后半个版本就编不过。这类报错
和自己的代码无关，看 `note: declared here` 指向的内核头文件就能确认是签名对不上。

**做法**
拿上游源码编，两行改动补上新参数：

```bash
git clone https://github.com/umlaeute/v4l2loopback.git
cd v4l2loopback && make && sudo make install && sudo depmod -a
sudo modprobe v4l2loopback video_nr=0 exclusive_caps=1
```

然后用 ffmpeg 往这个虚拟设备里持续推固定图案，`/dev/video0` 就是一个标准 V4L2 采集设备，
`V4l2Source` 一行不用改：

```bash
ffmpeg -re -f lavfi -i testsrc=size=640x480:rate=30 -pix_fmt yuyv422 -f v4l2 /dev/video0
```

**为什么这不是"退而求其次"**
一开始把 v4l2loopback 当成没有摄像头时的替代品，跑通之后发现它在两件事上**强于真摄像头**：

- **可重复**。`testsrc` 每次输出的图案完全一致。调 `convertFrame()` 时颜色偏了、U/V 平面接反了、
  stride 算错了，一眼就能看出来；真摄像头对着房间拍，画面每次都不同，**没有参照物**，
  只能靠"看着好像不太对"来判断。
- **可回归**。虚拟设备可以在任意机器上按需创建，V4L2 这条路径因此能进 CI、能参与压测。
  真摄像头做不到 —— 它不能被脚本创建，也没法保证两次运行输入相同。

这和 `NullSource` 的存在理由是同一条：**可重复的输入是调试和压测的前提**。区别只在于
`NullSource` 绕过了整个 V4L2 子系统，而 v4l2loopback 保留了完整的
`ioctl` / `mmap` / `QBUF` / `DQBUF` 调用链，验证的是真实的内核交互路径。

> 更一般的教训：**先问"我到底要验证什么"，再决定环境怎么搭**。这里要验证的是
> "V4L2 协议交互写对了没有"，不是"这个摄像头能不能用"。一开始盯着"把物理摄像头挂进来"，
> 是把手段当成了目的，白花了一下午在 USB 直通上。

## M2 · 自研传输

### 18. 协议头不能把整个结构体 `memcpy` 上网

**现象**
发送端和接收端使用同一份 `PacketHeader` 定义，本机自测可能正常；一旦更换编译器、调整字段顺序，
或与不同字节序的机器通信，接收端就会读出错误的 `streamId`、巨大 `seq` 等异常值。
线上协议明明规定包头是 12 字节，`sizeof(PacketHeader)` 也可能不是 12。

**原因**
`PacketHeader` 是 C++ 对象的**内存表示**，不是协议的**线上表示**，两者受不同规则约束：

- 编译器可能为满足字段对齐，在结构体成员之间或末尾插入填充字节；因此 `sizeof` 不保证等于各字段
  线上长度之和，填充字节也不属于协议。
- 多字节整数在内存中使用本机字节序；协议规定统一使用网络字节序（大端）。在常见的小端机器上，
  `0x12345678` 的内存顺序是 `78 56 34 12`，直接复制会把顺序发反。
- `#pragma pack(1)` 最多只能去掉填充，解决不了字节序问题，还会让内存布局依赖编译器扩展。

因此下面这种写法不可靠：

```cpp
std::memcpy(buf, &header, sizeof(header));  // 错：复制的是本机对象表示
```

**做法**
把线上布局当成协议契约，按规定偏移逐字段写入：`version` 写 `buf[0]`，`type` 写 `buf[1]`，
`streamId` 转为网络序后写 `buf[2..3]`，`seq` 写 `buf[4..7]`，`timestampMs` 写
`buf[8..11]`。解码时按相同偏移反向读取并转回本机字节序。

```cpp
buf[0] = header.version;
buf[1] = static_cast<uint8_t>(header.type);

const uint16_t streamId = htons(header.streamId);
const uint32_t seq = htonl(header.seq);
const uint32_t timestampMs = htonl(header.timestampMs);
std::memcpy(buf + 2, &streamId, sizeof(streamId));
std::memcpy(buf + 4, &seq, sizeof(seq));
std::memcpy(buf + 8, &timestampMs, sizeof(timestampMs));
```

这里禁止的是**一次复制整个结构体**；单个字段先完成字节序转换，再用 `memcpy` 写入固定偏移是安全的，
并且不会产生未对齐指针解引用的问题。`PACKET_HEADER_SIZE` 必须是协议明确规定的 12，不能写成
`sizeof(PacketHeader)`。

### 19. 组包缓存满了就淘汰最老的一条，会被"更老的迟到帧"反过来利用

**现象**
`FrameAssembler` 的残帧表按帧数封顶，满了就淘汰 `frameId` 最老的那一条。单元测试全绿，
局域网上也跑得好好的。但只要出现**超过整个窗口的乱序**——一个比表里所有帧都老的分片到达——
就会连着坏两件事：本来有希望收齐的帧被丢掉，而挤进来的那一帧又永远补不齐。

复现（容量 2，表里是还差一片的帧 5 和帧 6，此时帧 3 的第一片到达）：

```
after insert of old frame 3: pending=2 dropped=1
frame 3 completed? NO   tooLate=1  pending=2
```

**原因**
淘汰这个动作有个副作用：它要把**淘汰水位**推到被淘汰的那个 `frameId`，否则迟到的分片会把
已判死的帧重新建出来，占着容量等一个永远不会到齐的帧。于是形成了一个自食其果的顺序：

1. 帧 3 不在表里，表满了 → 淘汰最老的帧 5，水位推到 5；
2. 帧 3 插入成功；
3. 帧 3 的第二片到达 → 水位检查 `!seqNewerThan(3, 5)` → 判为迟到丢弃。

**帧 3 被自己刚才制造的水位挡在了外面。** 代价是帧 5 白丢了，帧 3 也没收上来，
而且帧 3 的条目还要占着容量直到它自己被淘汰——这期间 `retiredFrameId_` 还可能从 5 **倒退**回 3。

根子上是少问了一句：容量满的时候，**新来的这一帧配不配占这个位置**。无条件淘汰等于默认
"后到的一定比先到的新"，而这个前提在 UDP 上本来就不成立。

**做法**
淘汰之前先比一次，新来的必须比现有最老的还新，才有资格挤掉它：

```cpp
if (pending_.size() >= maxPendingFrames_) {
    const uint32_t oldestFrameId = oldestPendingFrameId();
    if (!seqNewerThan(dataHeader.frameId, oldestFrameId)) {
        ++stats_.packetsTooLate;   // 落后整个窗口, 收齐无望, 别挤掉还有希望的
        return Status::ok();
    }
    evictOldest();
}
```

改完之后同样的场景：`dropped=0`，帧 5 保住了，帧 3 被计为迟到。这条规则还顺带保证了
**水位单调**——只会淘汰比新来者更老的条目，`retiredFrameId_` 就再也不会倒退。

> 值得记下来的不是这个 bug 本身，而是**它为什么没被测出来**。22 条用例覆盖了乱序、重复、
> 重传、回绕、容量上限，唯独没有"新到的帧比表里所有帧都老"——因为写用例时脑子里的模型是
> "帧号大致递增，偶尔乱一点"。**测试只能覆盖你想得到的情况**，而这一条要等到 M4 上了 NACK
> 重传才会大量出现：重传的分片天然比当前在收的帧老得多，那时的现象是"一开重传帧率反而掉了"。
>
> 一般的教训：凡是**淘汰/驱逐**逻辑，都要单独问一句"被淘汰的一定该淘汰吗"。
> LRU、缓存、连接池都是同一类问题——按单一维度排序后取极值，很容易在极值那一端撞上
> 一个本不该参与排序的元素。

# 设计债 · 回头看才发现的

> 上面的「踩坑」是编译器/运行时**报错教我的**；这一节是**回头复盘才发现的**——
> 代码现在跑得好好的，但设计上欠了账，往后某个里程碑会来讨。
> 每条记：**症状**（怎么表现出来）、**机制**（为什么）、**打算怎么办**。
> 编号用 D 前缀，和踩坑的数字编号分开。

## D1. 热路径不能打日志，`peak()` 那种「计数 + 低频汇总」才是正解

**症状**
现在还没咬人。M3.4 一开始测端到端延迟就会咬：p99 莫名飙到几十毫秒，
查两天最后发现是自己的 `LOG_DEBUG`。

**机制**
`Logger::log()` 里有一把全局 `mutex`，且 stderr 无缓冲——**一条日志一次 `write(2)` 系统调用**。
1080p30、MTU 1200 下，一个 I 帧 100+ 分片，每秒几百到几千个包。每包一条日志
= 每秒几千次系统调用 + 几千次锁争用。

最毒的不是慢，是**测量工具进了被测路径**：日志本身成了延迟的一部分，
你测出来的数字不是系统的延迟，是"系统 + 你的日志"的延迟。

**以下位置一条 `LOG_DEBUG` 都不能有**：收包循环每个 UDP 包、`Packetizer` 每片、
`FrameAssembler` 每包插入、`BoundedQueue::push/pop`、`Decoder` 每次 send/receive、渲染每帧。

**打算怎么办**
照 `BoundedQueue::peak()` 的示范来：**热路径只累加计数器，由低频点每秒汇总打一条**。
队列自己不打日志，但把水位暴露出去让别人定期读——这个模式后面所有热路径模块都复用。

## D2. `LOG_TRACE` 并不是「零开销」，宏没有短路

**症状**
`Logger.h` 注释写着「TRACE/DEBUG 在 Release 模式下零开销(会在加锁前过滤)」。**不成立。**

**机制**
```cpp
#define LOG_TRACE(mod, ...) Logger::instance().log(LogLevel::TRACE, mod, __VA_ARGS__)
```
级别过滤确实在锁之前，但那是在 `log()` **函数体内**。C++ 的求值规则是
**实参在进入函数之前全部求值完毕**。所以：

```cpp
LOG_TRACE("decode", "frame %s", frame.debugString().c_str());
//                              ^^^^^^^^^^^^^^^^^^ 照样每帧执行
```
该构造的 string 构造了、该拼接的拼接了，送进 `log()`，`log()` 看一眼级别扔掉。
代价全付，收益为零。函数调用本身也没省——`log()` 是变参函数，编译器基本不会内联。

**打算怎么办**
宏自己短路：
```cpp
#define LOG_TRACE(mod, ...) \
    do { if (Logger::instance().enabled(LogLevel::TRACE)) \
             Logger::instance().log(LogLevel::TRACE, mod, __VA_ARGS__); } while (0)
```
但 `Logger` 现在**没有 `enabled()` 公开接口**（`level_` 是 private 且无 getter），
所以这个洞现在补不了，得先给 `Logger` 加接口。

## D3. 接收端不存在「反压」——阻塞式 `push` 压不住任何人，只压死自己

**症状**
直觉上「`push` 阻塞 = 不丢数据 = 安全」。在接收端这个直觉是**反的**。

**机制**
两点：

**① 阻塞不能消除丢包，只是把丢包搬到看不见的地方。**
收包线程堵在 `push` 上的那一刻，它就不再调 `recvfrom`。包继续到达，进内核
socket 接收缓冲区（`SO_RCVBUF`，Linux 默认约 200KB）。缓冲区满后内核**静默丢弃**
后续到达的包——程序里没有任何日志、任何返回值会告诉你，只有 `netstat -su`
的 `RcvbufErrors` 计数器在涨。

| | `tryPush` | 阻塞 `push` |
|---|---|---|
| 会不会丢 | 会 | **一样会** |
| 谁丢的 | 你的代码 | 内核 |
| 你知不知道 | 知道，可计数可上报 | 不知道 |
| 丢哪个 | 你说了算 | 内核说了算 |
| 丢之前先攒多久 | 立刻 | 先攒满 ~200KB ≈ 170 包 |

最后一行是低延迟项目的死穴：**那 200KB 是纯粹的隐藏延迟**。

**② 接收端压不住上游，因为上游是网络。**
发送端内部（采集 → 编码 → 发送）在同一个进程里，堵住编码线程，采集线程真会
慢下来——**那是真反压**。接收端队列的上游是网络，UDP 没有任何流控，
你堵住自己的收包线程，发送端完全不知道，照原速率发。

> **发送端的队列可以用阻塞传递压力；接收端的队列阻塞谁也压不住，只能压死自己。**

**③ 阻塞还会穿透全链**：渲染卡 → 队列B 满 → 解码堵在 push → 队列A 满 →
收包堵住 → 内核丢包。**一个环节打嗝，整条链锁死，最后在离病灶最远、最不可观测
的地方（内核）爆掉。**

推论（排查经验）：**堵塞从最下游开始向上游传播。你观测到的第一个满的队列，
通常是最靠上游的那个，而病灶在最下游。**

**打算怎么办**
接收端两个队列的策略在 M3.3/M3.5 定，但底线是：**满了必须由我自己丢，不能推给内核。**

## D4. 队列容量就是延迟预算

**症状**
「队列满了？把 cap 调大点」——这个反应在低延迟项目里是错的。

**机制**
稳态下生产速率 == 消费速率，因为**源是整条链的节拍器**：发送端 30fps 采集，
解码器不可能凭空造出更多帧。所以队列长期堆积**不是速率差造成的**，是
**突发和卡顿**造成的（`JitterBuffer` 一次放行多帧、vsync 阻塞、拖窗口、WSLg 抽风）。

而如果生产速率真的长期大于消费速率，**任何有限容量都会满**，加大 cap 只是推迟爆炸，
期间队列里堆的每一帧都在等：

> **cap = 30 @ 30fps = 整整 1 秒的潜在延迟。**

**打算怎么办**
**容量的作用是吸收抖动，不是吸收速率差。** 速率差吸收不了，只能丢。
现在 `--cap` / `--send-cap` 默认 4（4 帧 @ 30fps ≈ 133ms 上限）不是随手写的。
以后每定一个队列容量，都要把「这是多少毫秒延迟预算」的算式写进文档。

## D5. `BoundedQueue<T>` 永远做不到「保 IDR 丢 P 帧」

**症状**
`tryPush` 的原注释写着「给背压策略用：发送队列满时上层需要主动丢包(**保 IDR 丢非关键帧**)」。
**这个策略 `BoundedQueue` 执行不了。**

**机制**
它是模板，**不知道 `T` 是什么**。看不到帧类型、看不到 `DataHeader::FLAG_KEYFRAME`、
看不到 `frameId`。它能提供的驱逐策略只有**按位置选**：拒队尾（`tryPush`，丢最新）
或弹队首（丢最老）——仅此两种。

而「按位置选」在 H.264 上有毒：**丢掉的那帧如果是 IDR，后面所有依赖它的 P 帧全部
花屏，一路花到下一个 IDR（默认 GOP = fps = 30 帧 = 整整 1 秒）。**
丢一帧的代价不是丢一帧，是丢一秒。这跟丢最新完全不同——最新那帧还没有任何帧依赖它。

这跟本文档**第 19 条**（`FrameAssembler` 淘汰最老被迟到帧反向利用）是**同一个形状，
第二次出现**：按单一维度排序取极值，在极值那一端撞上了本不该参与排序的元素。
这次那个元素叫 IDR。

**打算怎么办**
> **驱逐决策必须由知道 payload 语义的那一层做，泛型容器只能提供原语。**

具体接口 M3.3 再定。两个候选：`forcePush` 接受谓词（但在锁内调用户代码有风险），
或队列改为暴露「带锁的批量操作」原语。

## D6. 「调用方自己 pop 再 push」不行，理由是原子性不是封装

**症状**
想「队满丢最老的」，最省事的写法是调用方自己来：

```cpp
if (q.size() >= q.capacity()) { T old; q.pop(old); q.push(std::move(frame)); }
```

**机制**
三步之间锁全放开，不是原子的：

- **观测→pop 之间**消费者取走一个 → 队列已经不满了，**你白丢一帧**
- **pop 时队列恰好空了** → `pop()` 在队空时**阻塞** → 生产者挂在这儿死等。
  这不是效率问题，是**死锁路径**
- **pop→push 之间队列被 `close()`** → `push` 返回 false → **一次丢两帧**
  （弹出来的那个也回不去了）

**打算怎么办**
> 判断一个操作该不该进容器，标准是**「它需不需要在一把锁里完成」**，
> 不是「谁该碰谁不该碰」。

## D7. `Status` 带 `std::string`，错误路径在热路径上会 `malloc`

**症状**
`Status` 注释保证「Ok 路径零堆分配」——只保证了 Ok 路径。**错误路径没人管。**

**机制**
```cpp
Status::error(Code::Timeout, "poll timeout on fd 3");  // 20 字符
```
libstdc++ 的 `std::string` **SSO 容量 15 字节**。20 > 15 → **每次一个 `malloc`，
析构一个 `free`**。而 poll 超时是收包循环的**常态事件**。

危害不是「平均慢」（每秒几百次 malloc 绝对值不大），是
**`malloc` 偶尔触发 arena 扩展甚至 `brk`/`mmap` 系统调用，一下几十微秒到几毫秒的
毛刺，正好打在 p99 上**。低延迟系统的敌人从来不是平均慢，是**尾部抖动**。

更根本的是设计味道：**`Timeout` 是预期内的常态，不是错误。**
用错误通道表达常态事件本身就错了。这和 D1 是同一类问题的两面——
**热路径上不要为不需要人读的事件生产给人读的字符串。**

**打算怎么办**
`poll` 超时改走正常返回路径（enum / bool / `optional`），不构造带 message 的 `Status`。

## D8. 配置的默认值没有单一真相源

**症状**
M3 加 `--render` / `--jitter-ms` / `--latency-report`，要改**三处，一处都不能漏**：
`isSupportedOption` + `printUsage` + 调用点。
漏了 `isSupportedOption` → 运行时报 `Unknown option`（而参数明明是对的）；
漏了 `printUsage` → 用户永远发现不了这个参数存在。

**机制**
同一件事被**四份互相独立、手工维护**的东西描述着：

| # | 真相源 | 位置 |
|---|---|---|
| 1 | `isSupportedOption()` 的一长串 `\|\|` | `Config.cpp:23` |
| 2 | `printUsage()` 手写的帮助文本 | `Config.cpp:184` |
| 3 | 各 `main.cpp` 里 `get(key, 默认值)` | 散落 20+ 处 |
| 4 | 用户的配置文件 | 运行时 |

现在就能看到的后果：

- **同一个默认值抄了 4 遍**：`get("log-level", "info")` 出现在
  `sender/main.cpp:66`、`receiver/main.cpp:55`、`server/main.cpp:10` 和 `:14`。
  想把默认级别改成 `warn` 要改 5 处（含 `printUsage`），漏一处就不一致，
  **没有任何测试会发现**。
- **同一个 key 两个默认值**：`getInt("frames", 100)`（sender）vs
  `getInt("frames", 0)`（receiver）。这次是故意的，但**编译器无法区分
  「故意的不同」和「手滑写错」**。
- **`--help` 说的和代码干的无关联**：`printUsage` 里的默认值是手打的字符串，
  跟 `get()` 的第二个参数之间没有任何机制保证一致，纯靠人肉维护。
- **一个 usage 服务三个二进制**：`printUsage` 字面写着 `Usage: lowlat_<app>`，
  于是 `lowlat_receiver --help` 会打印 `--device` `--bitrate` `--gop`
  ——接收端根本不用的参数。
- **分层反了**：`Config` 在 `common/`，是最底层通用模块，却硬编码了
  `--device` `--bitrate` `--gop` `--fps` 这些采集/编码概念。**底层认识了上层**，
  加个新模块就得回头改 `common`。

**打算怎么办**
让「参数名 + 默认值 + 帮助文本 + 归属哪个 app」这四件事**只写一遍**。
**方案（M3 复盘时定的）**：把 `Config` 改成**注册式**，提供 `registerOption(key, default, help)`，
由**各模块 / 各 app 自己注册**自己的参数，`Config` 只保管这张注册表。

一次改动解决上面全部五个症状：

- `isSupportedOption` 不用写了——注册表里有的就是合法的
- `printUsage` 不用手写了——遍历注册表生成
- `Usage: lowlat_<app>` 的 `<app>` 问题自动消失——每个 app 只注册自己的参数，
  `lowlat_receiver --help` 再也不会打印 `--bitrate`
- 分层反转修好了——`common/Config` 不再认识 `--device`，是 capture 模块自己去注册
- 默认值只写一遍——`get()` 不再需要第二个参数

前提：**调用方必须注册，否则 Config 不知道这个参数存在**。这不是缺陷，这正是机制
生效的方式——"四份真相源"收敛成"一份注册表"，即 single source of truth。

**M3 之后再动手**，现在改会波及三个 `main.cpp`。

## D9. `PacketHeader::timestampMs` 会回绕，但注释没写

**症状**
```cpp
uint32_t timestampMs = 0;   // 采集时刻(毫秒)，从 RawFrame::captureMs 透传
```
`steadyNowMs()` 返回 `uint64_t`，这里截成 `uint32_t` —— **约 49.7 天回绕**。
`CLOCK_MONOTONIC` 的起点是开机时刻，所以开机超过 49 天的机器上会绕回去。

**机制**
跟同结构体里的 `seq` 是同一个问题。`seq` 旁边已经写了
「比较大小必须用有符号差值 `int32_t(a - b) > 0`」，`timestampMs` 同理，
但注释漏了——M3.4 算延迟做减法时，回绕点会算出一个巨大的正数。

**打算怎么办**
M3.4 写延迟统计时补注释 + 用有符号差值做减法。

## D10. 端到端延迟：端点定义、测不到的那一段、以及为什么只做本地回环

**症状**
「端到端延迟 45ms」这句话本身**没有信息量**——别人没法判断它是不是在骗人。
两个端点定在哪、哪一段测不到、时钟可不可信，都不说清楚，数字就不可信。

### 端点定义（M3.4 报告里必须写这两行）

- **起点 = 采集那一刻**，即 `RawFrame::captureMs`。
  不是编码开始，不是打包时刻——`Encoder.h:50` 和 `Packetizer.h:38` 都特意注释了
  「**不在这里重新取时间**，一路透传」，就是为了这个。重新取就少算了编码耗时，
  而编码耗时**正是要测的东西之一**。
- **终点 = `SDL_RenderPresent()` 返回那一刻**。

### 测不到的那一段，只能声明，不能解决

`RenderPresent()` 返回之后，像素**真正亮起来**还要等一个 vsync，60Hz 下最多 16.7ms。
**这一段任何用户态程序都测不到**，不是本项目的能力问题。

所以正解不是"想办法测到"，而是在报告里写死一句：

> 本数字不含最后一次 vsync 等待（≤16.7ms @60Hz）。

**一个说清楚了边界的数字是可信的；一个没说清边界的数字比没有数字更糟。**

### 为什么 M3 只做本地回环，跨机器推到 M6

`Clock.h` 的 `steadyNowMs()` 用 `steady_clock`（`CLOCK_MONOTONIC`），
注释已经写明**跨机器不可比**。但 M3.4 要测的就是端到端——直接冲突。

**M3 的解法：收发两端跑在同一台机器上（回环 UDP）。** 两个进程共享同一个
`CLOCK_MONOTONIC`，`steadyNowMs()` 直接相减就是真实延迟。零偏移、零漂移、零假设。

跨机器要处理三件事，每一件都会往数字里掺不确定性：

1. **偏移本身没法直接测**。两台机器各读一次表相减，得到的是
   `offset + 单程延迟`——两个未知数一个方程。标准解法是 NTP 式四时间戳往返
   `offset ≈ ((t2-t1) + (t3-t4)) / 2`，**但它的前提是去程延迟 == 回程延迟**。
   而本项目的主题是**弱网**，弱网下路径不对称正是最先失效的假设——
   **测量工具在最需要它的场景下最不准。**
2. **偏移会漂**。两台机晶振频率差典型 10~100 ppm，100ppm = 每小时漂 360ms。
   "测一次一直减"不成立。
3. **`CLOCK_MONOTONIC` 跨机器连"偏移"的概念都没有**。它的起点是**开机时刻**，
   两台机开机时间可能差几天。而且 Linux 上它在**系统挂起期间停止计数**
   （WSL2 尤其容易碰到宿主机休眠）——所以偏移不仅漂，还会**跳变**。

**一般的工程判断（这条比结论本身重要）：**

> **先在最强的假设下拿到一个完全可信的数字，再逐步放宽假设。**
> 反过来做（一上来就想解决最一般的情况），你会得到一个数字，但不知道它对不对——
> 那比没有数字更糟。

对应本项目文档里自己写的原则：**先能出画面，再谈延迟好看。**

**打算怎么办**
M3.4 只报本地回环数字 + 两行边界声明。跨机器时钟同步留到 M6 压测，届时单开一条。

## D11. 接收端两个队列的丢弃策略：一个泄压阀，一个保险丝

**症状**
M3 接收端是 `收包 →[队列A]→ 解码 →[队列B]→ 渲染`。两个队列满了都得丢，
但**丢法完全不同**——一开始很容易以为"都用同一套就行"，那是错的。

### 先搞清楚：编码帧的依赖链长什么样

`Encoder.cpp` 里 `max_b_frames = 0` + `tune=zerolatency` + `gop_size = fps`，
所以码流是一条**单向依赖链**：

```
IDR ← P ← P ← ... ← P ← IDR ← P ← ...
      └─ 每个 P 解码时都要前一帧的解码结果 ─┘
       1 个 IDR + 29 个 P，然后下一个 IDR
```

**推论：丢链条中任何一环，它后面的全部花屏，一路花到下一个 IDR。**

所以在编码帧队列里，"保住 IDR"**远远不够**——P 帧和 IDR 一样丢不得，
区别只是丢 IDR 坏得更彻底。可以安全丢弃的只有两种帧：

> **没有任何后续帧引用它的帧** = 队尾（最新帧）+ IDR 的前一帧
> （IDR = Instantaneous Decoder Refresh，定义上就会清空参考帧缓冲，
> 所以 IDR 之后的帧在语法层面不可能引用 IDR 之前的东西）

而单帧粒度上，**"不花屏"和"降延迟"是互斥的**：

| 丢哪个 | 花屏 | 降延迟 |
|---|---|---|
| 队尾（最新） | 否 | **否**（老帧还堵在前面） |
| 队首（最老） | **是** | 是 |
| 中间任意一帧 | **是** | 是 |

"丢 IDR 的前一帧"是唯一两全的，但算一下命中率：GOP=30、cap=4，
**队列里根本没有 IDR 的概率约 87%**，还要求它不在队首——
**大约 10% 的时候能用上**。正确但几乎不适用。**单帧粒度这条路是死的。**

### 结论：两个队列，两套策略

| | 装什么 | 满了怎么办 | 代价 | 定位 |
|---|---|---|---|---|
| **队列 B** | 解码后的裸帧 | `forcePush` 丢最老 | 画面跳一帧 | **主泄压阀**，可随便触发 |
| **队列 A** | 编码帧 | **清空 + `JitterBuffer::reset()` 回到等 IDR 状态** | 冻结 ≤1 秒 | **保险丝**，几乎不该触发 |

**队列 B 为什么便宜**：解码之后帧间依赖就消失了，每帧都是完整图像，
`isKey` 这个概念在队列 B 里根本不存在。丢一帧就是丢一帧。

**队列 A 为什么是"清空"而不是"丢一帧"**：既然单帧粒度没有好答案，就把粒度放大——
**整条链一起扔，等下一个干净的起点**。这个机制 `JitterBuffer` 里**已经有了**
（`startOnKeyFrame` / `reset()` / `droppedBeforeStart`，注释原话："起播前丢弃是正常的
一次性代价"），直接复用，不用新写。

> 这个做法在工业界有名字：**drop to next keyframe**，WebRTC 就是这么干的。

### 最要紧的一条：保险丝只有在"极少烧"的前提下才成立

清空的代价是**平均 0.5 秒、最多 1 秒的画面冻结**（清空时刻随机，期望等半个 GOP）。
如果队列 A 频繁满 → 每一两秒冻结半秒 → 画面根本不能看。
而且此时**丢帧不是解药**：反复满说明解码器是真跟不上，清空只让它少解几帧，下一秒照样满。

**所以必须保证队列 A 几乎不满。而队列 A 满的最常见原因不是解码慢，
是解码线程堵在队列 B 的 `push` 上**（见 D3 的穿透链）。

> **把队列 B 设计对（`forcePush` 让解码线程永不阻塞），队列 A 这根昂贵的保险丝就基本不会烧。**
> 反过来，队列 B 用阻塞 `push`，等于把丢弃从"代价 = 1 帧"的地方推到"代价 = 30 帧"的地方。

### 两个后续旋钮（M3 不做，但要知道存在）

- **M4 的 PLI（Picture Loss Indication）**：清空后立刻向发送端要一个 IDR，
  冻结时间从"最多 1 秒"压到"一个 RTT + 编码一帧"≈ 几十毫秒。
  这才是完整解法。**M3 做不了——没有反向控制通道，M4 才有。**
- **`gop` 参数本身**：默认 30（1 秒）对低延迟项目偏大。调小 → 冻结更短、丢包恢复更快；
  代价是码率上升（IDR 通常是 P 帧的几倍到十几倍大）。**可量化的取舍，M6 压测的好素材。**

**打算怎么办**
M3.3 定 `forcePush` 的接口（见 D5、D6），M3.5 把两套策略接进管线。

## D12. `reset()` 不能拿来处理「队列满」——两种场景清的东西完全不同

**症状**
D11 定的策略是「队列 A 满 → 清空 + 让 JitterBuffer 回到等 IDR 状态」。
最省事的写法是直接调现成的 `JitterBuffer::reset()`。**这是误用**，会引出两个隐蔽故障。

**机制**
`reset()` 是给**重连**设计的——对端换了、流从头开始，**所有历史都无效**，六组状态全清：

```cpp
pending_                       待播帧
refFrameId_ / refExtended_     帧号扩展锚点
minOffsetMs_ / hasOffset_      时钟映射
lastOutExtended_ / hasOutput_  交付水位（"已经交付到第几帧了"，防倒退的闸）
started_                       起播门（"等到第一个 IDR 之前什么都不放"）
stats_                         计数器
```

而「队列 A 满」是完全不同的情况：**流没变，还是同一条，只是我暂时消化不动了。**

### 只有两组该动

```cpp
pending_.clear();     // 这一段确实不要了
started_ = false;     // 下游丢了帧，必须等下一个 IDR 重新开始
// 其余四组：全留
```

`started_` 为什么必须清：队列 A 里那些帧**已经离开 JitterBuffer 了**，是在下游被丢的。
解码器解到帧 496，497–500 在队列 A 里被清掉，接下来帧 501 引用 500——
解码器没见过它，**照样花屏**。所以必须从下一个 IDR 重来。

### 时钟映射为什么必须留

`minOffset = C + T_min` 估的是**链路下限**。队列 A 满说明的是"我消化不动"，
**不是"链路变了"**——链路没变，凭什么把它扔了？

而且清掉之后，重新锚定用的是**系统正卡着**的时候到的那一帧，`T` 很大 →
新 `minOffset` 偏大 → `playAt` 整体后移 → **每帧都多等**。
这正是 `computePlayAt` 注释里那个「基准偏晚」的失效模式：
**清掉反而让交付变晚，跟想要的效果相反。**

### 帧号锚点和交付水位是绑死的：三种组合，只有一种对

这两个值活在**同一个坐标系**里：锚点管"编号从哪起算"，水位管"旧编号走到哪了"。

| 锚点 | 水位 | 后果 |
|---|---|---|
| 清 | 清 | 防倒退的闸整个没了。网络上还在飞的**老 IDR** 到达时无人拦截，被当成新起点——**往回倒带**（GOP=30 时可倒 0.67 秒），延迟不降反升，队列很快又满 → **reset 正反馈循环** |
| 清 | 留 | **尺子换了，刻度没换**。回绕时永久卡死，见下面的推演 |
| **留** | **留** | ✅ 编号连续、闸门有效、回绕由有符号差值正确处理 |

**「清锚点留水位」为什么会卡死**——设回绕前已交付到 `lastOutExtended_ = 4294967290`，
下一帧 `frameId = 5`：

```
保留锚点：int32_t(5 - 4294967290) = 11  →  refExtended_ += 11  →  4294967301
          4294967301 > 4294967290  →  新帧，接受 ✅

清掉锚点：hasRef_ == false  →  refExtended_ = frameId = 5，直接返回 5
          5 < 4294967290  →  判为"太晚"  →  丢
          后续 6、7、8…… 永远小于 4294967290  →  全丢  →  永久卡死 ❌
```

**做法**
`JitterBuffer` 上新开一个方法 **`dropUntilKeyFrame()`**，只做那两件事，其余四组不碰。

**归属**：放在 `JitterBuffer` 上，由**收包线程**调用。这里严丝合缝——
队列 A 满是收包线程发现的（它是队列 A 的生产者），而 `JitterBuffer`
**本来就挂在收包线程上独占**，所以是同线程调用，一把锁都不用加。
（header 里"挂在收包线程"那个决定，到这里又验证了一次。）

**命名的判据**（比这个名字本身更有用）：

> **好名字说的是「调用之后我保证什么」，不是「我做了什么动作」。**

先把"保证"写成句子，名字自己会浮出来：

```
reset()              → 调用之后，对象回到刚构造的状态，所有历史作废。
dropUntilKeyFrame()  → 调用之后，下一个交付出去的帧一定是关键帧；
                       其余一切不变：同一条流、编号连续、时钟映射还在、统计继续累加。
```

一开始起的名字叫 `restart()`——被否掉是因为 `reset()` / `restart()` 摆在一起
**看不出任何区别**，而它们在四组状态上行为**完全相反**，是最容易用错的那种 API。
最终选 `dropUntilKeyFrame` 而不是更贴切的 `requireKeyFrame`，理由是：
**这个操作很贵（平均冻结 0.5 秒），名字里带个 `drop` 能让人写下这行调用时犹豫一下。
贵的操作，名字就该难听一点。**

**名字防不住所有误用，注释再上一道保险**——在 `reset()` 的文档注释里加交叉引用：
「队列满 / 下游丢帧不要用这个，用 `dropUntilKeyFrame()`；这里清掉的时钟映射和
交付水位在那个场景下必须保留，清了会导致往回倒带和回绕死锁。」

## D13. 「预算」和「上限」是两种数，混了会去改一堆不该改的参数

**症状**
把 JitterBuffer 的参数摆一起看，很容易吓一跳：

| 位置 | 容量 | 换算 @30fps |
|---|---|---|
| `targetDelayMs` | 50ms | 50ms |
| `maxFrames`(软上限) | 16 帧 | 533ms |
| `hardLimitFrames`(硬上限) | 32 帧 | 1067ms |
| 队列 A `--cap` | 4 帧 | 133ms |

"我配的是 50ms 水位，怎么这条链能存一秒多？"——然后就想去把 `targetDelayMs`
调大到跟 `maxFrames` "匹配"。**这是范畴错误。**

**机制**

这几个数描述的**不是同一种东西**：

| | `targetDelayMs = 50` | `maxFrames = 16` |
|---|---|---|
| 是什么 | **正常运行时每帧等多久** | **多久之后承认"出事了"** |
| 多久触发一次 | **每一帧** | **正常永不触发** |
| 类比 | 每个月的房租 | 银行卡的透支上限 |

正常跑着的时候 `pending_` 里根本攒不到 16 帧：

```
每帧在 pending_ 里最多待 targetDelayMs = 50ms
30fps 每 33ms 来一帧
→ 稳态常驻 50 / 33 ≈ 1.5 帧，上限 16 帧 = 十倍余量
```

要攒到 16 帧，`pop()` 得停止调用 533ms——那不是"缓冲变深"，是**消费端失速**。

> **`maxFrames` 不是缓冲大小，是失速探测器。**
> 问它该不该和水位匹配，就像问灭火器容量该不该和自来水管流量匹配。

### 把水位调到 500ms 会自我否定

真算一下：500ms 水位、30fps → 稳态 `pending_` 常驻 `500 / 33.3 ≈ 15 帧`，
而 `maxFrames = 16`。**软上限从"永不触发的保险"变成"每帧都在触发的常态"**，
每帧刚进来就被标成"立刻到期"强制放行，`framesForcedEarly` 疯涨，
**那 500ms 的水位一秒都兜不住，等于没设。** 想让两个数字"匹配"，
结果恰好让它们互相抵消。

### 正确的读法

| 位置 | 性质 |
|---|---|
| `targetDelayMs` | **预算**——每一帧都要付 |
| `maxFrames` / `hardLimitFrames` | **上限**——出事后的处置阈值，正常恒为 0 |
| 队列 A / B | **交接窗口**——正常应接近空，**有货就是病征** |

> **正常运行时的实际延迟 ≈ 水位 + 各级排队(≈0)。
> 那一秒多是"保证不会超过"，不是"每次都要花"。**

**做法**
遇到一个容量参数，先问它属于哪一类：**我每次都花，还是我保证不超过？**
两类数不该互相"对齐"，对齐了通常意味着上限那一侧失效了。

### 附：水位到底该设多少

不是感觉出来的，是**测**出来的：`水位 ≈ 该链路网络抖动的 p95/p99`。

- 本地回环：抖动几乎为 0，50ms 已经很奢侈
- 局域网：几毫秒
- 公网 / 弱网：几十到上百毫秒且会变 → 所以 M4 要做**自适应水位**

而且这是 **1:1 兑换，没有免费午餐**：**水位每加 1ms，端到端延迟就加 1ms**，
换来的是多兜住 1ms 抖动。500ms 是点播 / HLS 的量级；WebRTC 这类实时系统的
自适应 jitter buffer 通常跑在 **20~100ms**。本项目立意是"面向弱网的**低延迟**"，
水位一上 500ms，README 第一行就不成立了。

**M3.4 给测延迟的工具，M6 压测给抖动分布。在有数据之前，50ms 是合理起点——
而不是一个该凭感觉调的数。**

## D14. 静默的元信息丢失，会以「p99 = 3 天」的形式出现在报告里

**症状**
`Decoder::drainFrames()` 里，元信息靠 pts 从 `pending_` 取回来：

```cpp
RawFrame decoded;                       // captureMs 默认 = 0
copyToRawFrame(frame_, decoded);        // 只填像素，不碰 captureMs
if (pending != pending_.end()) {
    decoded.captureMs = pending->second.captureMs;
    decoded.frameId   = pending->second.frameId;
}
out.push_back(std::move(decoded));      // ← 取不到就带着 captureMs = 0 交出去
++stats_.framesOut;
```

**取不到就什么都不做**——帧照常交付、`framesOut` 照常 +1、四个计数器一个都不动。
而 M3.4 这么算延迟：

```cpp
latency = steadyNowMs() - frame.captureMs;
```

`steadyNowMs()` 是**开机以来**的毫秒数。一台开机 3 天的机器 → 这一帧算出
**259,200,000 ms ≈ 3 天**的延迟。

### `pending_` 是什么：一张穿过第三方库的寄存单

FFmpeg 的数据结构里**根本没有 `captureMs` / `frameId` 这两个字段**，
而 `decode()` 又不保证一进一出，不能用"刚送进去那一帧"来配对。
**唯一能穿过 FFmpeg 走一个来回的东西是 `pts`**：

```
寄存：pending_[pts] = {captureMs, frameId}
送进：send_packet(pkt->pts = pts)   ↓ FFmpeg（不认识 captureMs）
取件：receive_frame() → frame->pts  →  pending_.find(pts)
```

`Encoder::pending_` 是同一个模式、同一个理由。

**做法**

### 三种手段，各管一件事，别混

| | 加在哪 | 回答什么 | 本例用不用 |
|---|---|---|---|
| **哨兵** | 复用已有的不可能值 | 「这一笔数据可不可信」 | ✅ `captureMs == 0` |
| **计数器** | `DecoderStats` | 「总共发生了多少次」 | ✅ `framesMissingMeta` |
| **新字段** | `RawFrame` 每帧带着走 | 「这一帧可不可信」 | ❌ 不需要 |

**为什么不加字段**：`captureMs == 0` 是**永远不会合法出现**的值（它来自
`steadyNowMs()`，要合法为 0 得在开机后第一毫秒内采到帧），**它本身就是哨兵**。
而 `RawFrame` 是每帧都在队列上流动的结构，加一个 bool 会让每个用到它的地方
都得考虑这个字段的含义。

> **能用已有的不变量表达，就别加新状态。**

**结论**：帧照常交出去（画面是好的，丢了反而少 33ms 内容），统计靠哨兵跳过，
次数靠计数器记账。三件事各归各位，互不影响。

**丢掉的 `frameId` 不影响正确性**：排序早在 `JitterBuffer` 就做完了
（"交付顺序严格递增，绝不回头"），之后队列 A → 解码 → 队列 B → 渲染全是 FIFO，
**没有任何一环再读 `frameId`**。它在下游只是调试标签。

### 附：为什么延迟报告用分位数而不是平均值

1000 帧里混进 **1 帧**脏数据（259,200,000ms）：

| 指标 | 怎么算 | 被毁了吗 |
|---|---|---|
| p50 / p95 / p99 | 排序后取第 500 / 950 / 990 位 | **没有**——离群值排在第 1000 位，够不着 |
| 平均值 mean | 全部相加 ÷ n | **彻底毁了**，凭空多出 259,200ms |
| max | 取最大 | **彻底毁了** |

> **分位数按排名取值，对离群值天然免疫；平均值把所有值加起来，一个离群值就能带偏。**

但免疫是**有条件的**：1000 帧坏 1 帧 p99 没事，坏 **11 帧**（超过 1%）p99 就开始
被污染。**而"到底坏了几帧"只有计数器能回答**——所以哨兵和计数器缺一不可。

### 通用原则

> **静默处理异常，是把「偶发故障」变成「整个功能不工作，且没有任何线索」。**

之所以敢丢/敢忽略，靠的是"它很少发生"这个假设；而静默处理恰恰**放弃了验证这个
假设的唯一机会**。万一它不是罕见而是每帧都发生（比如某个 FFmpeg 版本的 pts 行为
和预期不同），你会看到黑屏，然后去查网络、查队列、查渲染器——**唯独查不到这里**。

配合 D1：**热路径上不打日志，但一定要留计数器。**

## D15. 一条流水线只该有一个节拍器

**症状**
M3.3 第一个要做的决定：渲染线程被什么驱动？

- **队列驱动**：`pop` 阻塞，来一帧画一帧
- **时钟驱动**：每 33ms 醒一次，取最新的画

直觉容易选时钟驱动——"这样两帧之间才是固定时间差"。**这个前提是错的。**

**机制**

### 帧到渲染器手上时，节奏**已经是齐的**

`JitterBuffer::pop()` 不是"有货就给"，是**按 `playAt` 时刻给**：

```
playAt = ts + minOffset + delay
         ↑
    ts 是采集时刻，30fps 下每帧相差 33ms
    minOffset 和 delay 对每帧都一样
→ playAt 之间也正好相差 33ms
```

> **`JitterBuffer` 的整个存在意义就是"按时放行"——它已经是节拍器了。**

### 再加一个时钟，两个钟会打架

- `JitterBuffer` 按**发送端时间轴**放行（跟着 `ts` 走）
- 33ms 定时器按**本地时钟**取

两台机器的晶振有频差（典型 10~100 ppm），这两个节奏**永远不会完全一致**。
慢慢地一个比另一个快：

| 谁快 | 后果 | 现象 |
|---|---|---|
| 定时器快 | 队列 B 反复取空 | **周期性卡顿** |
| 定时器慢 | 队列 B 持续堆积 | 延迟越滚越大，最后触发丢帧 |

**表现是每隔几十秒画面顿挫一下**，而且会去查网络、查解码——查不到，
因为病根是**两个时钟在对抗**，不在任何单个模块里。

### 时钟驱动还白送一笔延迟

"刚取完的下一瞬间来了新帧，也得等一整帧才会再取"——
**平均白送半个周期 = 16.7ms，最坏 33ms**。对一个卖点是低延迟的项目，纯亏。

**做法**
**选队列驱动。** 渲染器的活是"到了就画"，不是"自己数拍子"。

> **一条流水线上只该有一个节拍器。这里已经有了（源 → JitterBuffer），
> 下游每一级都只该被上游驱动。**

### 但队列驱动引出一个新问题（这就是 M3.3 Q2）

渲染线程堵在 `pop()` 上等帧时，**没人去调 `SDL_PollEvent`**：
关窗口点不掉，窗口管理器判定程序无响应，标题栏变灰。

而 `BoundedQueue` 给不了出路——它只有：

```cpp
bool push(T);       bool tryPush(T);
bool pop(T& out);   // ← 只有这一个，无限阻塞
void close();
```

**没有 `tryPop()`，没有带超时的 `popFor()`。**
这是继 D5（做不到"保 IDR"）、D6（pop+push 不原子）之后，
`BoundedQueue` 的**第三个 API 缺口**——三个缺口都出现在"队列要配合一个
它不了解的外部约束"的时候。

真正的难点是：**主线程只有一个，却要同时等两个互不相干的事件源**——
队列 B 来的帧（自己线程 notify 的）和窗口系统来的事件（socket 上来的）。
方案在 M3.3 定。

## D16. 一个线程等两个事件源；以及"多出来的复杂度换到了什么"

**症状**
M3.3 选了队列驱动（D15）之后，渲染线程堵在 `pop()` 上等帧时没人泵 SDL 事件，
窗口点不掉。真正的难点是：

> **主线程只有一个，却要同时等两个互不相干的事件源** ——
> 队列 B 来的帧（自己线程 `notify` 的）和窗口系统来的事件（socket 上来的）。

**机制**

### 纠正一：带超时的等待**不增加**帧延迟

```cpp
notEmpty_.wait_for(lk, 5ms, [this]{ return !q_.empty() || closed_; });
```

帧在第 1ms 到 → **第 1ms 立刻返回**（`notify_one` 把它叫醒）；帧不来 → 第 5ms 超时返回。

> **超时是"最多等多久"的上限，不是"必须等多久"的下限。**

所以 `popFor(5ms)` 对**帧**是零额外延迟。那 5ms 只影响**事件响应**
（队列一直空时，关窗口最多 5ms 后被处理）——人眼完全无感。

### 纠正二：SDL 的事件队列已经是那个队列，别重造

想自己建一个事件队列 + 用继承区分两种事件 + 上条件锁——**三样 SDL 都有了**：

| 打算自己做 | SDL 已经有 |
|---|---|
| 建事件队列 | SDL 内部的事件队列 |
| 继承 / 多态区分事件类型 | `SDL_Event` 是 **union**，`e.type` 就是区分依据 |
| 条件锁，没事件就睡 | `SDL_WaitEvent()` 内部就是阻塞等待 |

**`SDL_Event` 是 union 不是继承体系**——C 没有继承，它用"一个 `type` 字段 +
union"来表达"多种事件共用一块内存"。`SDL_PushEvent` 是**线程安全**的，
`SDL_RegisterEvents(1)` 可以申请自定义事件类型。

### 三个方案对账

| | 帧延迟 | 事件响应 | 空转 | 要给 `BoundedQueue` 加 |
|---|---|---|---|---|
| 1. 轮询 `tryPop` + 睡 2ms | +0~2ms | 0~2ms | 500 次/秒 | `tryPop` |
| **2. `popFor(5ms)`** | **+0** | 0~5ms | 200 次/秒 | `popFor` |
| 3. `SDL_PushEvent` 唤醒 | +0 | +0 | 0 | `tryPop` |

方案 3 要多付的：一个自定义事件类型、`SDL_PushEvent` 满了（SDL2 上限 65535）
返回负数的处理、以及**所有权穿过 `void*`** 的风险——
`SDL_Event` 是固定大小 union，装不下一帧，只能把指针塞进 `e.user.data1`，
`unique_ptr` 在那一刻放手。中途任何提前退出（窗口先关、`SDL_FlushEvents`
清空队列、`PushEvent` 失败）**都是静默泄漏**。

**做法**
**选方案 2。**

```
主线程 = 渲染线程，一个线程干三件事：

  for (;;) {
      RawFrame f;
      if (queueB.popFor(f, 5ms)) {      // 帧一到立刻返回，零额外延迟
          upload(f); present();
      }
      while (SDL_PollEvent(&e)) { ... } // 不管有没有帧，都泵一轮事件
  }

SDL_Init / CreateWindow / CreateRenderer / RenderPresent / PollEvent
全在主线程——符合 SDL 的线程契约。解码线程只往队列 B push，不碰 SDL。
```

### 通用判据（比这个结论本身更有用）

> **这多出来的复杂度，换到了什么能被人感知的东西？**

方案 3 换到的是"事件响应快 5ms"和"省 200 次/秒空转"——**人感觉不到，
CPU 也感觉不到**；付出的是自定义事件类型 + 失败处理 + 泄漏风险。**这笔交易亏。**

工程里大部分"更优雅的方案"都死在这一问上。

## D17. 停止信号往上游传时，标志位不够；阻塞中的线程听不见

**症状**
接收端三条线程：收包 → 队列 A → 解码 → 队列 B → 渲染。
加了 `stopping_` 标志，每条循环顶部都查，看着很对称、很干净。
然后用户点了窗口的 ×，**进程挂死在 `join()` 上，一动不动，没有任何错误信息。**

**机制**

停止信号在流水线上有两个传播方向，麻烦程度完全不同。

**自上而下**（Ctrl-C / `maxFrames` 收满 / `idleTimeout` 空闲）——
收包线程先停 → `close(队列A)` → 解码取空后退出 → `close(队列B)` → 渲染取空后退出。
**链式的，每一级自然唤醒下一级**，写起来几乎不用想。

**自下而上**（窗口关闭）—— 只有渲染线程的 `pumpEvents()` 看得见 `SDL_QUIT`，
而这时候另外两条线程很可能是这个状态：

```text
解码线程:  堵在 queueB.push()    <- 没人取了, 队列 B 满
收包线程:  堵在 queueA.push()    <- 解码停了, 队列 A 也满
```

**它们不会因为渲染线程退出而自动醒。**

关键在于**标志位只在循环顶部被查**，而这两条线程根本回不到循环顶部：

| 线程 | 阻塞在 | 标志能救它吗 | 靠什么醒 |
|---|---|---|---|
| 收包 | `recvFrom(..., 200ms)` / `queueA.push()` | 部分 | 超时，或 `close(A)` |
| 解码 | `queueA.pop()` / `queueB.push()` | **不能** | **只能靠 close** |
| 渲染 | `popFor(队列B, 5ms)` | 能 | 超时，自己会醒 |

解码线程是最惨的那个：它两头都可能无限期阻塞，而 `pop()` 是**没有超时**的条件变量等待。
标志位对它**一点用都没有**。

> **退出 = 置标志 + 唤醒，缺一不可。**
> 标志说"该走了"，`close()` 让它**有机会听见**。

**还有一个约束，是签名带来的**

```cpp
Status run(const std::atomic<bool>& stopRequested);
                 ^^^^^ const 引用 —— 管线写不了它, 写它是编译错误
```

这个 `const` 在 M2 是对的：那时所有停止信号都从外面来（signal handler 写 `gStopRequested`），
管线只需要读。但窗口关闭是**管线内部产生**的第四个触发源，它没法借这个变量往外传。

所以管线必须**自己再有一个** `std::atomic<bool> stopping_`，三条循环判两者的并集：

```cpp
while (!stopRequested.load() && !stopping_.load()) { ... }
```

**做法**

四个触发源（Ctrl-C / 窗口关闭 / `maxFrames` / `idleTimeout`），**一个收尾函数**：

```cpp
void ReceiverPipeline::requestStop() {   // 任何线程都能调, 调几次都行
    stopping_.store(true);   // 让还在循环里的线程下一轮就退出
    queueA_.close();         // 唤醒堵在 pop(A) 的解码 / 堵在 push(A) 的收包
    queueB_.close();         // 唤醒堵在 push(B) 的解码
}
```

三件事必须一起做，少一条就有线程醒不过来。

**为什么不能由 `run()` 统一协调**：`run()` 那条线程已经堵在 `join()` 上了。
收尾动作**只能由三条工作线程自己发起**。

**并发发起是安全的**：`std::atomic<bool>` 的写天然安全，`BoundedQueue::close()`
内部加锁且幂等（置位 + `notify_all`），重复调、多线程同时调都没问题。不需要额外互斥。

**顺带澄清两个容易混的机制**

```text
Ctrl-C  ->  SIGINT  ->  main.cpp 的 onSignal()  ->  gStopRequested = true
                        (内核送信号, 跟 SDL 一点关系都没有)

点  x   ->  窗口系统  ->  SDL 事件队列  ->  渲染线程 SDL_PollEvent()
```

Ctrl-C **不经过 SDL 事件泵**。之后哪条线程先"发现"，取决于谁先回到循环顶部
（渲染 5ms 一轮、收包 200ms 一轮），所以通常是渲染线程 —— 但这不保证，也不重要：
**谁先发现谁调 `requestStop()`**。

**一般规律（比结论本身重要）**

> **`join` 一个线程之前，它可能阻塞的每一个地方，都必须已经被打开了。**

写多线程收尾时，先把"每条线程会阻塞在哪几个点"列成一张表，
再逐个回答"这个点靠什么被唤醒"。表上任何一格填不出来，那里就是将来挂死的位置。


## D18. 跨线程读统计：先问"要多强的一致性"，再选机制；"无锁"不等于"更轻"

**症状**
三线程化之后，每秒那行统计由渲染线程打：

```text
[INFO] fps=30 latency p50=8 p95=14 | 队列A=0 队列B=1 | 丢帧=0 组包丢包=0
```

但数字散落在别的线程手里：`AssemblerStats` / `JitterBufferStats` 由**收包线程**每收一个包
就 `++`，`DecoderStats` 由**解码线程**改。渲染线程直接 `assembler_.stats()` 读它们 ——
看着人畜无害，一行日志而已。

**机制**

这是**数据竞争**：非原子的 `uint64_t` 被一条线程写、另一条同时读。
C++ 标准直接判它未定义行为，**不是"值可能不准"**。编译器有权假设不存在竞争，
于是可以把 `++stats_.packetsReceived` 缓存在寄存器里、可以重排、可以拆分读写。

**但要说实话**：在这个具体形状下，最可能看到的现象只是**字段之间错位** ——
`packetsReceived` 是刚才那个包之后的值，`packetsMalformed` 是再之前的。
因为 `assembler_.offer()` 是跨编译单元的非内联函数，每次返回时那些值必然已经落到内存。

问题在于**这份正确性是碰巧的**：

- 开了 LTO，`offer()` 可能被内联进收包循环 -> 编译器就有机会把计数器提到寄存器里，
  整个循环结束才写回 -> 渲染线程会读到一个**几秒钟不动**的数字
- 哪天有人把 `offer()` 挪进头文件变成 `inline`，同样的事
- ThreadSanitizer 会直接报错，以后想把 TSan 加进 CI 就得先解决它

> **"当前编译器碰巧没这么优化"不是一个可以依赖的性质。**

**先问需求，再选机制**

> **这一行日志需要多强的一致性？**
> "每个字段各自正确" 还是 "所有字段属于同一瞬间"？

对一行给人看的统计，前者就够。而且实际偏差比直觉小得多：渲染线程读那五六个字段是
连续几条 load 指令（纳秒级），包是每约 1.3ms 来一个（640x480@30fps 约 750 包/秒）——
两次 load 之间大概率一个包都没来，最坏差 1 个包。

判据：**什么情况下"字段之间差几个包"会让你做出错误的判断？** 想不出来，就不需要一致快照。

**两条路的对账（结论跟直觉相反）**

| | 改动面 | 热路径 | 得到的保证 |
|---|---|---|---|
| **B. 计数器改 `std::atomic`** | 三个 stats 结构体共约 20 个字段全改；`expectedPackets()`/`packetsLost()` 里加 `.load()`；结构体变**不可拷贝**，`ReceiverPipeline.cpp:105` 的 `stats_.assembler = assembler_.stats();` 直接编译不过，要手写逐字段赋值 | 每包约 6 次 `lock xadd` | **弱** —— 字段之间仍会错位 |
| **A. 快照 + 一把锁** | `FrameAssembler`/`Decoder`/`JitterBuffer` **一行不改**；只在 `ReceiverPipeline` 加 1 个 mutex + 1 个 `shared_` 快照 + 3 处调用 | 加锁频率自己定，可以降到 10 次/秒 | **强** —— 一致快照，白送的 |

A 的写法：

```cpp
mutable std::mutex statsMu_;
ReceiverPipelineStats shared_;

// 工作线程循环里(可以每包一次, 也可以每 100ms 一次 —— 统计行一秒才打, 陈旧度看不出来)
{
    std::lock_guard<std::mutex> lk(statsMu_);
    shared_.assembler = assembler_.stats();
    shared_.jitter    = jitter_.stats();
}

// 渲染线程要打印时
ReceiverPipelineStats snap;
{ std::lock_guard<std::mutex> lk(statsMu_); snap = shared_; }
```

各个 stats 结构体仍然**被各自的线程独占**，本来就没有竞争 —— 需要同步的只有那次快照拷贝。

**成本算给你看**：无竞争的 `std::mutex` 加解锁约 20ns（快路径就是一次原子 CAS，不进内核）。
750 次/秒 x 20ns = **15 微秒/秒**，0.0015% 的 CPU。而且这里几乎没有竞争 ——
一个写者，读者一秒才来一次。"加锁会堵塞"需要两条线程同时抢同一把锁，这里一秒最多撞一次。

**一般规律（比结论本身重要）**

> **"无锁"不等于"更轻"。**
>
> 在这个场景里它**改动面大 20 倍、保证更弱、热路径反而更重**。
> 真正省下来的东西是锁本身，而锁在这个频率下根本不是瓶颈。

选同步机制的顺序应该是：

1. **先定需要多强的一致性**（每字段正确 / 一致快照 / 严格顺序）
2. **再看改动面**（要动几个模块？会不会让类型变得不可拷贝，从而波及一堆调用点？）
3. **最后才算性能**，而且要算**绝对数字**不是相对感觉 ——
   "锁比原子慢"是对的，但 15 微秒/秒 这个绝对值让这句话失去意义

反过来做（一上来就挑"听着最快的那个"），你会得到一份改动面巨大、保证更弱的代码，
而省下的那点开销在火焰图上根本看不见。

**顺带一条**：`BoundedQueue::size()` / `peak()` **本来就加了锁**
（`BoundedQueue.h:193`，注释写着"返回即过期，只能用于观测"），队列深度这一格不用操心。


## D19. 收尾路径上的"失败"不是失败；假错误会按优先级盖掉真错误

**症状**
三条线程各自把自己的结果写进 `recvStatus_` / `decodeStatus_` / `renderStatus_`，
`run()` 在 `join()` 之后按"上游优先"挑一个返回 —— 看着很干净。

然后用户点了窗口的 ×，程序**退出码是 1**，日志里一行红字：`队列已关闭`。
用户只是正常关个窗口，程序报告说自己失败了。

更糟的一次：这台机器没有 `DISPLAY`，渲染线程 `open()` 真的失败了，
但 `run()` 返回的还是 **`队列已关闭`** —— 真正的原因被盖掉了。

**机制**

走一遍点 × 的路径：

```text
渲染线程:  pumpEvents() 返回 true
           -> requestStop():  stopping_ = true;  queueA_.close();  queueB_.close();
           -> renderer_->close();  退出

解码线程:  此刻正堵在 queueB_.push(frame) 上
           -> 被 close(B) 唤醒 -> push() 返回 false     <- 这一行

收包线程:  此刻正堵在 queueA_.push(frame) 上
           -> 被 close(A) 唤醒 -> push() 返回 false     <- 这一行
```

那两行 `false` 是**正常收尾的一部分**，不是故障。写成错误就有两层后果：

**表层** —— 每次正常退出（点 ×、Ctrl-C）`run()` 都返回非 `Ok`，`main.cpp` 退出码变 1。
顺带一提，`test_receiver_pipeline.cpp` 里 15 个用例都有 `ASSERT_TRUE(done.get().isOk());`，
会当场全红。

**深层（这个才要命）** —— 它跟"上游优先"这条规则互相咬：

```text
真实故障:  渲染线程 open 失败(没有 DISPLAY)  ->  renderStatus_ = IoError("SDL_Init failed")
                     |  requestStop()
假错误:    收包线程 push 返回 false           ->  recvStatus_  = NetError("队列已关闭")
                     |  上游优先
run() 返回: NetError("队列已关闭")             <- 真正的原因被埋掉了
```

**噪声按优先级排在了信号前面。** 两个各自都合理的决定，凑一起就把最需要看清的那一刻弄糊了。

**做法**

`BoundedQueue::push()` 的 `false` **只有一个含义**，看实现就知道：

```cpp
notFull_.wait(lk, [this]{ return q_.size() < cap_ || closed_; });
if(closed_) return false;      // 唯一的 false 出口
```

它不会因为"队列满"返回 false（那时它阻塞等待），只会因为**关闭**。
所以 `push()` 返回 false 时写 `Status::ok()` 是**无条件正确**的。

**一般规律（比结论本身重要）**

> **收尾路径上的每一个"失败"返回值，都要先问一句：这是故障，还是正常结束？**
>
> 分不清的话，第一个真正的故障就会被一堆收尾噪声埋掉 —— 而那正是你最需要看清楚的时刻。

这跟 `ISource::readFrame()` 为什么返回 `Status` 而不是 `bool` 是同一件事，
它的 `@note` 原话是：

> 就是为了让调用方能区分**正常结束**和**设备炸了**：前者安静退出，后者必须报警。
> 一个 bool 会把这两件事混成一件。

区别只在于：那边是**接口设计**（要不要提供这个区分），这边是**调用方使用**
（拿到了这个区分，要不要用对）。**提供了区分而用错，比没有区分更危险** ——
因为你会以为自己已经处理过了。

**和 [[D17]] 的关系**：同一条收尾路径上的两个坑，角度相反 ——
D17 是线程**醒不过来**，D19 是线程醒过来之后**说错话**。
